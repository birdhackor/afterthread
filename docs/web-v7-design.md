# web-v7 設計：接續修正

本文件是 web-v7 的**設計本體**。它經過兩輪設計審查：第一輪兩位審查者各兩則（第一則只看問題與
程式、獨立判斷，第二則對照草稿），第二輪由兩位沒參與過的審查者審最終稿與各方案的取捨。兩輪的
結論都是「方向可行」，逐條處置見附錄 A、B。實作計畫見 `docs/web-v7-plan.md`，實作期間的裁決記在
`docs/web-v7-decisions.md`（從 D48 起編號）。

## 0. 結論

修正沒有發布時，後端把這一輪的成果存成一份**未完成的修正（草稿）**：放在工具自己的套件目錄裡，
是工作區檔案的完整複本，加上一份記錄每一輪怎麼結束、AI 的交接筆記與需要操作者動手之事的說明檔。

操作者之後可以：

- 改 `config.env`、換憑證，或直接改草稿裡的檔案，再按「**接續修正**」：後端把草稿複製到新的暫存
  工作區，跑一場新的 builder session，提示帶上上一輪的交接筆記、後端量到的停止原因與變更清單；
- 自己把剩下的改完，按「**發布草稿**」：不呼叫 AI，後端驗證後發布，接著照常跑 `examples.json`；
- 或「**放棄**」。

每個工具最多一份草稿；發布成功才刪除；放棄要明確按。

## 1. 起因與問題

一次一鍵修正沒有發布：修正有一部分必須由操作者手動改 `config.env`（builder 被明令不能寫
`config.env`／`.env`），而且 builder 的工具呼叫用到了上限。兩件事本身都合理，問題在結束之後留不下
可以接續的東西。

| # | 問題 | 依據 |
|---|---|---|
| G1 | 沒發布的修訂留不下可靠、找得到的接續成果：工作區在 job 結束時一律清掉；清理失敗的殘留沒有接續的契約 | `run_revise` 的 `finally` → `_cleanup_staging` |
| G2 | 下一輪對上一輪一無所知，重新複製、重新重現、重新診斷 | `run_revise` 每次新開 `uuid4()` session；`_revise_user_prompt` 沒有「上一輪」。AI 日誌不是可靠的 checkpoint：工具參數只在下一次請求的訊息裡出現，受 `llm_log_body_max_chars` 與總量預算截斷、較舊的整段會被省略，ring 也只在記憶體 |
| G3 | 需要操作者動手的修正，沒有「做完再回來」的入口；再按一次修正就從零開始 | `not_published` 卡片沒有接續入口；`fixable` 不受影響，按鈕仍在 |
| G4 | 停止原因只有模型自己的話；同一個原因可能成為不同結局：回合用完可能是 `ready=false`，也可能是收尾那次回空內容（`EmptyResponse`）或格式錯（`InvalidStructuredOutput`）；逾時則沒有 summary | `llm.py` 的 `_run_structured`、`_extract_content` |
| G5 | 結果只在記憶體：job 表最多 20 筆、重啟即失 | `tool_builder._MAX_JOBS` |
| G6 | 沒有穩定的入口讓人看或改做到一半的程式 | 同 G1 |
| G7 | 模型不知道自己的回合數與對話大小上限；單一指令的逾時只寫成 "a couple of minutes" | `_BUILDER_SYSTEM_PROMPT`、`_REVISE_PROMPT_ADDENDUM` |

「工具呼叫次數超過上限」可能是下列任何一種：

| 上限 | 發生時 | 結局 |
|---|---|---|
| 回合數 `TOOL_INSTALL_MAX_ROUNDS`（預設 24，上限 64） | 下一次請求不帶工具，附 `_TOOL_BUDGET_EXHAUSTED` | 依最後的 JSON：`not_published`、發布（未經模型驗證），或失敗（`EmptyResponse`／`InvalidStructuredOutput`，沒有 summary） |
| 對話大小 `LLM_TOOL_CONVERSATION_BUDGET_TOKENS`（500k） | 同上，模型看到同一句話 | 同上 |
| 單一回覆的前 16 個呼叫照常執行 | 第 17 個起不執行，回拒絕文字 | 不結束 |
| 單一回覆超過 64 個呼叫，或呼叫內容與參數的字串長度合計超過 256×1024 | `tool_calls flood`／`oversized` | 失敗，沒有 summary |
| 總時間 `TOOL_INSTALL_TIMEOUT_SECONDS`（900 秒） | `asyncio.timeout` | 失敗，沒有 summary；當下的 `run_shell` 指令仍會跑到 `TOOL_INSTALL_SHELL_TIMEOUT_SECONDS`（預設 120，上限 600） |

本設計對每一種都成立：這一輪留下了東西，就存起來。

## 2. 不做的事

- **保存或重播完整對話**：工具輸出（真實 API 回應、附上紀錄的內文）會落地，成為 purge 清不到的副本；
  改過設定之後舊輸出也過時。
- **自動接續**：每一輪都是操作者按下的付費 session；「多跑一點」用 `TOOL_INSTALL_MAX_ROUNDS`。
- **安裝（新工具）的接續**：沒有既有套件當基準，形狀不同，另議。
- **網頁編輯 `config.env`、一鍵套用 AI 建議的設定**：寫入的原子性、衝突與權限尚未定義。
- **基底改變後自動 rebase 或合併**：見 §3.6。
- **一般化的持久 job 系統。**

## 3. 草稿

### 3.1 放在哪、存什麼

`<tools_dir>/<name>/.afterthread.meta/draft/`，只經由這個套件自己的、真目錄的 `.afterthread.meta/` 到達：
它是連結或不是目錄時，這個套件沒有自己的草稿，讀取、放棄、保存與 sweep 都不經過它。

- `files-<hex>/`：某次保存時工作區檔案的完整複本。目錄名用隨機十六進位，不用序號。
- `manifest.json`：說明檔，有大小上限；以 `tools._write_package_file_atomic` 原子寫入，以
  `_read_regular_file_capped` 讀取並驗證形狀。

| 欄位 | 說明 |
|---|---|
| `draft_id` | 這份草稿的識別，建立時隨機產生，放棄後重建的草稿必定不同 |
| `generation` | 說明檔的修訂號，每次改寫說明檔加 1；接續與放棄以 `(draft_id, generation)` 做樂觀比對 |
| `files_dir` | 目前生效的檔案目錄名 |
| `kept` | 接續換成新的檔案目錄時，上一份先記在這裡，確認可以刪才刪；沒刪的就留在這裡（§3.3 第 11 步）。sweep 不收 |
| `base_vid` | 第一輪複製的版本 |
| `feedback` | 第一次送出的意見（已遮蔽、截斷） |
| `runs` | 附上的失敗紀錄**只存引用與摘要**：id、時間、workflow、vid、結果、exit code，不存參數與輸出 |
| `attempts` | 最近 5 輪：job id、起訖時間、後端量到的停止原因與回合數、錯誤（安全的使用者訊息）、summary、handoff、operator_action、該輪的操作者說明、該輪沒存的檔案。文字一律先遮蔽再截斷，再以寫進說明檔的形式（JSON 字串字面）檢查一次。沒有留下結束紀錄的一輪，結局是 `interrupted`，結束時間留空（§3.5） |
| `running` | 進行中那一輪接續的 job id 與開始時間（只有接續會寫，§3.5） |
| `publishing` | 正要從這份草稿發布時寫入的意圖紀錄（§3.5），用來在重啟後對帳 |

**為什麼放在套件層，而不是讓工作區原地留在 `.staging`、說明存 SQLite**（附錄 A 有兩方的完整考量）：

- 刪除工具時整個套件目錄一次搬走，草稿跟著消失；同名重裝不會繼承舊草稿；沒有孤兒草稿，也不必和
  執行紀錄的 purge 互相牽扯。
- `.staging` 維持今天的語意（一場 session 的暫存，結束就刪），README 與文件站的「`.staging` 殘留
  可以直接手動刪除」仍然成立；把草稿留在 `.staging` 會讓這句話變成刪除唯一成果的指示。
- session 仍在 `.staging` 裡跑，builder 從不在套件目錄裡起跑，既有 staging 防護不變。
- 套件層 `.afterthread.meta/` 的讀取只讀固定檔名（`_resolve_current_data`、`_read_enabled_state`、
  遷移的 `_has_our_state_marker`），多一個 `draft/` 不影響它們；v5 §4 的版面要補上它。

**為什麼存整個目錄，而不是只存改過的文字檔**：操作者要能直接打開、修改做到一半的程式；`entry` 可以是
`["./run.sh"]`，執行權限要保得住；二進位檔與連結也是。

### 3.2 每一輪都在新的暫存工作區

- 第一輪：照舊從 `versions/<current>` 複製到 `.staging/<uuid>/build`。
- 接續：把草稿的 `files_dir` 複製到新的 `.staging/<uuid>/build`，用保存的同一條複製管線：
  - 連結依來源改寫成相對連結；
  - 邊複製邊累計檔案數與大小；
  - 在複本上再判一次連結並解析；
  - 複本整棵重掃秘密，命中的不帶入。

  另外，根目錄有兩樣不帶入：
  - `.env`，含大小寫不同、但其實是同一個條目的名字。操作者若把 `.env` 放進草稿，它的值不在已知秘密集合裡，不能讓
    `read_file` 讀進對話。判斷「是不是同一個條目」的查詢失敗時，也不帶入。
  - `.afterthread.meta/`。

  沒帶入的都記下，告訴模型與操作者。複本要保住權限位元，因為 §3.3 第 11 步要比對雜湊。

session 執行期間不碰草稿目錄；草稿只在保存那一步換成新的目錄。上一份成果在新的一份確認落盤之前
不會被刪；上一輪殘留的指令只寫得到它自己的暫存目錄（除非它循著連結寫出去，§3.3 第 6 步的連結規則
就是為此）。

代價：後端在一輪中途重啟，這一輪的進度不會進草稿，草稿回到上一份。暫存目錄留在 `.staging` 底下，但沒有畫面指向它。

### 3.3 保存

保存發生在兩個時點：一輪結束而沒有發布時，以及 `ready=true`、發布**之前**。全部在 worker 上，包含
下列步驟：

1. **等這一輪自己啟動的 `run_shell` 全部結束。** 只有逾時的路徑會有在飛的指令（正常路徑上，迴圈
   每輪都等完所有工具結果才送下一次請求）。每個指令在受保護的 task 裡跑；session 結束時設下這一場的
   中止訊號，`_communicate_bounded` 在輪詢時看到它，就用自己在 `teardown_lock` 下的拆除流程殺掉
   process group 並回收（不從外部 kill，免得打到已回收而被重用的 PID），再等每個指令的停止證據；訊號設下之後
   才要啟動的指令不會啟動。一個指令只在兩種情況算**已停止**：它的 leader 已回收，而且回收之後它的
   process group 已不存在（`_communicate_bounded` 的拆除在回收後立刻確認，之後持續確認到拆除的時限），
   或它根本沒有啟動子行程。
   SIGKILL 送出成功不算：送到不等於已退出，而 macOS 送訊途中 fork 出來的成員根本收不到。asyncio task 的狀態（關閉時 task 會被
   取消，worker 卻還在跑）、worker 返回（它可能在拆除之前就被例外打斷）、時間到，都不算。無法確認停止，
   這一場的保存、發布、清理就永久放棄，暫存目錄原地保留並回報路徑，之後的 job 也不碰它；名額守的是
   後端寫入者之間的互斥，已放棄寫入的 session 不再持有它。這個出口不得再等待可能被卡住的資源，例如
   共用的 threadpool（D52）。現有的清理與發布也因此不再與還在跑的指令競爭。
2. **剝除** builder 寫的 `.env`（`_strip_builder_env`）與根目錄的 `.afterthread.meta/`
   （`_strip_builder_sidecars`）。剝除失敗就不保存檔案。
3. **確認工作區**：`_verify_staging_root`，加上存在、是目錄、不是連結（現有函式對不存在的路徑放行）。
4. **值不值得存**：
   - 第一輪：工作區相對基底有變更，或模型交回的 summary／handoff／operator_action 不是空的，才建立
     草稿。
   - 接續：工作區與開工時複製進來的內容逐檔雜湊相同（例如第一次請求就失敗），就只記下這一輪，不換
     檔案目錄。接著要發布的保存例外：一律複製，讓發布後的刪除有這次保存做出的複本可比（§3.5）。
5. **大小上限**：檔案數與總位元組有上限（設定值），算的是實際複製進草稿的東西，換回的舊版（第 7 步）
   也算，在複製時邊寫邊累計。超過就不保存檔案，記下原因。掃描之前另對工作區量一次，限的是掃描的成本。
6. **連結**：連結的目標以連結所在目錄為起點、純字串解析後仍在工作區內者，存成相對連結；指向工作區
   外（含其他檔案目錄、舊的暫存目錄、草稿本身）者不存，記進該輪沒存的檔案。目標路徑裡只要有 `..` 緊接在
   一個本身是連結的元件之後，也不存：作業系統會先解析那個連結，再從它指向的地方往上走，字串看不到（`x -> .` 加上
   `l -> x/../旁邊的目錄/f`，字串說在工作區內，作業系統卻走出去）。絕對目標不做字面正規化：只把開頭的
   工作區路徑換成相對的前綴，其餘元件（含 `.`、`..`）原樣保留、照同一條規則判。規則可以保守地拒絕作業系統其實
   解析在內的形狀，但都記進沒存的檔案；留下的連結，只要路徑上沒有換回舊版或沒存的項目，在複本裡解析到原本在
   工作區裡指向的同一個位置。這個判斷先在工作區上做一次，決定
   要不要規劃這個連結；換回舊版（第 7 步）會改變路徑上的元件是不是連結、指向哪裡，所以複製完成後，
   再以複本為根把每個連結判一次：先全部判完再刪，不過的不存，記進沒存的檔案。判斷一個元件是不是連結時，
   查詢失敗而不是回報「不存在」或「某一層不是目錄」，就是無法確認：這個連結不存，記為 `unreadable`。
   複本上判完之後，再以作業系統解析每個留下的連結（查詢錯誤會傳出來的那種解析），直接檢查安全性質：
   落在複本內、或確認懸空而且失敗的位置在複本內的才留；落在外面、在複本外懸空（之後寫到那裡的東西會讓它
   解析得到，例如第一輪最後才寫出的說明檔）、或無法確認的不存，記進沒存的檔案。這道檢查不改存下的字串，
   也不取代上面的規則（確認懸空的連結仍要通過它），保真則由對作業系統的差分測試守。兩道檢查都只對
   判斷時的那棵樹成立。
7. **秘密掃描**：用 P2 的完整掃描器，讀完整個檔案（分段、段間重疊至少「最長秘密長度減一」），並檢查
   檔名與連結目標。
   - 命中的路徑不保存這一輪的內容，改保留上一份（或基底）的版本；上一份也命中就整個不存。一律記下並
     告訴下一輪與操作者。
   - 掃描失敗就不保存檔案。
   - 不用遮蔽標記改寫內容，那可能改壞程式語意。
   - 工作區上的這一次決定規劃（哪些路徑換回舊版）。存下的是複本，而複本和工作區不全相同：換回的舊版、
     改寫成相對路徑的連結目標。所以複本做好、連結判過之後，用同一份已知秘密把**複本整棵**再掃一次，
     命中的路徑刪掉、記進沒存的檔案；這次掃描失敗就整輪不保存檔案。檢查的是寫到磁碟上的那個形式。
   - 這條保證的範圍是「後端保存的產物，以保存當時的已知秘密檢查過」；保存之後才登記的秘密、或操作者
     手放進草稿的內容，由下一次複製進暫存工作區時的掃描處理（§3.5），在那之前磁碟上的舊內容不變。
8. **持有共享 tools lock**（`tools.acquire_shared_tools_lock`，與 `_make_handler`、健康檢查相同）
   直到第 11 步結束：期間刪除工具會回 `409 ai_job_in_progress`。在鎖內確認套件目錄仍是開工時那一個
   （`<tools_dir>/<name>` 的 `(st_dev, st_ino)` 與開工時相同）；不是就不保存。草稿目錄只用不遞迴的
   `os.mkdir` 建立在既存的 `.afterthread.meta/` 之下，永遠不重建已刪除的套件。基底版本讀不到、
   `current` 已經移動，都**不**阻止保存：草稿照存，只是狀態為已過期（§3.7），可以檢視、取回、放棄。
9. **複製（不是搬移）**工作區到 `draft/.incoming-<hex>/`，fsync 整棵樹，rename 成 `files-<hex>`，
   fsync `draft/`。第一次建立 `draft/` 時一併 fsync 它的上層。用複製：若還有程序在原工作區寫入，
   寫到的是暫存目錄。先寫暫名再 rename：崩潰留下的半成品不會擋住下一次保存。
10. **原子寫入新的說明檔**：`generation` 加 1、指向新目錄、記下這一輪、清掉 `running`；接續時，
    上一份檔案目錄同時記進 `kept`。用 `_write_package_file_atomic` 的 `durability_out` 取得「是否已確認
    落盤」。
11. **處理上一份檔案目錄**：只在接續、而且換成了不同的新檔案目錄時才做。它已在第 10 步記進 `kept`，
    下面三件事都親眼確認了，才當場刪：
    - 第 10 步確認落盤；
    - 開工時它的雜湊（`copied_out`，複製之前取），與複製完成、模型開始之前的工作區雜湊（`copied_in`）
      相同：帶進工作區的正是開工時的內容。漏掉的項目、改寫的連結、複製期間被換掉又換回來的檔案，都會讓
      兩者不同；
    - 它現在的雜湊仍等於 `copied_out`：這一輪進行中沒人改它。

    其餘情況它留在 `kept`，告訴操作者它在哪、為什麼留。`kept` 的名字要等之後改寫說明檔時，親眼看到它不在
    （`lstat` 回不存在）才拿掉。只記一輪、保存失敗、沿用原本的檔案目錄時，都不動上一份。

任何一步失敗：

- **說明檔照樣改寫**：檔案沒存成時，仍盡量記下這一輪、清掉 `running`，`files_dir` 不動。秘密清單不完整時
  不寫，連失敗說明也不寫。
- **保存交回三件事**：檔案是否存成新的檔案目錄（`saved`）、這一輪是否已經記進說明檔、說明檔是否確認落盤。
- **保存失敗不改變這一輪的結局。**
- **job 卡片照實說**：
  - 這一輪的進度沒有存進草稿；
  - 成果留在哪裡；
  - 接續時，請取回草稿裡需要的內容。不宣稱草稿的檔案是哪個時點的：它可能來自更早的某一輪，也可能被手改過。

**成果沒有人接住，就不清暫存**：指令確認停止之後，這一輪的暫存目錄只在下列情況清除：
- 成果已經存進草稿，而且說明檔確認落盤；
- 已經發布；
- 沒有值得保存的東西：第一輪沒有變更，模型也沒有交回筆記；
- 建置器的 `.env` 剝除失敗：工作區可能還留著它，所以嘗試清掉，不保存檔案。

其他出口一律保留，包括：
- 保存沒存成；
- 保存寫了說明檔，卻無法確認落盤（`saved` 仍是 True）；
- 發布失敗，而發布前的保存沒有確認落盤；
- 遮蔽模型筆記時拿不到完整的秘密清單。

保留的規則：
- **先剝除建置器的 `.env`**：保留之前一律先剝除。指令確認停止之後先剝除，再遮蔽筆記、保存；例外或取消時，在保留
  之前補剝。剝除失敗就照上面的例外清掉。
- **旗標立起的時點**：在取得停止證據的當下立起，向外傳播的例外與取消也接得到。
- **回報的路徑**：job 回報成果實際所在的路徑（「成果留在 …」）。發布分兩段搬移：暫存的 `build` 先搬到同一場的
  `shell`，再搬進 `versions/<vid>`。所以成果可能在暫存目錄裡，也可能已是 `versions/` 底下一個沒被 `current`
  指到的版本；回報的是它當下所在的那一個。
  - 這個承諾只對正常返回、而且位置已知的出口成立。例外與取消只在後端記錄寫 session 的路徑。
  - 工作區本身驗證不過時，只能說原本的工作區路徑沒有確認。
- **還在寫的 worker**：發布的 worker 可能還在寫暫存目錄時（取消送達時它還在跑），也不清除。
- **組版本來源說明**（遮蔽秘密）失敗，也算發布失敗。
- **無法確認停止的出口**：照 §3.3 第 1 步，不剝除，整個保留。

**sweep**（`_sweep_stale_backups`，在 job 收尾、排他鎖下執行）：
- 前提：讀說明檔，解析成功、`files_dir` 合法，而且先對說明檔與 `draft/` 目錄做 fsync 成功，才收 `.incoming-*`；
  任一條件不成立，就整個 `draft/` 不碰。
- 另外收已授權刪除（放棄、發布後刪除）改名留下的殘留。
- **不收沒被說明檔點名的 `files-*`**：「沒被點名」不是可以刪的證據。說明檔寫完、還沒確認落盤就當機，舊說明檔回來，
  新的檔案目錄就變成沒被點名，而操作者可能已經照畫面給的路徑改過它。這種目錄留到放棄為止。

### 3.4 送出接續

順序沿用現行 revise；草稿的判定放在取得名額**之後**，與 `expected_vid` 相同（不變量 K）。

請求帶 `draft_id` 與 `draft_generation` 就是接續：兩者要嘛都有、要嘛都沒有（否則 422），`draft_id`
符合 `DRAFT_ID_PATTERN`，`draft_generation` 至少為 1。

1. **路由**：讀一次說明檔，取出記著的紀錄 id。這一次在名額之前，只為了用 DB session 重讀，讀不到就當沒有。
   - 從 `tool_run` 寬鬆重讀：已被清除的只留說明檔裡的摘要，不拒絕。
   - 新附上的 `run_ids` 照舊嚴格檢查：不存在回 404，屬於別的工具回 422。
   - 兩者合併：新附的排在前面，去重，最多 3 筆。
2. `.env`／`config.env` 閘，在名額之前。
3. 取得名額 → `job_busy`。
4. 解析套件與 `current`；`expected_vid` 比對 → `version_mismatch`。前端送的就是草稿的 `base_vid`，
   所以 `current` 已移動的情況多半在這一步擋下。
5. **再讀一次說明檔**並判定。沒帶 `draft_id`：有草稿回 `409 draft_pending`（可接續時說「請接續或放棄」，
   其他狀態說「請先放棄」；狀態由清單用的同一個判定算出），沒有草稿就是第一輪。帶了 `draft_id`，依序看
   第一個成立的：

| 情況 | 回應 |
|---|---|
| 看到 `draft/` 不存在 | `409 draft_gone` |
| `draft/` 看不到，或說明檔讀不出、形狀不對 | `409 draft_unusable` |
| `draft_id` 不同 | `409 draft_gone` |
| `generation` 不同 | `409 draft_changed`：同一份草稿在畫面讀到之後被改寫過（例如另一個分頁剛接續），畫面重讀。放棄後重建的是另一份，落在上面的 `draft_gone` |
| 檔案目錄不在，或不是目錄 | `409 draft_unusable` |
| 有 `publishing`：正在發布、已發布或結果未知（§3.7），不讀 origin | `409 draft_publishing` |
| 說明檔的 `base_vid` 不是 `current`（後端自己比，不只靠請求的 `expected_vid`） | `409 version_mismatch` |
| 第 1 步讀到的不是同一份 `(draft_id, generation)`，含第 1 步讀不到 | `409 draft_changed`：這一輪用的紀錄，必須是判定的那份說明檔記著的 |

每個拒絕碼在路由都有對應，沒有對應的不能變成 500。

6. 轉成 job。

### 3.5 開工與結束（job 內）

**第一輪**開工時不寫任何草稿資料；只在結束時依 §3.3 決定要不要建立。

**接續**開工：

1. 前置檢查照舊：job 內那一道 `.env` 閘、秘密登記等等。這些拒絕都不碰草稿。
2. 在說明檔寫入 `running`（job id、開始時間）。
   - 寫不進去 → 這一輪不開始、不花錢，job 失敗並說明。
   - 寫入要在共享鎖內，確認套件仍是原來那一個，說明檔仍是判定時那一份。
   - 這次寫入交回寫完的說明檔（新的 generation），之後的保存與比對都用它。
   - 發現上一個 `running` 沒清：先把它記成一輪，結局 `interrupted`，`finished_at` 留空，`job_id` 與 `started_at`
     取自舊標記。沒有其他占用名額的 job，但這證明不了它的指令已經停止。
   - `kept` 先修剪掉看到不在的名字，仍達上限就不開始。
3. 先記下草稿檔案目錄的雜湊（`copied_out`），再用保存的同一條管線，把它複製到新的暫存工作區（§3.2），全程持共享鎖。
   - 複製之前先量一次大小，超過就不開始。
   - 整棵的掃描失敗也不開始。
   - 複製完成、模型開始之前，再記下工作區的雜湊（`copied_in`）。§3.3 第 4、11 步要用這兩個雜湊。
4. 其餘照舊：meta-tools、預算。`config.env` 與 `.env` 每輪重讀。

**一輪由誰收尾**（接續）：
- **未開始**：第 2 步之後、開始對話之前的出口。清掉自己的 `running`，不算一輪，`runs` 不變。
- **已執行**：對話結束、指令確認停止之後的每個正常出口，都把這一輪記進說明檔，並清掉 `running`。
  - 保存已經記下的，不再記。
  - 還沒記的，另外寫一次，只記這一輪：工作區驗證不過、sidecar 或 env 剝除失敗、保存前就失敗、保存意外失敗。
  - 這一次寫入要在鎖內確認：套件身分、`draft_id`、第 2 步交回的 generation，以及 `running.job_id` 是這個 job。
    任何一項不符，或寫不進去，`running` 就留著。
  - 這一輪新附的紀錄，在這次寫入時併進 `runs`。
- **指令無法確認停止，或未預期的例外**：不碰說明檔，`running` 留著，留給下一輪記成 `interrupted`。

**結束**：

| 結局 | 草稿 |
|---|---|
| `ready=true` | **流程**：依 §3.3 先保存，這次一律複製；在說明檔寫入 `publishing`（job id、時間）；發布。<br>**發布成功，而且下面兩件事都成立 → 刪除整個草稿目錄**：草稿的檔案仍是發布前存下的那一份（與保存時記下的指紋相同）；`draft/` 裡除了說明檔與那份檔案目錄，沒有別的東西。刪的時候先改名再刪，同 `delete_tool`。<br>**發布成功，但下面任一種 → 留著草稿**：<br>• 有額外的項目（`kept`、沒被點名的目錄、別的東西），或內容不同：job 卡片說草稿仍有額外的項目，可能含沒發布的內容。<br>• 無法確認（讀不完整）：job 卡片照實說無法確認。<br>• 刪不掉。<br>這幾種都是「已發布」，只能放棄；清單的說明提醒，先取回需要的內容再放棄。<br>**接續的發布前保存沒存成、發布卻成功**：不寫 `publishing`。job 帶出保存或補記交回的草稿身分，都沒有時才用開工時的身分，說這一輪沒存進草稿。<br>**發布失敗**（驗證、內嵌秘密、基底被換、搬移之後的寫入）：剛存的就是成果，清掉 `publishing`，記下錯誤。保存沒確認落盤時，暫存照 §3.3 保留 |
| `ready=false`、逾時、上游錯誤、格式錯誤、改名被拒 | 保存（§3.3） |
| 開工前就被拒（job 內的 `.env` 閘……） | 草稿不動，不算一輪 |
| 寫入 `running` 之後、開始對話之前被拒（複製、掃描、大小、`kept` 上限） | 清掉自己的 `running`，不算一輪 |

`origin.feedback`：原本的意見＋各輪操作者的說明＋附上紀錄的摘要（不含 stderr 與參數，不變量 V）＋
「草稿 `<draft_id>`，經過 N 輪」。各段先遮蔽，整段由呼叫端截到 20,000 字，讓 `origin.json` 遠低於
`_AI_META_MAX_BYTES`，不會在搬移之後才寫入失敗。

### 3.6 基底被手改（資訊，不是閘門）

草稿可能放好幾天，期間操作者可以手改基底版本（D21）。`package_identity` 只看 `tool.json`，
`docs/web-v5-design.md` §12 也明文接受「改 `run.py` 不動 `tool.json` 不會被拒絕」。

本設計**不**把整樹內容指紋當成接續或發布的閘門：工具執行時以版本目錄為 cwd，會在裡面寫
`__pycache__`、快取或 log（這個 repo 的執行環境沒有設 `PYTHONDONTWRITEBYTECODE`）。拿它當閘門，
一個只是在執行期寫了檔的工具，會讓付費成果變成只能放棄的「已過期」，也等於未經裁決就推翻 v5 §12。

已過期只由 `current != base_vid` 判定。「基底在草稿建立後被改過哪些檔」做成**資訊**：只比對開工時
就存在的檔案（新增的檔不算），告訴模型與操作者。這與逐檔合併一起放在後續階段，另做設計審查。

### 3.7 狀態

讀取時推導，依序判定：

1. **進行中**：`running` 指向本行程裡 queued 或 running 的 job。
2. **無法使用**：說明檔讀不出或形狀不對、`files_dir` 不在或不是目錄。只能放棄。
3. **發布中／結果未知**：有 `publishing`。job 仍在 → 發布中；job 已不在 → 看 `current` 的
   `origin.json`：`previous == base_vid` 而且 `feedback` 帶這份草稿的 `draft_id` → 已發布（顯示哪一版，
   只能放棄）；否則 → 結果未知（說明情況，只能放棄或到路徑取回）。
4. **已過期**：`current != base_vid`。可以檢視、到路徑取回、放棄。
5. **可接續**：以上皆非。`running` 留著，但 job 已不在或已結束時，顯示「上一輪沒有正常結束，它的進度沒有存進草稿」。
   不說草稿的檔案是第幾輪的：保存沒存成之後，它可能來自更早的某一輪，也可能被手改過。

### 3.8 放棄

`DELETE /api/tools/{name}/draft`，帶 `draft_id` 與 `generation`；無法使用的草稿改帶列表給的
`discard_token`（由草稿目錄與說明檔的檔案身分算出的不透明值；沒有說明檔或讀不到時，另含 `draft/` 底下
成員的名字與身分，重建的草稿因此不會拿到舊的值。其中任何一項的查詢失敗（而不是看到它不存在、或某一層
不是目錄）時，算出的值只供顯示：兩次查詢同樣失敗，不代表是同一份草稿，所以放棄時不刪，比照下面
「看不到它」回報 `draft/` 本身是殘留）：

- 取得名額；被占用 → `409 job_busy`。
- 比對不符 → `409 draft_changed`。擋的情境：分頁 A 打開確認框，分頁 B 接續了一輪、或放棄後重建了
  一份新草稿，A 再按確認就會刪掉沒看過的新成果。
- 先改名再刪除：改名成同一層的 `.afterthread.meta/draft.discarded-<hex>`，殘留跟著套件走；刪不掉就回報殘留
  路徑，由 sweep 重試。只有親眼看到 `draft/` 已不存在才回報已刪；看不到它（`lstat` 失敗而不是不存在）
  就回報 `draft/` 本身是殘留。
- 放棄不看狀態：進行中與發布中由名額擋（`409 job_busy`），能不能刪由上面的觀測決定。

### 3.9 發布草稿（不經 AI）

人接手的終點：操作者改完草稿（或只差設定，AI 已改好程式），按「發布草稿」。

- 一種新的 job（`kind=publish_draft`），占用名額；送出時比對 `(draft_id, generation)` 與
  `expected_vid == base_vid`，只接受可接續的草稿。
- job 內：寫 `publishing` → 複製 `files_dir` 到新的暫存工作區（§3.2 的規則與掃描）→ 剝除 → 驗證 →
  `_publish_revised_version`（`origin.feedback` 寫明「操作者發布的草稿，未經 AI」與 `draft_id`）→
  刪除草稿 → 照常重產總結、跑 `examples.json`。
- 不呼叫 LLM、不花錢；卡片與修訂相同（含驗證結果）。

## 4. 提示

### 4.1 所有修訂（第一輪也算）

- **預算**：最多 N 個工具回合、M 分鐘、每個 `run_shell` 指令 S 秒、對話大小上限；數值從設定插入，
  取代 "a couple of minutes"。
- **省回合**：一次回覆可以同時呼叫多個工具，但只有前 16 個會執行。短的測試合併成一個指令跑，但要在
  S 秒內，超過就分批；逐例印出結果，任何一例失敗整批就算失敗。
- **做不完時**（包括被告知預算用完）：`ready=false`，`handoff` 寫給下一輪——找到什麼、改了哪裡、驗證
  了什麼、還剩什麼、下一步；**不抄原始參數、輸出或個人內容**。做完時 `handoff` 留空。被告知預算用完時，
  除非最後一次測試已經證明修好，否則不要回 `ready=true`。
- **需要操作者動手時**，不論做完與否都寫 `operator_action`，設定類給可以直接貼上的 `KEY=value` 行。
  例如程式已在 `run_shell` 裡用新值驗證過、可以發布，但套件的 `config.env` 仍要操作者貼上那一行
  （D50）。
- **附上的失敗紀錄**：遮蔽標記不是真的值；參數不完整時照實說無法原樣重現，不要猜。

### 4.2 接續的那一輪

系統提示加：「這是第 N 次嘗試。工作區是上一輪留下的成果，不是安裝中版本的乾淨複本，也可能含操作者
之後手動做的修改。先確認現況，不要重做已完成的事，也不要無故撤回之前的修改。」

使用者提示的段落順序固定，每段有上限：

1. 原本的意見，上限 20,000 字；沒有就是 `_NO_FEEDBACK`。
2. 操作者這一輪的說明，上限 20,000 字；有才出現。
3. 上一輪：
   - 怎麼結束：後端量到的停止原因與錯誤，2,000 字；
   - summary 2,000、handoff 4,000、operator_action 1,000；
   - 那一輪操作者的說明，20,000 字。

   更早的每輪一行，最多 4 行，每行 300 字。
4. 沒帶進來的檔案與原因，最多 50 筆，每筆 300 字，附「另有 N 筆」。工作區裡的 `config.env` 標明「執行時不會載入」。
5. 相對於 `versions/<base_vid>` 的變更檔名清單：
   - 檔名先遮蔽，最多 50 筆，每筆 300 字；
   - 排除根目錄的 `.afterthread.meta/`；
   - 任一邊雜湊不出來時寫「無法列出」，不寫「沒有變更」。
6. 工作區目前的 `tool.json`，從整理好的暫存工作區讀：草稿可能已經改過它。
7. `config.env` 全文、`.env` 的 key 名、衝突的 key：照舊，每輪從套件層重讀。
8. 附上的失敗紀錄：
   - 送出時重讀：不變量 L 對每一輪各自成立。內文沿用各自的存檔上限，重新遮蔽後再截。
   - 已清除的只列摘要，並註明無法重跑。
   - `run.vid == base_vid` 時說「執行的是這份草稿的基底版本，工作區可能已經改過，請先確認現況」；不同時，保留
     原本的 vid 與警告。
   - 接著是除錯程序；沒有內文的紀錄，不要求重跑。

**總上限**：
- 使用者提示不超過 `char_allowance(llm_prompt_budget_tokens)`；系統提示加使用者提示，不超過
  `char_allowance(llm_tool_conversation_budget_tokens)` 的一半。標題、固定指示與省略標記都算在內。
- 超過時加省略標記，縮減的順序是：
  1. 更早的輪次與兩份清單；
  2. 附上紀錄的內文；
  3. `config.env`；
  4. `tool.json`；
  5. 原本的意見；
  6. 上一輪的筆記；
  7. 最後才是這一輪的說明與固定指示。
- 第一輪用同一個函式。單欄上限與總上限都可能讓第一輪的提示和以前不同。

說明檔的 `NOTE_CAP` 與請求的上限一致，都是 20,000 字。

## 5. 停止原因由後端量

- `generate_structured` 加選填參數 `stats`，由 `_run_structured` 填入：工具回合數、回應次數、收尾的
  觸發（回合／對話大小／無）、最後怎麼失敗（沒有失敗、空回覆、格式錯、上游錯誤、單一請求逾時、整場
  期限到期）。兩種事實都留：例如「回合用完觸發收尾，收尾那次回了空內容」。
- **不傳 `stats` 時完全不變**：同一組模擬回應，請求、handler 呼叫、結果與例外都相同。
- job 多 `stopped_by`、`failure`、`rounds_used`、`max_rounds`；卡片寫出上限與對應的設定名稱，而且只在
  真的是整場期限到期時才說 `TOOL_INSTALL_TIMEOUT_SECONDS`。
- 修訂改用 `ReviseResult`：`InstallResult` 加 `handoff`（上限 4,000 字）與 `operator_action`（上限
  1,000 字），安裝不變。兩者先遮蔽再截斷，**只用來顯示與交接，任何邏輯都不讀**。

## 6. 與其他操作的互動

- **刪除工具**：草稿跟著套件走。保存期間持共享 tools lock，刪除回 `409 ai_job_in_progress`；保存之外
  的時間刪除，進行中的接續在自己的暫存工作區跑完，保存時發現套件不是原來那一個就不保存。
- **丟棄版本**：不動草稿；草稿因 `current` 移動而變成已過期。
- **purge**：不碰草稿（草稿不是紀錄）。
- **跑一次範例**：不影響草稿。草稿沒有改檔、只要求動手時，卡片提示「改完設定後可以先按『跑一次範例』，
  通過就可以放棄草稿」。草稿有改檔時，對應的是「發布草稿」。
- **同名重裝**：新的套件目錄沒有草稿。
- **後端重啟**：草稿在磁碟上；被中斷的那一輪丟失。
- **隱私**：草稿是另一個保存範圍。工作區檔案與筆記可能含個人內容（例如模型寫進 `examples.json` 的
  查詢）；草稿不持久複製附上紀錄的內文、不讀回已清除的紀錄；放棄會刪掉整份草稿。README 寫明。

## 7. API

- `ToolSummary.draft`：
  - 形狀：`{draft_id, generation, attempts, state, base_vid, path, draft_dir, kept, discard_token, last:
    {stopped_by, failure, outcome, finished_at, operator_action, summary 摘要, omitted 數}}`，或 null。
  - `draft_dir` 是整個草稿目錄。`kept` 是保留下來的舊檔案目錄的路徑，列的是說明檔裡沒有親眼看到不在的那些。
  - `last.outcome` 為 `interrupted` 時，`finished_at` 是 null。
  - 列表只對有草稿的套件讀說明檔。
- `POST /api/tools/{name}/revise`：
  - 多 `draft_id`、`draft_generation`：有帶就是接續。兩者要嘛都有、要嘛都沒有，否則 422。
  - `feedback` 是這一輪的說明，可省略；`run_ids` 可附新的紀錄。
  - `_something_to_do` 放寬：帶了這一對，就不需要意見或紀錄。
  - 拒絕碼見 §3.4。
- `POST /api/tools/{name}/draft/publish`：`{draft_id, draft_generation, expected_vid}` → 202＋job id。
- `DELETE /api/tools/{name}/draft`：`draft_id`＋`generation`，或 `discard_token`。
- job 狀態：多 `stopped_by`、`failure`、`rounds_used`、`max_rounds`、`operator_action`、`handoff`、
  `draft: {saved, draft_id, generation, attempts, reason, retained_path}`。
  - `attempts` 是這份草稿累計的輪數，剛保存成功的那一輪，卡片的「第 N 輪」用它。
  - `saved` 為 True 時：`reason` 是附註（例如保留了上一份目錄），`retained_path` 是說明檔沒確認落盤時，成果
    另外留著的地方。
  - `saved` 為 False 而有 `retained_path`：成果留在那裡，沒存成草稿。
  - job 成功時，`reason` 說草稿為什麼留著。
- 新路由都宣告在 `/jobs/{job_id}` 之前（名為 `jobs`／`draft` 的工具）。

## 8. 前端

- **卡片**：
  - 內容：停止原因、「需要你動手」、收合的交接筆記。已發布的修訂也顯示後兩者；停止原因只在預算結束了工具階段時才顯示。
  - **這一輪自己的結果一律顯示**：「進度已保存（第 N 輪）」（另帶附註與另外留著的路徑），或「未能保存（原因）」，
    以及成果留在哪裡。它可能是成果唯一的取回位置。
  - **對目前草稿的宣稱與按鈕**，只在下列條件都成立時出現：
    - 清單的草稿與 job 的 `draft_id`、generation 都相同；
    - 清單資料來自觀察到 job 結束之後才發起、並且成功完成的那次讀取。

    generation 不同時，說「目前的草稿已不是這張卡片對應的那一份」。沒有對應工具列的卡片一律不給按鈕。
  - **按鈕**：草稿可接續、而且沒有其他工作在跑時，給「接續修正」「加上說明後接續…」。「發布草稿」在 P5 加上。
    「放棄」只在工具列。
- **工具列的草稿提示**：
  - 列出：輪數、上一輪停止原因、「需要你動手」、summary 摘要、上一輪沒存的檔案數；草稿路徑（可複製）、整個草稿
    目錄，以及保留下來的舊目錄（`kept`，可複製）。另外說明草稿目錄裡可能還有沒列出的目錄。
  - 按鈕：同一組按鈕，再加「放棄」。放棄的確認框說明整個草稿目錄都會刪掉，需要的請先取回。
  - 已過期、無法使用、已發布、結果未知：只給說明與「放棄」。進行中不給按鈕。
- 有草稿時，這一列與「最近執行」的「請 AI 修正」換成「接續修正（附上這筆）」。
- 每個 `draft_*` 拒絕碼在純函式裡定義反應與文案（`versionWriteConflictReaction`、
  `reviseRefusalNotification`、`ToolFailureNotice` 的判斷），寫 vitest；其他頁面收到
  `draft_pending` 時說明並連到工具頁。
