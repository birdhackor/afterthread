# web-v5 計畫：工具子系統改為「不可變版本 + 指標切換」

本文件描述**打算**做的事。實作過程中若與現實牴觸，以 `docs/web-v5-decisions.md`
的裁決為準（沿用 web-v4 的體例：計畫寫意圖，decisions 寫「為什麼最後不是這樣」）。

## 為什麼

web-v4 的 overall review 跑了九輪，每輪都找到新的競態，沒有收斂趨勢
（5 → 4 → 2 → 3 → 4 → 7 → 3 → 3 → 4）。逐輪修下來的結論是：**修的是實例，不是類別**。

真正的類別是一句話：

> **可變的路徑就是身分。** 名稱 → 路徑 → *此刻*擺在那裡的東西。

於是每一個跨時間的操作都被迫自己問一次「它還是原來那個嗎」，而每多一個跨時間的操作
就多一個競態。證據不是推論：

- R7-1 修好 `enabled_llm_tools` 的「掃描→建 handler」配對，R9-2 就在 `list_tools`
  找到**結構完全相同**的另一份（同樣先 `_scan_all()` 全部實體化，再依路徑二次讀取）。
- R6 的三條 finding 是**同一個形狀**出現在三個不同地方（守衛與被守衛的動作之間夾著
  真正的工作）。
- R5、R7-2、R8-1、裁決 #8 全部源自**同一個根因**：`enabled` 存在 `tool.json` 裡，
  所以切換啟用會就地改寫 manifest、移動它的身分。

## 目標與非目標

**目標**：讓上述整類問題**不成立**，而不是繼續逐個修好。

**非目標**：
- 不追求對抗操作者。D21 的信任邊界不變——操作者手改工具檔案仍然是**支援的行為**
  （README 有寫，本次 session 使用者的第三個問題就是在確認這件事）。所以
  「不可變」是**我們自己的操作**之間的約定，不是對操作者強制的性質。
- 不改 LLM 呼叫、日誌、記憶項目等其他子系統。
- 不改 `/api/tools` 的既有語意（名稱定址、404/409 行為維持）。

## 設計

### 現行版面

```
<tools_dir>/
  <name>/              # 真實目錄（symlink 一律拒絕）
    tool.json          # name/description/parameters/entry + enabled   ← 混了可變狀態
    run.py …           # 實作
    .env               # 秘密（修訂時以 _preserve_env_file 特別保留）
    .ai_meta.json      # 總結側檔
  .staging/<uuid>/     # 建置中
  .bak-<…>/            # 修訂備份（救援副本）
  .stale-<…>/          # 延後清理
```

### 目標版面

```
<tools_dir>/
  <name>/
    versions/<vid>/    # 發布後我們自己絕不再改
      tool.json        # 只有規格，沒有 enabled
      run.py …
      origin.json      # 建置來源（openapi_url + instructions），發布時就寫好
      summary.json     # 該版本的 AI 總結（產生後寫入該版本）
    current            # 純文字檔，內容是目前生效的 <vid>
    .state.json        # 可變狀態：enabled（未來可含 finalized）
    .env               # 秘密，跨版本存活（不再需要特別保留邏輯）
  .staging/<uuid>/
```

### 關鍵決定（草案，實作時各自進 decisions）

- **指標用「檔案」不用 symlink**。`current` 是一個小文字檔，內容是通過 regex 驗證的
  版本 id；切換用 mkstemp + `os.replace`（與現行側檔寫入同一個原子寫法）。
  用 symlink 會迫使我們鬆動既有的「拒絕 symlink 套件目錄／manifest」硬化，
  那是這個子系統最不該動的部分。
- **`enabled` 搬到 `.state.json`**，dot-prefix 與 `.ai_meta.json` 同慣例（掃描與
  模型可見檔案清單都不會撿到）。切換啟用從此**不再碰 manifest**，`tool.json` 的身分
  也就不再因為一次開關而移動。
- **手改仍然被接住**。解析出版本目錄之後，manifest 身分檢查**保留**——它現在只回答
  「有人手動改過嗎」這一個問題，而不是同時被開關污染。對話中途 schema 變了仍然拒絕，
  行為不變。
- **`.env` 放在套件層**，跨版本自然存活，修訂流程裡的保留／可遮蔽性重驗邏輯可以簡化。
- **origin 在發布版本時就寫進版本目錄**。web-v4 R8 的「origin 永久遺失」在此不成立：
  它不再依賴一趟 LLM 往返之後才落盤。
- **總結屬於版本**。「總結描述的是另一個實作」這類問題隨之消失；`finalized` 屬於套件
  （是使用者對這個工具的意圖），留在 `.state.json`。
- **舊版本靠引用計數回收**。現行的「執行中登記」變成版本引用計數，語意更直接；
  保留最近數版可順帶得到**回溯上一版**的能力（附帶收穫，不是本次目標）。

### 這個設計讓哪些既有問題不成立

| web-v4 找到的問題 | 新設計下 |
|---|---|
| R3／R6-1 執行中套件被換走或刪除（改道） | 不成立：子行程的 cwd 是不可變的版本目錄 |
| R5 執行登記身分被開關改寫 | 不成立：開關不碰 manifest |
| R7-1 掃描→建 handler 的身分配對 | 不成立：版本目錄內容不會變 |
| R9-2 `list_tools` 撕裂的列 | 不成立：同上 |
| R8-1 origin 永久遺失 | 不成立：origin 在發布時就落盤 |
| R7-2 開關與重新產生互鎖 | 不成立：開關不再讓總結寫入失效 |
| 裁決 #8 失敗 session 連結遺失 | 不成立：同上 |

**不會**因此消失的（仍需各自處理）：
- R9-1 日誌編號跨行程重用（llm_log 的環狀緩衝區與 per-process 計數器問題，與版面無關）
- 操作者手改造成的中途 schema 變動（刻意保留現行「拒絕」行為）
- 裁決 #7 的實例身分問題（可望因 `current`/vid 而**有解**，但屬後續）

## 階段

| 階段 | 範圍 | 為什麼這樣切 |
|---|---|---|
| **P1** | `enabled` 移出 `tool.json` → `.state.json`（含既有安裝的遷移） | 最小、最集中的根因修正。`.state.json` 在新舊版面都放在同一個位置，不會白做 |
| **P2** | 版本版面端到端：`current` 指標、解析、掃描、執行、安裝／修訂發布新版本、遷移 | 讀寫兩側必須一起換，中間狀態沒有意義 |
| **P3** | origin 與總結移入版本目錄 | 依賴 P2 的版面 |
| **P4** | 舊版本回收（引用計數 + 保留策略），視成本決定是否附帶回溯 | 只有在版本存在之後才有意義 |
| **Overall** | 全距對抗式 review 迴圈至收斂 | 沿用 web-v4 的做法 |

每個階段完成後 commit、跑該階段的 codex review 迴圈至收斂，再進下一階段。

## 風險

- **這是子系統核心的重寫**，產品碼約 8.6k 行、測試約 12.8k 行。回歸風險是本計畫最大的
  成本，遷移路徑（既有安裝）是最容易出錯的一段。
- **測試會大量改動**。現行測試大量直接組出 `<tools_dir>/<name>/tool.json` 這個版面；
  要有一個共用的建構輔助函式，否則每個階段都在改同一批 fixture。
- **e2e 不涵蓋工具**（smoke 的 `tools_dir` 未設定），所以整合面的保護只有單元測試，
  這點在 P2 要特別留意。
