# web-v6 設計：設定與秘密分家、一鍵請 AI 修正工具

本文件是 web-v6 的**設計本體**，尚未經過 design review。

**起因是一次實際使用**：一個 0.4.0 之前建的工具執行時出錯，操作者到工具頁送出修訂，修訂在
呼叫 LLM 之前就被拒——「既有工具包的 .env 內有值過短、無法遮蔽」——而那份 `.env` 裡唯一過短的
是 TTL 這類設定數字。追下去是兩個彼此獨立的設計缺口；第 1 節列出完整的問題清單。

這個 app 沒有對話介面，AI 功能都是逐項操作。所以「叫 AI 除錯」不能靠在修訂意見裡問「你看得到
log 嗎」：它必須是一個按鈕，按下去 AI 就拿到失敗的現場（第 8 節）。

操作者已經裁決的部分集中在第 3 節。

```
GET •••[秘密已遮蔽]•••/search failed (region •••[秘密已遮蔽]•••, ttl 3600); user asked about •••[秘密已遮蔽]••• trip
```

## 4. 設定與秘密分家：`config.env`

| 檔案 | 放什麼 | 誰寫 | 遮蔽 | 長度 | 修訂時 AI 看到什麼 |
|---|---|---|---|---|---|
| `<name>/.env` | **只放秘密** | 安裝表單注入、操作者手改 | 全部（不變） | 至少 6 字元（不變） | key 名；值只進 `run_shell` 的環境 |
| `<name>/config.env`（新） | TTL、endpoint、mode 等設定覆寫 | 操作者手改 | **不遮** | 不限 | 全文 |
| `versions/<vid>/` 的程式碼 | 設定預設值 | builder | — | — | 本來就在工作區 |

**載入順序**（工具執行與修訂的 `run_shell` 相同）：透傳變數 → `TLS_NO_VERIFY` → `config.env` →
`.env`。同一個 key 兩邊都有時 `.env` 優先，秘密永遠不會被公開值蓋掉；工具頁與修訂提示都標示這個
衝突。

**讀取規則**：完全沿用 `.env` 的讀取器——`_read_regular_file_capped`（O_NOFOLLOW、只收一般檔、
64 KiB 上限）加 `_parse_dotenv_text`（`interpolate=False`；否則 `X=${OPENAI_API_KEY}` 會解析成
後端金鑰）。執行時讀不到就當作空的，與 `.env` 的 degrade 規則相同；修訂時讀不到就拒絕，理由也與
`.env` 相同：builder 測試的環境必須等於執行時的環境。

**不動的東西**：`known_secret_values`、兩道 `.env` 閘（長度下限與逐行拼法）、內嵌秘密掃描、遮蔽值
快取都只讀 `.env`，本設計不改它們的程式碼。這是選這個方案的主因：遮蔽是全專案審最多輪的部分。

**修訂提示多兩段**。兩者都是操作者／檔案系統來源的插值，照 R2-4 的規則先過 `redact_known_secrets`：

- `Operator configuration overrides (config.env)`：全文，並說明這些值蓋過程式內的預設值；若意見要
  改其中一項，改程式預設**不會生效**，要在 summary 裡講明由操作者改 `config.env`。v5 第 3 節記下的
  「修訂回報成功、行為完全沒變」因此至少**看得見**。
- `Credentials available as environment variables in run_shell (values hidden)`：`.env` 的 key 名。

**builder 提示**：維持「設定預設值寫在程式碼、不寫 `.env`」，補一句操作者可以用套件層的
`config.env` 覆寫、那個檔案在工作區之外、不要建立它。版本內容裡就算出現同名檔案，後端也不會載入
它（執行時只讀套件層那份），所以不需要像 `.env` 那樣在發布前剝除。

**已知的限制**：放進 `config.env` 的值**不會被遮蔽**，把秘密放錯檔案就會出現在日誌與提示裡。工具頁
對 key 名含 `KEY`、`TOKEN`、`SECRET`、`PASSWORD` 的 `config.env` 項目顯示提醒；不做更多偵測，因為
從值猜不出是不是秘密（問題 A1 的 `PIN=1234`）。

**沒選的方案**：

- 用規則猜哪些值是設定：猜不出來。
- 在 `.env` 內標記哪些 key 是公開的：要改遮蔽核心，而且 `cat .env` 時兩種值仍混在一起。
- 設定一律寫進程式碼、不提供覆寫：不需要新機制，但每調一次 TTL 都是一次付費修訂。

## 5. `.env` 閘的錯誤訊息

`_unmaskable_env_error`（`tool_builder.py:2312`）改成回報**是哪些 key**。訊息仍然只講條件、key 名
與補救，絕不含值：

- 過短：「既有工具包 .env 的 `CACHE_TTL`、`TIMEOUT` 值短於 6 字元、無法遮蔽，修訂已取消：如果是
  秘密請加長；如果只是設定，請移到同目錄的 config.env。」
- 拼法：「既有工具包 .env 的 `TOKEN` 那一行寫法無法對應到實際值……」。被後面同名行蓋掉的舊行，也用
  `_env_line_key` 取得它的 key。

key 名最多列 5 個（其餘寫「等 N 個」），每個截到 64 字元，並先過 `redact_known_secrets`。

## 6. 工具執行紀錄 `tool_run`

### 6.1 欄位

新的 SQLModel 表，放在 `models.py`。`init_db` 的 `create_all`（`db.py:259`）會建立缺少的表，不需要
migration。

| 欄位 | 說明 |
|---|---|
| `id` | 自增主鍵 |
| `tool_name` | 套件名（索引） |
| `vid` | **實際執行的版本**，也就是廣告時綁定的那一版 |
| `started_at`、`duration_ms` | |
| `outcome` | `ok`／`failed`（非零 exit）／`timeout`／`start_failed`／`refused`（停用、版本已換、身分不符，工具沒有執行） |
| `exit_code` | `failed` 才有 |
| `workflow` | 呼叫來源：`capture`、`enrich`、`assist_update`……；後端自己執行的是 `health_check`（跑一次範例）與 `verify`（修正後自動驗證），見第 10 節 |
| `llm_log_id`、`llm_log_process` | 連回 AI 日誌那一筆；用既有的 process token 判斷後端是否重啟過 |
| `args`、`stderr`、`stdout` | **只有非 `ok` 才存**，已遮蔽、有上限（第 6.2 節） |

只記錄**已安裝工具**的執行（`_make_handler` 這條路）。builder 的 meta-tool（`run_shell` 等）不記，
它們留在建置那一場的 AI 日誌裡。

### 6.2 寫什麼

- **成功只記中繼資料**，不存參數與輸出。D09 的理由（內容含個人資料）對成功執行一樣成立，而成功
  執行對除錯的價值低。
- **失敗存內文**：參數（至多 8,000 字）、stderr 的**尾端**（至多 16,000 字，traceback 的關鍵在
  最後）、stdout 開頭（至多 4,000 字）。
- **先遮後切**，沿用全專案 redact→cap 的順序。stderr／stdout 直接取 `_run_tool_subprocess` 已經為
  模型遮好的那份文字再切；參數在 `_inflight_secrets` 範圍內用 `redact_known_secrets` 遮，與輸出
  用同一刻的已知秘密集合。整段先遮過，之後從頭切或從尾切都只會切到遮蔽標記，切不出秘密片段。
- **讀出時再遮一次**：寫入之後才加進 `.env` 的秘密，在顯示與附進提示時也會被遮（與 v5 不變量 F
  同一個精神）。

### 6.3 寫入方式

- `_run_tool_subprocess`（`tools.py:2829`）改成回傳結構化結果：outcome、exit code、已遮蔽的
  stdout／stderr，以及給模型的字串。`_make_handler`（`tools.py:3023`）照舊把給模型的字串交回，其餘
  交給紀錄器。**交給模型的字串不得因此改變。**
- 紀錄器用注入的方式接（`tools.set_run_recorder(...)`，在 `main.py` 接線），與
  `llm_log.set_secret_provider` 同一個模式：`tools.py` 不直接依賴資料庫，測試可以換掉它。紀錄器
  回傳寫入的 id，供第 8.2 節的請求收集器使用。
- **觀測者不變量**：寫入失敗只記一行不含內文的 WARNING，工具結果照常回給模型，與 `llm_log` 的
  no-observer-failure 不變量相同。
- 寫入在獨立的短 session 裡完成。AI 路由在 LLM 呼叫期間不持有 DB transaction
  （`routers/ai.py:413` 的既有規則），所以不會與請求自己的 session 互鎖。
- 連回 AI 日誌：`generate_structured`（`llm.py:1301`）建立 recorder 時 id 就已經分配好
  （`llm.py:1356`），把 id、process token 與 workflow 放進 ContextVar，handler 讀它即可。

### 6.4 生命週期

- **刪除工具 ⇒ 一併刪除它的紀錄**。刪除結果是 `removed` 或 `retained` 都刪；回
  `409 ai_job_in_progress` 時什麼都不動。名稱不是身分：不刪的話，同名重裝的新工具會繼承舊工具的
  失敗紀錄。
- **丟掉一個版本 ⇒ 紀錄保留**，畫面標示「版本已丟棄」。那是歷史，仍可附進修訂，提示會說明那一版
  已不存在。
- 操作者手動刪掉工具目錄（D21）留下的紀錄是**孤兒**，由 purge 的孤兒範圍清除（第 7 節）。

## 7. 手動 purge

**不自動刪除。** 每筆紀錄的大小有上限，成功只記中繼資料，所以成長很慢；工具頁顯示總筆數與約略
大小，由操作者決定何時清。

**範圍**（可以組合）：

| 條件 | 選項 |
|---|---|
| 工具 | 某一個工具／全部 |
| 結果 | 全部／只清成功／只清失敗 |
| 時間 | 全部／N 天前的 |
| 孤兒 | 只清已不存在的工具留下的紀錄 |
| 單筆 | 指定一筆（例如內容不想留） |

**先預覽再刪**：每次 purge 先以 `dry_run` 算出筆數，確認對話框顯示「將刪除 N 筆」，確認後才真的刪。
這與遷移腳本的 `--dry-run` 是同一個習慣。

**三個入口，共用同一個服務函式**：

- **工具頁**：每個工具的「最近執行」有「清除紀錄」選單（全部／只清成功／30 天前）；頁首顯示
  「執行紀錄 N 筆、約 X KB」與「清除…」；單筆在詳情裡刪。
- **API**：全域操作放在獨立前綴 `/api/tool-runs`。`routers/tools.py:676` 的註解記載過，
  `/api/tools/` 底下任何字面的第一段都可能是合法套件名，獨立前綴讓這個問題不存在。
  - `GET /api/tool-runs/stats`：每個工具的筆數、失敗數、約略大小，以及孤兒數
  - `POST /api/tool-runs/purge`：`{tool?, outcome?, older_than_days?, orphans_only?, dry_run}` →
    `{matched, deleted}`
  - `GET /api/tool-runs/{id}`、`DELETE /api/tool-runs/{id}`
  - 單一工具的列表：`GET /api/tools/{name}/runs`
- **CLI**：`afterthread purge-tool-runs [--tool NAME] [--outcome ok|failed|all] [--older-than DAYS]
  [--orphans] [--dry-run] [--yes] [--vacuum]`，與 `init-env` 同一個 Typer app。後端沒在跑時也能用。

**磁碟空間**：SQLite 的 DELETE 不會縮小檔案，空出的頁會被之後的寫入重用。要真的縮小，CLI 提供
`--vacuum`。它會重寫整個資料庫（包含記憶內容），所以只放在 CLI，不放在網頁上。

**與修訂的互動**：附上紀錄的修訂在**送出時**就把紀錄內容快照下來交給工作（第 8.3 節），之後 purge
那幾筆不影響已排隊或進行中的修訂。

## 8. 一鍵請 AI 修正

### 8.1 按一下做什麼

直接送出 `POST /api/tools/{name}/revise`，帶 `run_ids`（失敗紀錄）與 `expected_vid`（目前版本），
**不帶意見、不開表單**。旁邊另有「加上說明…」，打開既有的修訂表單並附上同樣的紀錄，給想補充背景的
時候用。

`run_ids` 最多 3 筆。有附紀錄時 `feedback` 是選填；沒寫時提示寫明「操作者只要求修正附上的失敗」。
附哪幾筆由操作者決定，builder 不自己去翻紀錄：提示內容可預期，也不會帶進無關的資料。

### 8.2 入口

| 入口 | 附上哪幾筆 |
|---|---|
| 工具列表：最近一次執行失敗的工具，列上顯示「最近一次執行失敗」與按鈕 | 最近那一筆失敗 |
| 工具詳情的「最近執行」：每筆失敗各一顆；也可以勾選最多 3 筆一起送 | 點的那筆／勾選的 |
| 擷取、補齊、協助更新的 AI 結果：這次請求裡有工具失敗時，結果旁顯示提醒與按鈕 | 這次請求裡失敗的那幾筆（最多 3 筆） |
| 「跑一次範例」與修正後自動驗證的結果（第 10 節） | 失敗的那幾筆 |

第三個入口讓失敗在**發生的地方**就看得到。做法：AI 路由在請求開始時放一個 ContextVar 收集器，位置
是既有的 `_advertised_tools_lock`（`routers/ai.py:187`），它本來就包住每個會廣告工具的請求。紀錄器
每寫一筆失敗就把 id 放進去，路由再把它們放進回應的 `tool_failures`（工具名、結果、紀錄 id）。LLM
本身失敗而回 502 時沒有回應可放，但紀錄照樣寫進資料庫，工具列表上看得到。

### 8.3 按下之後

修訂工作沿用既有的 job 輪詢與全域名額：

1. 路由在取得全域名額**之前**讀出並驗證紀錄：不存在或不屬於這個工具就回 404／422，不建立工作、
   不花錢（與 `expected_vid` 不符時同一個原則）。讀出的是快照，連同已遮蔽的內文交給 `run_revise`，
   之後 purge 那幾筆不影響這次工作。
2. `.env` 入口閘照舊。擋下時的訊息列出 key（第 5 節），直接顯示在按鈕旁。
3. builder session 帶著失敗紀錄與固定的除錯程序（第 8.4 節）。
4. 三種結局，工作卡片各有呈現：

| 結局 | 條件 | 卡片 |
|---|---|---|
| **已修正** | `ready=true` | 發布新版本，接著**後端自動驗證**：用新版本重跑附上的失敗輸入與所有範例（第 10 節的執行入口），結果記進執行紀錄（`workflow=verify`）並顯示在卡片上。驗證有失敗就轉紅，旁邊放一鍵「丟掉這一版」。不自動丟棄：那是付費建置的結果，由操作者決定 |
| **AI 診斷** | `ready=false` | 不發新版。卡片用**橘色**而不是紅色，主文是 AI 的診斷，例如「API 回 401，API_KEY 可能已過期，請更新 .env」 |
| **失敗** | LLM 錯誤、逾時、入口閘 | 照舊紅色 |

job 狀態要能分出「AI 診斷」與「失敗」：目前 `ready=false` 會變成一般錯誤字串「AI 判定修訂尚未
完成：…」（`tool_builder.py:2627`），要多一個結局欄位給前端分辨。

撤銷一次修正就用既有的「丟掉這一版」。**不可變版本是一鍵可以直接發布的前提**：修錯了退回去就好。

### 8.4 除錯程序（修訂提示）

提示加一段 `Failing runs attached by the operator`。每筆列出時間、workflow、**執行的版本是否就是
工作區這一版**、結果、exit code、stdin 參數、stderr 尾端，並附固定程序：

1. 先用完全相同的參數重現（`echo '<args>' | <entry>`），確認看到同樣的錯誤。重現不了就照實說並
   找原因（API 變了、憑證、資料相依），不要猜著改。
2. 修正根因。
3. 用每一組附上的參數、以及 `examples.json` 的每個範例重跑，全部成功才回 `ready=true`。
4. 問題不在程式碼（例如憑證過期、API 停機）時回 `ready=false`，說明原因與操作者該做什麼。
5. 把修好的輸入改寫成不含個人內容的等價輸入，加進 `examples.json`（第 10 節）。
6. summary 寫出根因、改了什麼、怎麼驗證、新增了哪些範例。

### 8.5 防呆

- **不加確認框**：一鍵就是一鍵。費用的上限來自既有的全域名額——同一時間只能有一個 AI 工具工作；
  工作進行中所有修正按鈕停用（與既有「送出修訂」相同的停用條件）；`job_busy` 時顯示「目前有其他
  AI 工作進行中」。
- **舊版本的失敗**：失敗發生的版本不是目前版本時，按鈕旁標示「失敗發生在舊版本」，提示也要求先
  確認還能不能重現。
- **避免重複付費**：目前版本的 `origin.json` 若已記著這筆的 id（第 8.6 節），紀錄旁標示「目前版本
  就是為了修這筆而產生」。仍然可以再按。
- **從其他頁面按下**：畫面顯示「已開始修正」與連到工具頁的連結 `/tools?job=<id>`（與既有的
  `/llm-logs?log=<id>` 同一個模式），工具頁依網址接上那個工作的進度卡片。
- **停用中的工具**：可以修正（修訂不執行已安裝的工具），但不做自動驗證，因為執行路徑對停用的工具
  fail closed。卡片寫明「工具已停用，未自動驗證」。
- **有副作用的工具**：builder 重現時、以及自動驗證時，都會真的再用失敗的輸入執行一次。會寫入或刪除
  資料的工具，按下之前要知道這一點；查詢類工具沒有影響。

### 8.6 provenance

新版本的 `origin.json` 多記 `attached_run_ids`（整數清單），讓版本記得自己是為了哪幾次失敗而修。
`_origin_document`（`tools.py:930`）只檢查已知欄位的型別、不拒絕多出的欄位，而 `_utf8_safe_meta`
對清單原樣放行，所以讀取端不用改。

### 8.7 一鍵做不到的

exit 0 但結果不對：沒有失敗紀錄可附。這種情況照舊用修訂表單寫意見。

## 9. 前端

- **工具列表**：最近一次執行失敗的工具，列上顯示「最近一次執行失敗」與「請 AI 修正」。
  `ToolSummary` 多一個 `last_run: {id, outcome, started_at, vid} | null`。
- **工具詳情**：
  - 「設定」：`config.env` 的內容（key=value）、`.env` 的 key 名（不顯示值）、兩邊衝突的 key，以及
    `config.env` 裡看起來像秘密的 key 的提醒。`.env` 的 key 旁邊說明「`.env` 的每個值都會被當成
    秘密遮蔽，不是秘密的請移到 config.env」。先做唯讀，編輯照舊手改檔案。
  - 「最近執行」：時間、版本、來源、結果、耗時。失敗的那一筆可以展開看參數與 stderr，並有「請 AI
    修正」與「加上說明…」；可勾選最多 3 筆一起送。
  - 「跑一次範例」與它的結果（第 10 節）。
  - 「清除紀錄」選單（第 7 節）。
- **工作卡片**：三種結局（第 8.3 節）；已修正時列出自動驗證的結果，驗證失敗時旁邊是一鍵「丟掉這一版」。
- **擷取、補齊、協助更新**：回應帶 `tool_failures` 時，在 AI 結果旁顯示提醒與「請 AI 修正」。
- **頁首**：執行紀錄總筆數與大小、「清除…」。
- **網址**：`/tools?job=<id>` 接上進度卡片。

## 10. 版本內的回歸輸入 `examples.json`

**是什麼**：每個版本目錄裡一份小檔案，列出「這個工具一定要能處理的輸入」，等於這個工具的測試清單：

```json
{
  "examples": [
    {"name": "一般查詢", "args": {"query": "SQLite WAL"}},
    {"name": "查無結果時回空清單（修正 2026-10-26 的 KeyError）", "args": {"query": "zzzz-no-hit"}}
  ]
}
```

通過條件只有「exit 0、沒有逾時」。它打的是真的 API，結果會變，所以不比對輸出內容。

**為什麼放在版本裡**：它是版本內容，跟著程式碼走。修訂會把目前版本複製到工作區，所以範例自動帶到
下一版；丟掉一個版本，就回到上一版當時的範例。

**怎麼用**：

1. **builder 維護**：安裝時把它測過的輸入寫進去；修好一次失敗後，把那組輸入的等價版本加進去
   （第 8.4 節）。
2. **修訂時全部重跑**：修訂提示要求 `ready=true` 之前把每個範例都跑過一遍。這擋的是「修好 B、弄壞
   A」——目前 builder 只驗它當下試的那組輸入。
3. **後端執行入口**：工具頁的「跑一次範例」（手動健康檢查）與修正後的自動驗證（第 8.3 節）共用。
   做法是重用 AI 請求執行工具的同一條路：取得共享鎖（`acquire_shared_tools_lock`）、
   `bind_request_tools_lock`，再從 `enabled_llm_tools()` 取出那個工具的 handler 直接呼叫。身分檢查、
   遮蔽、執行紀錄因此全部照舊，紀錄的 workflow 是 `health_check` 或 `verify`。停用中的工具不在
   `enabled_llm_tools()` 裡，所以不跑。失敗的範例可以一鍵請 AI 修正（第 8.2 節）。

**限制**：

- 只能放**唯讀**的輸入（查詢類）。會寫入或刪除資料的 API，範例每跑一次就真的動一次。
- **個資**：失敗紀錄的參數可能含個人內容，而版本內容永久保留、purge 清不到。提示要求 builder 改寫
  成能觸發同一條程式路徑、但不含個人內容的等價輸入（例如換一個同樣查無結果的關鍵字），並在 summary
  列出新增的範例。
- 範例數量設上限（例如 10 個），每個沿用一般工具呼叫的 timeout。
- 後端讀 `examples.json` 時要驗形狀；格式錯誤就回報，不執行。

## 11. 不變量與必須有的測試

| # | 不變量 | 必須有的測試 |
|---|---|---|
| A | `config.env` 的值不進遮蔽集合 | 套件的 `config.env` 有 `REGION=taipei` → `redact_known_secrets("taipei")` 不變；同一個值也出現在 `.env` 時則被遮 |
| B | `.env` 的政策不變 | 現有 `.env` 閘與遮蔽測試全部原樣通過 |
| C | 閘的錯誤訊息列 key 名、絕不含值 | 短值與錯誤拼法各一例：訊息含 key、不含值；超過 5 個 key 時只列 5 個 |
| D | 載入順序：`config.env` 蓋過透傳與 `TLS_NO_VERIFY`，`.env` 蓋過 `config.env` | 同一 key 在三處各有值，子行程拿到 `.env` 的值；修訂的 `run_shell` 環境相同 |
| E | `config.env` 不做插值 | `X=${OPENAI_API_KEY}` 在子行程裡是字面字串 |
| F | 記錄不改變交給模型的字串；寫入失敗不影響工具呼叫 | 每種 outcome 的回傳字串與改動前逐字相同；紀錄器丟例外時工具結果照常 |
| G | 存下的內文不含任何已知秘密 | 工具把 `.env` 的秘密印到 stderr、模型也把它放進參數 → 存下的欄位只有遮蔽標記 |
| H | 成功執行不存內文 | `ok` 紀錄的 `args`／`stderr`／`stdout` 皆為 null |
| I | 讀出時再遮一次 | 紀錄寫入後才把其中一段文字加進 `.env` → GET 回應與修訂提示裡都已遮蔽 |
| J | purge 刪掉的正好是預覽算出的那些；`dry_run` 不刪任何東西 | 每種範圍組合：`dry_run` 的 `matched` 等於之後實際的 `deleted`，範圍外的紀錄不動 |
| K | 刪除工具會刪掉它的紀錄；回 `409` 時不動 | 刪除後同名重裝 → 紀錄為 0；`ai_job_in_progress` 時紀錄仍在 |
| L | 附上紀錄的修訂在送出時就快照 | 送出後立刻 purge 那幾筆 → 修訂提示仍含它們 |
| M | 不存在或不屬於這個工具的 `run_ids` 在建立工作前就被拒 | 回 404／422，沒有 job id、沒有 LLM 呼叫 |
| N | 一鍵送出不需要意見 | 只帶 `run_ids` 與 `expected_vid` 的請求被接受；兩者都沒有（沒有意見也沒有紀錄）時 422 |
| O | `ready=false` 的修訂不發布版本，結局是「診斷」 | 結局欄位為診斷、`current` 不變、`versions/` 沒有新目錄 |
| P | 自動驗證與健康檢查走 AI 請求的同一條執行路徑 | 執行期間有 `workflow=verify`／`health_check` 的紀錄；停用的工具不執行，卡片標示未驗證 |
| Q | AI 回應的 `tool_failures` 只含這次請求寫下的失敗 | 兩個並行請求各自只看到自己的失敗 |

## 12. 交付單位

| 階段 | 範圍 | 規模 |
|---|---|---|
| P1 | 第 4、5 節：`config.env` 與列出 key 的閘訊息。一起出貨，因為新訊息要你把設定搬到 `config.env` | 中 |
| P2 | 第 6、7 節：`tool_run` 紀錄、工具詳情「最近執行」、purge（網頁、API、CLI） | 中 |

| P4 | 第 8.2 節第三個入口：擷取、補齊、協助更新的回應帶 `tool_failures` | 小到中 |

## 13. 剩下的不確定

1. **「結果不對但 exit 0」抓不到**：成功執行不存內文，所以這類問題仍要在修訂意見裡描述。之後可以
   加一個「每個工具可選擇記錄成功執行的內容」的開關。
2. **模型送出無效的參數 JSON**：`llm.py` 在呼叫 handler 之前就擋下，不會留下執行紀錄。那是模型的
   問題，不是工具的。
3. **`config.env` 的網頁編輯**：先做唯讀。要在網頁上改，得先定義寫入時的原子性與權限模式（`init-env`
   已有一套可以參考）。
4. **停用中的工具能不能跑範例**：目前沿用執行路徑的 fail-closed，不跑。若要「先測再啟用」，得在
   執行路徑加一個操作者明示的例外，那是安全敏感的改動，有需要再議。
5. **一鍵沒有確認框**：費用的上限只靠全域名額。若實際使用發現容易誤按，再加輕量的防呆（例如按住
   確認），而不是確認框。
