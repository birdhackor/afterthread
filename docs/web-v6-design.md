# web-v6 設計：設定與秘密分家、一鍵請 AI 修正工具

本文件是 web-v6 的**設計本體**。已經過一輪 design review（Fable，22 條 finding），逐條處置見第 14 節；
實作計畫見 `docs/web-v6-plan.md`。

**起因是一次實際使用**：一個 0.4.0 之前建的工具執行時出錯，操作者到工具頁送出修訂，修訂在
呼叫 LLM 之前就被拒——「既有工具包的 .env 內有值過短、無法遮蔽」——而那份 `.env` 裡唯一過短的
是 TTL 這類設定數字。追下去是兩個彼此獨立的設計缺口；第 1 節列出完整的問題清單。

這個 app 沒有對話介面，AI 功能都是逐項操作。所以「叫 AI 除錯」不能靠在修訂意見裡問「你看得到
log 嗎」：它必須是一個按鈕，按下去 AI 就拿到失敗的現場（第 8 節）。

操作者已經裁決的部分集中在第 3 節。

### A. 設定與秘密

遮蔽結果是

```
GET •••[秘密已遮蔽]•••/search failed (region •••[秘密已遮蔽]•••, ttl 3600); user asked about •••[秘密已遮蔽]••• trip
```

**一句話：規則沒錯，錯在檔案沒有分類。**

## 2. 校準

沿用 v5 設計第 2 節：單人本機工具、沒有敵對行為者、手改是支援的工作流程（D21）。併發類問題要指
得出一個操作者真的做得出來的順序；修法與嚴重性成比例；正確性、失效復原、唯一副本不打折。裁決
紀錄 #15 的判準照用：單一操作內部的次秒級窗口不防，分鐘級的工作期間照防。

## 4. 設定與秘密分家：`config.env`

| 檔案 | 放什麼 | 誰寫 | 遮蔽 | 長度 | 修訂時 AI 看到什麼 |
|---|---|---|---|---|---|
| `<name>/.env` | **只放秘密** | 安裝表單注入、操作者手改 | 全部（不變） | 至少 6 字元（不變） | key 名；值只進 `run_shell` 的環境 |
| `<name>/config.env`（新） | TTL、endpoint、mode 等設定覆寫 | 操作者手改 | **不遮** | 不限 | 全文 |
| `versions/<vid>/` 的程式碼 | 設定預設值 | builder | — | — | 本來就在工作區 |

**載入順序**（工具執行與修訂的 `run_shell` 相同）：透傳變數 → `TLS_NO_VERIFY` → `config.env` →
`.env`。同一個 key 兩邊都有時 `.env` 優先，秘密永遠不會被公開值蓋掉；工具頁與修訂提示都標示這個
衝突。`config.env` 也能蓋過 `TLS_NO_VERIFY`，與 `.env` 本來就能蓋過它一樣。

**讀取規則**：完全沿用 `.env` 的讀取器——`_read_regular_file_capped`（O_NOFOLLOW、只收一般檔、
64 KiB 上限）加 `_parse_dotenv_text`（`interpolate=False`；否則 `X=${OPENAI_API_KEY}` 會解析成
後端金鑰）。執行時讀不到就當作空的，與 `.env` 的 degrade 規則相同；修訂時讀不到就拒絕，理由也與
`.env` 相同：builder 測試的環境必須等於執行時的環境。

**不動的東西**：`known_secret_values`、兩道 `.env` 閘（長度下限與逐行拼法）、內嵌秘密掃描、遮蔽值
快取都只讀 `.env`，本設計不改它們的程式碼。這是選這個方案的主因：遮蔽是全專案審最多輪的部分。

**修訂提示多兩段**。兩者都是操作者／檔案系統來源的插值，照 R2-4 的規則先過 `redact_known_secrets`：

- `Operator configuration overrides (config.env)`：全文，並說明這些值蓋過程式內的預設值；若意見要
  改其中一項，改程式預設**不會生效**，要在 summary 裡講明由操作者改 `config.env`。v5 第 3 節記下的
  「修訂回報成功、行為完全沒變」因此至少**看得見**。
- `Credentials available as environment variables in run_shell (values hidden)`：`.env` 的 key 名。

**builder 提示**：維持「設定預設值寫在程式碼、不寫 `.env`」，補一句操作者可以用套件層的
`config.env` 覆寫、那個檔案在工作區之外、不要建立它。版本內容裡就算出現同名檔案，後端也不會載入
它（執行時只讀套件層那份），所以不需要像 `.env` 那樣在發布前剝除。

**已知的限制**：放進 `config.env` 的值**不會被遮蔽**。具體是三種情況：

- **同一個秘密兩邊都有**：遮蔽集合有它（來自 `.env`），提示與 `cat config.env` 的輸出都會遮——
  除非 `config.env` 那一行用了可逆的寫法（例如跳脫的引號），那正是 `.env` 拼法閘擋下的形狀，而閘
  不看 `config.env`。
- **短於 6 字元的秘密放進 `config.env`**：本來就遮不掉。
- **builder 在 `run_shell` 執行 `env` 或 `cat config.env`**：會逐字看到所有設定值。定義上不是秘密，
  可以接受。

工具頁對 `config.env` 的兩種提醒都是零猜測：key 名含 `KEY`、`TOKEN`、`SECRET`、`PASSWORD`；以及
**值等於或包含某個 `.env` 的值**（精確比對）。不做更多偵測，因為從值猜不出是不是秘密（問題 A1 的
`PIN=1234`）。

**沒選的方案**：

- 用規則猜哪些值是設定：猜不出來。
- 在 `.env` 內標記哪些 key 是公開的：要改遮蔽核心，而且 `cat .env` 時兩種值仍混在一起。
- 設定一律寫進程式碼、不提供覆寫：不需要新機制，但每調一次 TTL 都是一次付費修訂。

## 5. `.env` 閘

### 5.1 錯誤訊息

`_unmaskable_env_error`（`tool_builder.py:2312`）改成回報**是哪些 key**。訊息仍然只講條件、key 名
與補救，絕不含值：

- 過短：「既有工具包 .env 的 `CACHE_TTL`、`TIMEOUT` 值短於 6 字元、無法遮蔽，修訂已取消：如果是
  秘密請加長；如果只是設定，請移到同目錄的 config.env。」
- 拼法：「既有工具包 .env 的 `TOKEN` 那一行寫法無法對應到實際值……」。被後面同名行蓋掉的舊行，也用
  `_env_line_key` 取得它的 key。

key 名最多列 5 個（其餘寫「等 N 個」），每個截到 64 字元，並先過 `redact_known_secrets`。

### 5.2 送出時就檢查

現行的閘在修訂 **job 裡**（`run_revise`，`tool_builder.py:2517`–`2536`）：送出後先回 202，幾秒後
輪詢才拿到紅色的失敗卡片。一鍵按下的地方可能不是工具頁，操作者可能根本看不到那張卡片。

改成：送出路徑在取得全域名額**之前**，用一次 worker hop 跑同一道閘（`_read_env_for_values`、
`_unmaskable_env_error`，加上 `config.env` 可讀性）。擋下就回 `409`、code `env_policy`，訊息是
第 5.1 節那段——不建工作、不花錢。既有的修訂表單一樣受惠。

**job 裡那道閘保留**，作為後盾：從送出到 job 真正開跑可能隔分鐘級，裁決 #15 要防。

## 6. 工具執行紀錄 `tool_run`

### 6.1 欄位

新的 SQLModel 表，放在 `models.py`。`init_db` 的 `create_all`（`db.py:259`）會建立缺少的表，不需要
migration。

| 欄位 | 說明 |
|---|---|
| `id` | 自增主鍵 |
| `tool_name` | 套件名（索引） |
| `vid` | **實際執行的版本**，也就是廣告時綁定的那一版 |
| `started_at`、`duration_ms` | |
| `outcome` | `ok`（stdout 超過上限而被截斷時另記 `truncated`）／`failed`（非零 exit）／`output_overflow`（stderr 超過上限，整組行程被終止）／`timeout`／`start_failed`／`refused`（停用、版本已換、身分不符：工具沒有執行） |
| `exit_code` | `failed` 才有 |
| `workflow` | 呼叫來源：`capture`、`enrich`、`assist_update`……；後端自己執行的是 `health_check`（跑一次範例）與 `verify`（修正後自動驗證），見第 10 節 |
| `check_id` | `health_check`／`verify` 那一批的 job id，用來推導驗證狀態（第 9 節）；其他為 null |
| `llm_log_id`、`llm_log_process` | 連回 AI 日誌那一筆；用既有的 process token 判斷後端是否重啟過。`health_check`／`verify` 沒有這個連結，前端不顯示空連結；ring 只有 50 筆，連結失效是常態 |
| `args`、`stderr`、`stdout` | **只有非 `ok` 才存**，已遮蔽、有上限（第 6.2 節） |

只記錄**已安裝工具**的執行（`_make_handler` 這條路）。builder 的 meta-tool（`run_shell` 等）不記，
它們留在建置那一場的 AI 日誌裡。

### 6.2 寫什麼

- **成功只記中繼資料**，不存參數與輸出。D09 的理由（內容含個人資料）對成功執行一樣成立，而成功
  執行對除錯的價值低。
- **失敗存內文**：參數（至多 8,000 字）、stderr 的尾端（至多 16,000 字，traceback 的關鍵在最後）、
  stdout 開頭（至多 4,000 字）。stderr 本身最多只讀到 `llm_tool_output_max_chars`（預設 50,000）
  就會終止行程，所以「尾端」指的是讀進來那一段的尾端。
- **先遮後切**，沿用全專案 redact→cap 的順序。stderr／stdout 直接取 `_run_tool_subprocess` 已經為
  模型遮好的那份文字再切；參數在 `_inflight_secrets` 範圍內用 `redact_known_secrets` 遮，與輸出
  用同一刻的已知秘密集合。整段先遮過，之後從頭切或從尾切都只會切到遮蔽標記，切不出秘密片段。
  **逾時與輸出超限兩條路徑目前在遮蔽之前就回傳**（`tools.py:2887`），結構化結果必須在這兩條路徑
  也先遮，才交給紀錄器。
- **寫入前套 `_utf8_safe`**（`tools.py:1325`）：模型送出的參數可以含 lone surrogate，sqlite3 會拒絕
  寫入。
- **讀出時再遮一次**：寫入之後才加進 `.env` 的秘密，在顯示與附進提示時也會被遮（與 v5 不變量 F
  同一個精神）。
- **已知殘留**：寫入時還不是已知秘密、之後才搬進 `.env` 的值，尾端切法可能在開頭留下一段碎片，讀出
  時遮不到。那個值在當時已經完整出現在給模型的結果與 AI 日誌裡，這條殘留不擴大暴露面，接受。

### 6.3 寫入方式

- `_run_tool_subprocess`（`tools.py:2829`）改成回傳結構化結果：outcome、exit code、已遮蔽的
  stdout／stderr，以及給模型的字串。`_make_handler`（`tools.py:3023`）照舊把給模型的字串交回，其餘
  交給紀錄器。**交給模型的字串不得因此改變。**
- 紀錄器用注入的方式接（`tools.set_run_recorder(...)`，在 `main.py` 接線），與
  `llm_log.set_secret_provider` 同一個模式：`tools.py` 不直接依賴資料庫，測試可以換掉它。紀錄器
  回傳寫入的 id；寫入失敗時回報 `recorded=false`，第 8.2 節的請求收集器照樣收到這次失敗。
- **觀測者不變量**：寫入失敗只記一行不含內文的 WARNING，工具結果照常回給模型，與 `llm_log` 的
  no-observer-failure 不變量相同。
- 寫入在獨立的短 session 裡完成，連線用短的 busy timeout（1–2 秒），不讓 purge 之類的寫入把 LLM
  迴圈卡住 5 秒（sqlite3 的預設）。AI 路由在 LLM 呼叫期間不持有 DB transaction
  （`routers/ai.py:413` 的既有規則），所以不會與請求自己的 session 互鎖。
- 連回 AI 日誌：`generate_structured`（`llm.py:1301`）建立 recorder 時 id 就已經分配好
  （`llm.py:1356`），把 id、process token 與 workflow 放進 ContextVar，handler 讀它即可。

### 6.4 生命週期

- **刪除工具 ⇒ 一併刪除它的紀錄**。順序是檔案系統刪除成功（`removed` 或 `retained`）之後才刪紀錄；
  回 `409 ai_job_in_progress` 時什麼都不動。紀錄刪除失敗時，回應帶 `runs_deleted: false`，前端提示
  用「清除紀錄」的孤兒範圍清掉。名稱不是身分；但就算舊紀錄留下，它們的 vid 也不可能等於同名重裝的
  新工具的版本，所以不會觸發一鍵修正（第 8.5 節）。
- **丟掉一個版本 ⇒ 紀錄保留**，畫面標示「版本已丟棄」。
- 操作者手動刪掉工具目錄（D21）留下的紀錄是**孤兒**，由 purge 的孤兒範圍清除（第 7 節）。

## 7. 手動 purge

**不自動刪除。** 每筆紀錄的大小有上限，成功只記中繼資料，所以成長很慢；工具頁顯示筆數與失敗筆數，
由操作者決定何時清。

**範圍**（可以組合）：

| 條件 | 選項 |
|---|---|
| 工具 | 某一個工具／全部 |
| 結果 | 全部／只清成功／只清失敗 |
| 時間 | 全部／N 天前的 |
| 孤兒 | 只清已不存在的工具留下的紀錄 |
| 單筆 | 指定一筆（例如內容不想留） |

**先預覽再刪**：`dry_run` 回 `{matched, max_id}`，確認框顯示「將刪除 N 筆」；確認時帶回 `max_id`，
實刪加上 `id <= max_id`。預覽之後才落地的紀錄（例如另一個分頁的工具呼叫剛好失敗）不會被一起刪掉。

**兩個入口，共用同一個服務函式**：

- **工具頁**：每個工具的「最近執行」有「清除紀錄」選單（全部／只清成功／30 天前）；頁首顯示筆數
  與「清除…」；單筆在詳情裡刪。
- **API**：全域操作放在獨立前綴 `/api/tool-runs`。`routers/tools.py:676` 的註解記載過，
  `/api/tools/` 底下任何字面的第一段都可能是合法套件名，獨立前綴讓全域操作避開這個問題。
  - `GET /api/tool-runs/stats`：每個工具的筆數、失敗數，以及孤兒數
  - `POST /api/tool-runs/purge`：`{tool?, outcome?, older_than_days?, orphans_only?, dry_run, max_id?}`
    → `{matched, deleted, max_id}`
  - `GET /api/tool-runs/{id}`、`DELETE /api/tool-runs/{id}`
  - 單一工具的列表：`GET /api/tools/{name}/runs`

  **宣告順序是兩個地雷**：`/api/tools/{name}/runs` 是兩段式 GET，要宣告在 `/jobs/{job_id}` 之前；
  `/api/tool-runs/stats` 要宣告在 `/{id}` 之前，否則 `stats` 會被當成 id 而回 422。兩者都要有路由
  順序測試。

**不提供 CLI**：它唯一獨有的價值是 VACUUM 與「後端沒在跑時也能清」，前者在 README 寫一行手動
做法就夠，後者對單人本機工具沒有實際需求。

**磁碟空間**：SQLite 的 DELETE 不會縮小檔案，空出的頁會被之後的寫入重用。要真的縮小，README 寫明
在**後端停止時**執行 `sqlite3 <資料庫檔> 'VACUUM'`（後端在寫入時 VACUUM 會失敗）。

**與修訂的互動**：附上紀錄的修訂在**送出時**就把紀錄內容快照下來交給工作（第 8.3 節），之後 purge
那幾筆不影響已排隊或進行中的修訂。

## 8. 一鍵請 AI 修正

### 8.1 按一下做什麼

直接送出 `POST /api/tools/{name}/revise`，帶 `run_ids`（失敗紀錄）與 `expected_vid`（目前版本），
**不帶意見、不開表單**。工具詳情裡另有「加上說明…」，打開既有的修訂表單並附上同樣的紀錄，給想補充
背景的時候用。

`run_ids` 最多 3 筆。有附紀錄時 `feedback` 是選填；沒寫時提示寫明「操作者只要求修正附上的失敗」。
附哪幾筆由操作者決定，builder 不自己去翻紀錄：提示內容可預期，也不會帶進無關的資料。

**provenance**：後端把附上紀錄的摘要（id、時間、結果、exit code，不含 stderr）寫成一行意見文字，
附在操作者的意見後面（或單獨成為意見），存進新版本既有的 `origin.feedback`。版本因此記得自己是為了
哪幾次失敗而產生；`origin.json` 不需要新欄位，`write_origin_meta` 的固定欄位（`tools.py:1822`）
也不用動。

### 8.2 入口

| 入口 | 附上哪幾筆 |
|---|---|
| 工具列表：最近一次執行是「可修的失敗」時（第 8.5 節），列上顯示「最近一次執行失敗」與按鈕 | 最近那一筆 |
| 工具詳情的「最近執行」：每筆可修的失敗各一顆 | 點的那一筆 |
| 擷取、補齊、協助更新的 AI 結果：這次請求裡有工具失敗時，結果旁顯示提醒與按鈕 | 這次請求裡的失敗（最多 3 筆） |
| 「跑一次範例」與修正後自動驗證的結果（第 10 節） | 失敗的範例 |

「加上說明…」只放在工具詳情；其他入口只有一鍵。

第三個入口讓失敗在**發生的地方**就看得到。AI 路由在請求開始時放一個 ContextVar 收集器，位置是既有
的 `_advertised_tools_lock`（`routers/ai.py:187`），它本來就包住每個會廣告工具的請求。每次工具失敗
都進收集器（就算紀錄沒寫成），路由再把它們放進回應的 `tool_failures`，每筆是
`{run_id, tool_name, vid, outcome, recorded}`。

這些頁面不知道工具的目前版本，所以按下時前端先讀一次工具列表：

- 失敗的 `vid` 等於 `current_vid`：送出，`expected_vid` 用它。
- 不相等：不送，顯示「工具已更新，失敗發生在舊版本」與連到工具頁的連結。
- `recorded=false`（紀錄沒寫成）：只給連到工具頁的連結。
- 回 `409 version_mismatch`：重讀一次再判斷；`409 job_busy`：顯示「目前有其他 AI 工作進行中」；
  `409 env_policy`：顯示第 5.1 節的訊息。

LLM 本身失敗而回 502 時沒有回應可放，但紀錄照樣寫進資料庫，工具列表上看得到。

### 8.3 按下之後

修訂工作沿用既有的 job 輪詢與全域名額：

1. `run_ids` 的驗證與快照在取得全域名額**之前**：這是資料庫讀取，與版本無關。不存在或不屬於這個
   工具就回 404／422，不建立工作、不花錢。`expected_vid` 的比對**維持在取得名額之後**（不變量 K，
   `tool_builder.py:2949`–`2960`）。快照連同已遮蔽的內文交給 `run_revise`，之後 purge 那幾筆不影響
   這次工作。
2. `.env` 閘在送出時就跑過（第 5.2 節）。
3. builder session 帶著失敗紀錄與固定的除錯程序（第 8.4 節）。
4. 三種結局，工作卡片各有呈現：

| 結局 | 條件 | 卡片 |
|---|---|---|
| **已發布** | `ready=true` | 發布新版本，接著**自動驗證**：用新版本跑 `examples.json`（只跑範例，不重跑附上的原始輸入），結果記進執行紀錄（`workflow=verify`）並顯示在卡片上。總預算與短路見第 10 節。驗證有失敗就轉紅，旁邊放「丟掉這一版」。不自動丟棄：那是付費建置的結果，由操作者決定 |
| **未發布** | `ready=false` | 不發新版。卡片用**橘色**，標題「AI 未發布新版本」，主文是 AI 的 summary。它可能是外部原因（憑證過期），也可能是 builder 修不好；卡片不宣稱是哪一種 |
| **失敗** | LLM 錯誤、逾時 | 照舊紅色 |

job 狀態多兩個欄位：`outcome`（`published`／`not_published`／`failed`）與 `verification`
（`{runs: [{run_id, name, outcome}], completed, total, budget_exhausted}`）。目前 `ready=false`
會變成一般錯誤字串「AI 判定修訂尚未完成：…」（`tool_builder.py:2627`），`InstallJob` 也沒有這兩個
欄位（`tool_builder.py:2739`）。

撤銷一次修正就用既有的「丟掉這一版」。**不可變版本是一鍵可以直接發布的前提**：修錯了退回去就好。

### 8.4 除錯程序（修訂提示）

提示加一段 `Failing runs attached by the operator`。每筆列出時間、workflow、**執行的版本是否就是
工作區這一版**、結果（`output_overflow` 寫成「輸出超過上限被終止」，不寫 exit -9）、exit code、
stdin 參數、stderr 尾端，並附固定程序：

1. 先用完全相同的參數重現（`echo '<args>' | <entry>`），確認看到同樣的錯誤。重現不了就照實說並
   找原因（API 變了、憑證、資料相依），不要猜著改。
2. 修正根因。
3. 用每一組附上的參數、以及 `examples.json` 的每個範例重跑，全部成功才回 `ready=true`。
4. 問題不在程式碼（例如憑證過期、API 停機）時回 `ready=false`，說明原因與操作者該做什麼。
5. 把修好的輸入改寫成不含個人內容的等價輸入，加進 `examples.json`（第 10 節）。只放唯讀的輸入。
6. summary 寫出根因、改了什麼、怎麼驗證、新增了哪些範例。

### 8.5 防呆

- **只有可修的失敗才給按鈕**：`outcome` 是 `failed`、`output_overflow`、`timeout`、`start_failed`，
  **而且失敗的版本就是目前版本**。`refused` 只顯示文字（例如「最近一次呼叫被拒：工具已停用」）；
  舊版本的失敗只顯示「失敗發生在舊版本」。這條規則由後端算（`last_run.fixable`），前端不重算。
  它同時擋掉重複付費：修好並發布之後，原本那筆的版本不再是目前版本，按鈕自然消失。
- **不加確認框**：一鍵就是一鍵。費用的上限來自既有的全域名額——同一時間只能有一個 AI 工具工作；
  工作進行中所有修正按鈕停用（與既有「送出修訂」相同的停用條件）。
- **從其他頁面按下**：畫面顯示「已開始修正」與連到工具頁的連結 `/tools?job=<id>`，工具頁依網址接上
  那個工作的進度卡片（第 9 節）。
- **停用中的工具**：可以修正（修訂不執行已安裝的工具），但不做自動驗證，因為執行路徑對停用的工具
  fail closed。卡片寫明「工具已停用，未自動驗證」。
- **副作用**：後端只自動執行 `examples.json`；附上的原始輸入只由 builder 在 session 內重現（它本來
  就有 D21 範圍內的執行能力）。builder 被要求只把唯讀輸入寫進範例。

### 8.6 一鍵做不到的

exit 0 但結果不對：沒有失敗紀錄可附。這種情況照舊用修訂表單寫意見。

## 9. 前端

- **工具列表**：`ToolSummary` 多一個 `last_run: {id, outcome, started_at, vid, fixable} | null`。
  可修時顯示「最近一次執行失敗」與「請 AI 修正」；不可修時只顯示文字。
- **工具詳情**：
  - 「設定」（資料來自新的 `GET /api/tools/{name}/settings`）：`.env` 的 key 名（不顯示值）、
    `config.env` 的內容（值仍經過 `redact_known_secrets`，萬一秘密放錯檔也不會從這裡外流）、兩邊
    衝突的 key、第 4 節的兩種提醒。`.env` 的 key 旁邊說明「`.env` 的每個值都會被當成秘密遮蔽，
    不是秘密的請移到 config.env」。**遷移來的工具**（任一版本 `origin.json` 的 `source` 是
    `legacy-ai-meta` 或 `pre-existing/unknown`）另外顯示提醒：「這個工具建於 0.4.0 以前，`.env`
    可能混著設定」並列出 key。先做唯讀，編輯照舊手改檔案。
  - **驗證狀態**：由目前版本的 `verify`／`health_check` 紀錄（依 `check_id` 分批）推導——「沒有
    範例」、「尚未驗證」、「驗證通過（3/3，時間）」、「驗證失敗（2/3）」、「驗證未完成（預算
    用完）」。後端重啟、驗證中斷之後的復原路徑，就是按「跑一次範例」。
  - 「最近執行」：時間、版本、來源、結果、耗時。失敗的那一筆可以展開看參數與 stderr，可修的有
    「請 AI 修正」與「加上說明…」。
  - 「跑一次範例」與它的結果（第 10 節）。
  - 「清除紀錄」選單（第 7 節）。
- **工作卡片**：三種結局（第 8.3 節）；已發布時列出自動驗證的結果，驗證失敗時旁邊是「丟掉這一版」。
- **擷取、補齊、協助更新**：回應帶 `tool_failures` 時，在 AI 結果旁顯示提醒與按鈕（第 8.2 節）。
- **頁首**：執行紀錄筆數、「清除…」。
- **`/tools?job=<id>`**：以 jobId 為 key 的獨立卡片。非終態時與本地工作一樣觸發全域停用；終態時
  用 `tool_name` 做名稱前綴的重新讀取（沿用 `revalidateSummaryAndList`），不寫任何以 vid 為 key 的
  快取，所以不影響 v5 不變量 H／J。`toolsRoute` 加 `validateSearch`（比照 `/llm-logs`，
  `router.jsx:169`），丟掉不合法的值。job 被逐出或後端重啟時，沿用既有的「找不到這個修訂工作」文案。

## 10. 版本內的回歸輸入 `examples.json`

**是什麼**：每個版本目錄裡一份小檔案，列出「這個工具一定要能處理的輸入」，等於這個工具的測試清單：

```json
{
  "examples": [
    {"name": "一般查詢", "args": {"query": "SQLite WAL"}},
    {"name": "查無結果時回空清單（修正 2026-10-26 的 KeyError）", "args": {"query": "zzzz-no-hit"}}
  ]
}
```

通過條件只有「exit 0、沒有逾時」。它打的是真的 API，結果會變，所以不比對輸出內容。

**為什麼放在版本裡**：它是版本內容，跟著程式碼走。修訂會把目前版本複製到工作區，所以範例自動帶到
下一版；丟掉一個版本，就回到上一版當時的範例。

**怎麼用**：

1. **builder 維護**：安裝時把它測過的輸入寫進去；修好一次失敗後，把那組輸入的等價版本加進去
   （第 8.4 節）。
2. **修訂時全部重跑**：修訂提示要求 `ready=true` 之前把每個範例都跑過一遍。這擋的是「修好 B、弄壞
   A」——目前 builder 只驗它當下試的那組輸入。
3. **後端執行**：
   - 「跑一次範例」是 job 表裡的一種 job（`kind=health_check`）：同一個輪詢端點、同一張卡片、占用
     全域名額，所以所有版本寫入按鈕一起停用。
   - 修正後的自動驗證在修訂 job 內、發布之後執行，用同一個執行函式。
   - 執行函式重用 AI 請求執行工具的同一條路：取得共享鎖（`acquire_shared_tools_lock`）、
     `bind_request_tools_lock`，再從 `enabled_llm_tools()` 取出那個工具的 handler 直接呼叫。身分
     檢查、遮蔽、執行紀錄因此全部照舊。停用中的工具不在 `enabled_llm_tools()` 裡，所以不跑。
   - **總預算**：預設 5 分鐘（設定值）。第一個逾時之後，其餘範例標示「略過」不再執行（同一個 API
     多半一起掛）。超過預算就結束這一批，標示「驗證未完成（N/M）」。
   - 執行期間持有共享鎖，所以刪除與丟棄會回 `409 ai_job_in_progress`；預算就是這段等待的上限。
   - 失敗的範例可以一鍵請 AI 修正（第 8.2 節）。

**限制**：

- 只能放**唯讀**的輸入（查詢類）。會寫入或刪除資料的 API，範例每跑一次就真的動一次。
- **個資**：失敗紀錄的參數可能含個人內容，而版本內容永久保留、purge 清不到。提示要求 builder 改寫
  成能觸發同一條程式路徑、但不含個人內容的等價輸入（例如換一個同樣查無結果的關鍵字），並在 summary
  列出新增的範例。
- 範例數量設上限（例如 10 個），每個沿用一般工具呼叫的 timeout。
- 後端讀 `examples.json` 時要驗形狀；格式錯誤就回報，不執行。

## 13. 剩下的不確定

1. **「結果不對但 exit 0」抓不到**：成功執行不存內文，所以這類問題仍要在修訂意見裡描述。之後可以
   加一個「每個工具可選擇記錄成功執行的內容」的開關。
2. **模型送出無效的參數 JSON**：`llm.py` 在呼叫 handler 之前就擋下，不會留下執行紀錄。那是模型的
   問題，不是工具的。
3. **`config.env` 的網頁編輯**：先做唯讀。要在網頁上改，得先定義寫入時的原子性與權限模式（`init-env`
   已有一套可以參考）。
4. **停用中的工具能不能跑範例**：目前沿用執行路徑的 fail-closed，不跑。若要「先測再啟用」，得在
   執行路徑加一個操作者明示的例外，那是安全敏感的改動，有需要再議。
5. **一鍵沒有確認框**：費用的上限只靠全域名額。若實際使用發現容易誤按，再加輕量的防呆（例如按住
   確認），而不是確認框。
6. **沒採納的 review 建議**：讓 builder 自報失敗原因的分類欄位（R11）、AI 日誌顯示每筆遮蔽了幾處
   （R20）。前者是模型自報、不可靠；後者是新的日誌欄位，對單人工具價值不明。有需要再議。
