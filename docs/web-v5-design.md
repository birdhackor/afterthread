# web-v5 設計：不可變版本 + 指標切換

本文件是 web-v5 的**設計本體**。`docs/web-v5-plan.md` 是最初的計畫，其設計章節已被取代
（保留以追溯「當初打算怎麼做、後來為什麼不是」）。已完成的 P1 的裁決在
`docs/web-v5-decisions.md`（D41 及其五個 review 附錄）。

**修訂紀錄**：第一版經過一輪 design review（9 條 finding，6 條 P1）與一輪與操作者的討論後
重寫。第 12 節逐條記錄每一條 finding 的處置。

## 1. 要解決什麼

v4 的 overall review 跑了九輪、33 個 finding，全部是同一個類別的實例：

> **可變的路徑就是身分。** 名稱 → 路徑 → *此刻*擺在那裡的東西。

P1 已經拆掉其中一個根因（開關就地改寫 manifest）。本設計拆掉另一個，也是比較大的那個：
**套件的內容會被原地換掉**。

## 2. 版面

```
<tools_dir>/<name>/                 # 整個目錄是後端管的
    .afterthread.meta/              #   後端的：這個工具「現在」的狀態
        state.json                  #     { "afterthread": ..., "enabled": bool }
        current                     #     目前生效的 <vid>
    versions/                       #   後端的：由後端建立、命名、刪除
        <vid>/                      #     一個版本
            .afterthread.meta/      #       後端的：這一版的資料
                origin.json         #         這一版是從什麼做出來的
                summary.json        #         這一版的 AI 總結（人類看的）
            tool.json               #       以下是工具自己的東西
            run.py …
    .env                            #   你的憑證，跨版本存活
```

### 所有權規則

第一版的規則寫「`.afterthread.meta/` 是後端的，其餘都是工具的」——**那是錯的**，因為
`versions/` 也是後端建立、命名、刪除的。正確的講法要分兩層：

- **套件層 `<name>/`**：整個目錄由後端管。`.afterthread.meta/` 與 `versions/` 都是後端的；
  `.env` 是**操作者的**（你會手動編輯，而且 v0.3.0 已出貨在這個路徑）。工具的檔案在這一層
  **一個都沒有**——它們全都住在某一版裡面。
- **版本層 `versions/<vid>/`**：`.afterthread.meta/` 是後端的，**其餘全部是工具的**。

這條界線的意義是：**工具（和產生它的 builder session）只在版本層裡活動，而後端在版本層只
佔用一個名字。** P1 review r5 的教訓——不要在別人的目錄裡宣告單一檔名——在這裡的落實方式是
只宣告一個目錄名，而且只在工具真正會寫東西的那一層宣告。

### 「不准碰」不是強制力

builder 的指示會寫明保留名稱，但**指示不能取代檢查**——builder session 有 shell，寫得出
任何東西。現行的 `_strip_builder_sidecars` 之所以存在就是這個理由，它必須繼續存在，只是
比對對象從一組檔名改成「staging 根目錄下的 `.afterthread.meta/`」（staging 根目錄就是未來的
版本根目錄）。

## 3. 三層可變性

第一版寫「發布後不再變」，同時又保留「隨時可以重新產生總結」——自相矛盾。正確的講法是三層：

| 東西 | 什麼時候固定 |
|---|---|
| 版本裡的**工具檔案** | 發布後後端不再修改（你手動改仍然可以，見第 7 節） |
| `origin.json` | **在提交之前**寫完，之後不再修改 |
| `summary.json` | **可以隨時整份原子替換**（總結晚於發布才生得出來，而且你可以按「重新產生」） |

這個區分是承重的：任何「這個目錄還會不會變」的判斷都要看它問的是哪一層。

## 4. 生命週期

### 全新安裝

1. builder 在 `.staging/<uuid>/` 建置（現行行為，不變）
2. 驗證 staging（現行行為，不變）
3. **在隱藏的暫存位置組出完整的套件外殼**：`versions/<vid>/`（staging 搬進來）、
   `.afterthread.meta/{state.json, current}`、把 staging **根目錄**的 `.env` 拉到套件層
4. `versions/<vid>/.afterthread.meta/origin.json`
5. **一次 rename 把整個外殼搬到 `<name>/`** ← 這一刻才叫安裝完成
6. 之後產生 `summary.json`

第 5 步之前 `<name>/` 完全不存在，所以任何一步失敗都只是丟掉暫存的東西，**不會留下一個佔著
名字又修不好的目錄**。

### 修訂

1. builder 在 `.staging/<uuid>/` 建置（不變）
2. 驗證（不變）
3. 把 staging 搬進 `<name>/versions/<vid>/`（新版本，舊版本原地不動）
4. 寫這一版的 `origin.json`（含這次的意見）
5. **切換 `current`** ← 這一刻才叫修訂完成
6. 之後產生 `summary.json`

第 5 步之前新版本已經在磁碟上，但**沒有任何東西指向它**，所以它是惰性的。`current` 是
唯一的提交點。

### 執行

工具是在一次 AI 工作**開始時**被廣告給模型的，模型可能幾分鐘後才呼叫。所以：

- **廣告的當下記住 `<vid>`**，連同那一版的規格一起
- **呼叫的時候直接跑那一版**，不再去讀 `current`

這是正確的語意：模型看到的是那一版的參數規格，跑那一版本來就對。中途發生的修訂不影響
進行中的對話——下一次對話才會拿到新版。

### 刪除工具

整個 `<name>/` 移除（有東西在執行就照現行做法延後）。

## 5. 版本保留與「丟掉這一版」

**所有版本永久保留，沒有自動回收。** 一個版本只有兩種方式消失：你按「丟掉這一版」，或你
刪掉整個工具。

**「丟掉這一版」的語意**：

- 刪掉目前這一版的目錄，`current` 指回**前一版**
- 只剩一版時丟掉 = **刪掉整個工具**（走現有的確認對話框，因為後果一樣）

「前一版」需要順序，所以 `<vid>` 用 **`20260728T134501Z-a3f9c1`**：UTC 時間戳（字典序＝時間
序）+ 六位隨機碼（防同一瞬間撞號）。看資料夾名字就知道那一版是什麼時候做的。

**沒有自動回收帶來的簡化**（這是第一版設計裡三個不確定項消失的原因）：不需要引用計數、
不需要保留策略、不需要「廣告到對話結束」的租約。一個在對話開始時被廣告的版本，永遠不會在
對話中途自己消失。唯一的例外是你在對話進行中親手丟掉它——那次呼叫會失敗，而那是你剛做的
動作。

**磁碟成本**：每一版是工具程式碼的完整副本，通常幾 KB。憑證不在版本裡（`.env` 在套件層），
而且安裝時的內嵌秘密掃描會擋掉把憑證寫進程式碼的版本，所以保留全部版本**不會**讓秘密多
曝露一份。

## 6. 移除「定版」

**`finalized` 整個拿掉**，連同 409 `tool_finalized`、`PATCH /api/tools/{name}/summary`、
兩道前置閘、換裝前的重讀、`StoreRefusal.FINALIZED`、以及前端「定版／解除定版」兩顆按鈕和
它們背後那套不對稱閘門規則（目前散在 8 個檔案約 240 處）。

**它原本的第一個用途**是保護可變的總結。總結一旦屬於版本，安裝和修訂都只寫進**新**版本的
資料夾，永遠不會碰到舊版本——這個用途消失。

**它原本還有第二個沒寫在名字上的用途**：中止一場進行中的修訂（現行程式在換裝前最後一刻
重讀定版狀態，前端也刻意讓它在工作進行中還能按）。design review 正確地指出拿掉它會失去這個
能力。**但這個能力在新版面下不需要**：建置全程都在暫存資料夾，套件只有在提交那一刻才變成
系統看得到的東西。中止一場修訂，跟讓它跑完再丟掉，結果一樣。所以取代它的是第 5 節的
**「丟掉這一版」**，而那是更直接的做法。

**「重新產生總結」保留。** 總結是寫給人看的（`tool.json` 的 `description` 才是給模型看的），
寫得不好不會讓工具行為出錯。新模型下唯一會覆蓋某一版總結的路徑，只剩下你自己按那顆按鈕。

## 7. 手改仍然被接住

你手動編輯版本目錄裡的工具檔案仍然是**支援的行為**（D21）。「不可變」是**後端自己的操作
之間**的約定，不是對你強制的性質。

現行的「對話中途 `tool.json` 被改過就拒絕執行」保留不變：後端在廣告當下記下該版
`tool.json` 的檔案身分，執行前再取一次。差別是這道檢查現在**只回答手改這一個問題**——因為
修訂不會再原地改寫任何東西。

## 8. 併發

**全域一次一個工作維持不變**（`_admit_job`）。安裝、修訂、同步重新產生總結共用一個名額。

理由有兩個，第二個是 design review 挖出來的：

1. 兩場修訂**同一個工具**時，`current` 是會被覆蓋的暫存器——兩次原子寫入都會成功，後寫的
   蓋掉先寫的，其中一場「成功」的修訂等於沒生效。（不同工具各有各的 `current`，不會互相
   覆蓋，所以這個理由本身只需要「每個工具一次一個」。）
2. **AI 日誌的歸屬**：後端記錄「這一版是哪次 session 建的」時，問的是「這個工作流程最新的
   一筆」而不是「我這次產生的那一筆」。兩場同工作流程的 session 並行時，這個答案會變成隨機
   ——工具 A 的日誌連結可能開出工具 B 的建置過程。這是裁決紀錄 #3 已接受的殘留，而它可以被
   接受**正是因為**全域一次一個讓它幾乎不可能發生。

放寬成「每個工具一次一個」會解決 (1) 但讓 (2) 從「幾乎不可能」變成「同時修兩個工具就會
發生」。操作者的實際使用是一次做一個（每場建置數分鐘且要花錢），所以維持全域限制的代價
是零，而放寬要付的代價是真的。**等到真的需要並行時，正確的做法是先把日誌歸屬修對
（讓每次呼叫記住自己產生的那一筆），而不是先放寬。**

## 9. `origin.json` 與 `summary.json` 的寫入契約

現行的 `write_tool_meta` 是側檔的**唯一收口**：固定 schema（不序列化呼叫端給的 dict）、
秘密遮蔽、大小上限、原子寫入，而且**遮蔽失敗就整個不寫**。把 origin 拆成獨立檔案**不得**
把這些丟掉。

- 兩個檔案都走**同等**的 typed / bounded / sanitized / fail-closed / atomic publisher
- **來源網址在捕捉當下就降級成無憑證的 provenance**（現行行為，不變）：presigned query 或
  路徑裡的 token 是遮蔽比對不到的，所以直接丟掉那些部分而不是遮蔽
- `origin.json` 現在還裝著**你的修訂意見**——自由文字，同樣要過遮蔽
- **`origin.json` 寫入失敗必須阻止提交**（它是發布的一部分）；`summary.json` 失敗只是
  沒有總結，不影響已完成的安裝或修訂

## 10. 遷移

一次性離線腳本，操作者手動執行，執行時沒有服務在跑。所以**不需要**讀取端同時看得懂兩種
版面，也不需要 lazy migration。

腳本要處理兩種既有狀態：

1. **v0.3.0 出貨的扁平版面**：`<name>/tool.json`（`enabled` 在裡面）+ 實作檔 + `.env`
2. **本分支 P1 之後**：同上，外加 `<name>/.afterthread-state.json`

`.ai_meta.json` **從未出貨**（`dcd2aef`，2026-07-26；v0.3.0 是 2026-07-23），所以只有分支上
的開發資料會有它。

腳本的行為：

- 先**完整備份**整個 tools 目錄
- 每個套件：建立 `versions/<vid>/`（vid 用套件的 mtime 或固定的初始值）、把工具檔案搬進去、
  `.env` 留在套件層、`enabled` 從 `.afterthread-state.json` 或 manifest legacy 欄位讀出來
  寫進新的 `state.json`、寫 `current`
- 若套件**本來就有** `versions/` 或 `.afterthread.meta/`（這兩個名字以前都不是保留字）：
  **停下來報告，不要自作主張**。操作者手動處理即可，不需要通用政策
- 遷移後 `_STATE_PUBLISH_LOCK` 可以刪除（它是 P1 的過渡性守衛，前提是狀態檔會被換裝波及；
  新版面下狀態檔不在被換掉的目錄裡，而且沒有 legacy 套件了）

## 11. 這個設計讓哪些既有問題不成立

| 問題 | 為什麼不成立 |
|---|---|
| R3／R6-1 執行中套件被換走或刪除 | 子行程的 cwd 是不可變的版本目錄，而且版本不會自動刪除 |
| R7-1 掃描→建 handler 的身分配對 | 廣告當下綁定 `<vid>`，執行時跑那一版；版本內容不會變，也不會消失 |
| R9-2 `list_tools` 撕裂的列 | 同上 |
| R8-1 origin 永久遺失 | `origin.json` 是提交的一部分，不依賴事後的 LLM 往返 |
| P1 r1-1 修訂覆蓋剛完成的切換 | 狀態檔不在被換掉的目錄裡 |
| 裁決 #9 修訂吞掉手改的狀態檔 | 同上 |
| 「總結描述的是另一個實作」 | 總結屬於版本 |

**注意 R7-1 那一列的條件**：它不成立**不是**因為版本不可變這一件事，而是「不可變 + 不自動
刪除 + 廣告當下綁定」三件事一起。少任何一件都不成立——這是第一版設計裡最嚴重的宣稱錯誤。

**不會**因此消失：

- v4 R9-1 日誌編號跨行程重用（llm_log 的問題，與版面無關）
- 操作者手改版本裡的工具檔案造成的中途變動（刻意保留拒絕行為，見第 7 節）
- 裁決 #5（能替換 tools root 的人已有服務的 uid）
- 裁決 #3 的日誌歸屬（見第 8 節）

## 12. design review 第一輪的處置

| # | 內容 | 處置 |
|---|---|---|
| 1 (P1) | 所有權規則自相矛盾，`versions/` 也是後端的；legacy 撞名 | 規則改寫（§2）；撞名交給遷移腳本停下來報告（§10） |
| 2 (P1) | 沒有把 staging 根 `.env` 拉到套件層，憑證會遺失 | 加進安裝流程（§4 第 3 步） |
| 3 (P1) | 沒有原子發布，失敗會留下佔名殘骸 | 隱藏位置組好再一次 rename（§4） |
| 4 (P1) | 遷移會重開 toggle 競態 | 離線一次性腳本，沒有並行操作（§10） |
| 5 (P1) | 沒有版本租約，R7-1 仍可達 | 全部保留 + 廣告當下綁定（§4、§5、§11） |
| 6 (P1) | `origin.json` 掉了 fail-closed 契約 | 明訂同等 publisher（§9） |
| 7 (P2) | `finalized` 也是中止訊號 | 不需要中止（建置在暫存區）；用「丟掉這一版」取代（§6） |
| 8 (P2) | `current` 會被覆蓋 | 維持全域一次一個，理由寫明（§8） |
| 9 (P2) | 可變性不變量自相矛盾 | 拆成三層（§3） |

## 13. 階段拆法

| 階段 | 範圍 |
|---|---|
| **P2** | 移除「定版」（後端 + 前端，約 240 處）。純刪除，不動版面，讓下一階段在簡化過的程式碼上動手 |
| **P3** | 版本版面 + 遷移腳本 + 「丟掉這一版」 |

原計畫的 P4（舊版本回收）**取消**——全部保留就沒有回收。原計畫的 P3（origin 與總結搬進
版本）已併入本設計，不再是獨立階段。

先刪定版再換版面的理由：定版的移除會拿掉一整套守衛與閘門，版面改動如果在它之後做，動的是
簡化過的程式碼；反過來則要把同一批總結相關程式碼改兩次。

## 14. 剩下的不確定

1. **遷移腳本的 `<vid>` 從哪來**：既有套件沒有「建立時間」的可靠來源（mtime 會被各種操作
   推動）。可能就用一個固定的初始 vid，反正遷移後只有一版。
2. **`.env` 留在套件層是否永遠正確**：如果將來某一版需要不同的環境變數（例如改用不同的
   API endpoint），單一 `.env` 會是問題。目前判斷是「不會，因為修訂是改實作不是換 API」，
   但這是假設而不是證明。
3. **前端「丟掉這一版」的確認流程**：只剩一版時等同刪除工具，需要讓你清楚知道按下去會發生
   什麼，但又不該每次都跳一樣的重量級警告。
