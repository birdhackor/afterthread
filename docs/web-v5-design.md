# web-v5 設計：不可變版本 + 指標切換

本文件是 web-v5 的**設計本體**。`docs/web-v5-plan.md` 是最初的計畫，其設計章節已被取代
（保留以追溯「當初打算怎麼做、後來為什麼不是」）。已完成的 P1 的裁決在
`docs/web-v5-decisions.md`（D41 及其五個 review 附錄）。

**修訂紀錄**：三輪 design review（9 + 15 + 15 條 finding）與兩輪與操作者的討論。第 16 節
逐條記錄每一條 finding 的處置。三輪的性質依序是：**規則自相矛盾** → **規則沒寫下來** →
**規則寫下來了但錯，或兩條各自正確的規則互相打架**。

## 1. 要解決什麼

v4 的 overall review 跑了九輪、33 個 finding，全部是同一個類別的實例：

> **可變的路徑就是身分。** 名稱 → 路徑 → *此刻*擺在那裡的東西。

P1 已經拆掉其中一個根因（開關就地改寫 manifest）。本設計拆掉另一個，也是比較大的那個：
**套件的內容會被原地換掉**。

**第二輪 review 的第一課**：本設計自己引進了一個新的「名字 → 路徑 → 此刻在那裡的東西」
——`current`，一個內容是目錄名的檔案——而第一版只寫了「切換是原子的」六個字。第 7 節是
補上的讀寫契約。

**第三輪 review 的第一課**：把一件事拆成兩個目錄之後，**每一個原本只需要一個答案的地方
都變成需要兩個**，而且漏掉的那些不會報錯，只會安靜答錯。第 4 節從「葉節點函式的分派表」
改成「連同時需要兩個錨點的函式一起指名」，就是因為第一版的表只分派了葉節點。

## 2. 操作環境與嚴格度校準

本專案是**單人本機工具**，這件事是設計前提，不是免責聲明。實際環境：

- **一個操作者，通常一個瀏覽器分頁。** 沒有多使用者、沒有多租戶。
- **建置類工作要花錢且以分鐘計。** 操作者不會、也沒有動機同時開好幾場。
- **沒有敵對行為者**（D21：能改套件檔案的人已經有服務的 uid）。手改是**支援的工作流程**。
- **工具集規模是個位數到數十個**，不是數千個。

由此得到的**嚴格度校準**，適用於本設計的 review 與實作：

- **併發類的 finding 要說出一個單一操作者做得出來的實際順序**，並以**對這個操作者的後果**
  判斷嚴重性，而不是以理論上的可達性。
- **修法要與嚴重性成比例。** 用「把這個操作加進既有的單一名額」就能關掉的，就那樣關掉；
  要引入新的鎖、租約、引用計數或協定，先問值不值得。
- **但這個折扣不涵蓋三類問題**，它們與併發無關，一律照原本的嚴格度處理：
  1. **正確性**——同一個問題在兩處會得到兩個答案、或某個函式被餵了錯的東西卻不會報錯。
  2. **失效復原**——當機、中斷、寫入失敗之後留下的狀態，以及有沒有路徑離開那個狀態。
  3. **資料遺失**——尤其是憑證與 origin 這種**唯一副本**。
- **「不成立」的宣稱不打折。** 一條宣稱某類問題不再可達的敘述，錯的時候比一個 bug 更糟，
  因為它會讓後續的 review 不再看那一塊。第 15 節的每一列都要對得起這個標準。

第三輪有兩條 finding 明確走了這條校準：第 9 條（廣告後被手動丟掉）reviewer 給了「引入
reservation/refcount」與「撤回保證並明訂 refusal」兩條路，本設計選後者；第 5 條（`.env` 讓
提交點變成兩個）則相反——它屬於失效復原類，不打折，因此改的是設計而不是嚴重性。

## 3. 版面

```
<tools_dir>/<name>/                 # 整個目錄是後端管的
    .afterthread.meta/              #   後端的：這個工具「現在」的狀態
        state.json                  #     { "afterthread": ..., "enabled": bool }
        current                     #     目前生效的 <vid>（契約見第 7 節）
    versions/                       #   後端的：由後端建立、命名、刪除
        <vid>/                      #     一個版本
            .afterthread.meta/      #       後端的：這一版的資料
                origin.json         #         來源、修訂意見、前一版（＝已提交標記）
                summary.json        #         這一版的 AI 總結（人類看的）
            tool.json               #       以下是工具自己的東西
            run.py …
    .env                            #   你的憑證，跨版本存活，而且是你的（見下）
```

### 所有權規則

- **套件層 `<name>/`**：整個目錄由後端管。`.afterthread.meta/` 與 `versions/` 都是後端的；
  `.env` 是**操作者的**（你會手動編輯，而且 v0.3.0 已出貨在這個路徑）。工具的檔案在這一層
  **一個都沒有**——它們全都住在某一版裡面。
- **版本層 `versions/<vid>/`**：`.afterthread.meta/` 是後端的，**其餘全部是工具的**。

這條界線的意義是：**工具（和產生它的 builder session）只在版本層裡活動，而後端在版本層只
佔用一個名字。**

**`.env` 屬於操作者這一條是承重的，不是分類上的講究。** 第三輪 finding 5 證明了這一點：
只要修訂還能出貨 builder 寫的 `.env`，一次修訂就有**兩個**要發布的東西（`.env` 與
`current`），而兩者沒有安全的先後——先寫 `.env` 而 `current` 失敗，等於舊程式吃到新設定；
先寫 `current` 而 `.env` 失敗，等於新程式缺設定。第 8 節因此**收掉修訂出貨 `.env` 的能力**，
那不是為了省事，而是所有權規則本來就這麼說：builder 不該伸手進你的檔案。

### 「不准碰」不是強制力

builder 的指示會寫明保留名稱，但**指示不能取代檢查**——builder session 有 shell，寫得出
任何東西。現行的 `_strip_builder_sidecars` 之所以存在就是這個理由，它必須繼續存在，只是
比對對象從一組檔名改成「build 根目錄下的 `.afterthread.meta/`」。

## 4. 兩個目錄錨點：哪個函式拿到哪一個

分層之後有**兩個**錨點。餵錯目錄**不會報錯，只會安靜地答錯**：拿版本目錄去讀 `.env` 會
讀不到憑證並忽略開關，拿套件目錄去跑會找不到 `run.py`。

**規則：不留任何一個叫 `directory` 而語意含糊的參數。** 引入
`ResolvedPackage(package_root, version_root, vid)`，兩個路徑成員是**不同型別**（同 D40 r5
讓兩種 identity 有不同 shape 的手法），餵錯是型別錯誤而不是執行期的錯答。

### 只需要一個錨點的

| 既有函式 | 拿哪一個 |
|---|---|
| `package_enabled` / `_read_enabled_state` | package_root |
| `_read_manifest_object` / `_scan_package` 的 manifest 讀取 | version_root |
| `package_identity`（`tool.json` 的 inode） | version_root |
| `_load_tool_dotenv` / `_env_values_for_package` | package_root |
| `_run_tool_subprocess` 的 cwd | version_root |
| `directory_identity`（執行中保護的登記） | version_root |
| `read_tool_meta`（總結） | version_root 的 `.afterthread.meta/` |

### 同時需要兩個的——必須整個 `ResolvedPackage` 傳進去

第一版的表只分派了葉節點，漏掉了這些**本來就一個目錄做完好幾件事**的函式：

| 函式 | 它同時做的事 |
|---|---|
| `_make_handler` / `_run_tool_subprocess` | 查啟用（package）、讀 `.env`（package）、驗 manifest identity（version）、當 cwd（version） |
| `tool_meta` 的總結 prompt 組裝 | 版本檔案 inventory（version）、`.env` 的 key 名（package） |
| `validate_package` | manifest 與內容（build/version root）、`.env` 大小閘（見下） |
| `delete_tool` 的延後判定 | 要走訪**所有** version_root |
| `.stale-` 殘骸清掃 | 同上，見下 |

### 已確認的兩個缺陷

**（一）刪除的延後判定會對不到 inode。** 已查證：handler 登記的是**子行程實際執行的那個
目錄**的 identity（`tools.py:3993`），而 `delete_tool` 查的是**被 rename 的套件根目錄**
（`tools.py:4357`）。分層之後兩個 inode 不相等，「沒人在跑」的判定為真，`rmtree` 在活著的
子行程底下執行。

**（二）`.stale-` 清掃有一模一樣的毛病，而且第二版設計把它寫成「不變」——那是錯的。**
`_sweep_stale_backups` 檢查的是 stale 套件**根目錄自己**的 identity
（`tool_builder.py:2494`），登記的卻是巢狀的版本目錄，所以延後成功之後，**下一場建置工作
結束時的清掃會把它收走**。單一操作者做得出來的順序：分頁 A 呼叫一個慢工具 → 分頁 B 啟動
一場安裝 → 刪除該工具（正確延後，改名成 stale）→ 建置結束執行清掃 → stale 被 rmtree →
慢工具的子行程讀檔 ENOENT。

**兩者的修法是同一條**：凡是要判斷「這個套件底下還有沒有東西在跑」的地方，都要走訪
**所有版本目錄**的 identity。`delete_tool`、`.stale-` 清掃、以及未來任何同類判斷共用一個
函式，不要有第二種拼法。

### `.env` 大小閘的時機

現行閘讀的是「傳進來的那個目錄的 `.env`」（`tools.py:1160`），而安裝時驗證發生在**還沒有
package root 的時候**。所以要檢查**兩次**：

1. **hoist 之前**檢查 build 根目錄的 `.env`——擋掉 builder 產出的超大檔
2. **組裝完成、秘密注入之後**檢查 shell 的套件層 `.env`——那才是工具最終會讀到的那一份

少了第二次，一個超大的 `.env` 會安裝成功，執行期再靜默降級成空環境
（`tools.py:3273` 的 degrade-to-`{}`），工具跑起來但沒有憑證。

## 5. 三層可變性

| 東西 | 什麼時候固定 |
|---|---|
| 版本裡的**工具檔案** | 發布後後端不再修改（你手動改仍然可以，見第 11 節） |
| `origin.json` | **在提交那一刻就已經在裡面**，之後不再修改（第 8 節的組裝順序） |
| `summary.json` | **可以隨時整份原子替換**（總結晚於發布，而且你可以按「重新產生」） |

## 6. `.afterthread.meta/` 的合法狀態

半完成的 meta 目錄是**當機與寫入失敗的正常產物**，不是異常輸入。

### 套件層 `<name>/.afterthread.meta/`

| 狀態 | 判定 |
|---|---|
| `<name>/` 存在但**完全是空的** | 我們自己中斷的安裝留下的殘骸：列為 invalid，且**下一次同名安裝可以直接覆蓋它**（第 8 節） |
| 目錄不存在（但 `<name>/` 非空） | 未遷移的舊版面套件：invalid，訊息要指向遷移腳本（第 14 節） |
| `current` 缺、壞、或指不到一個完整版本 | 套件 **invalid，不啟用、不執行**（第 7 節，fail closed） |
| `state.json` 缺 | **視為 disabled** |
| `state.json` 是別人的（FOREIGN） | 同 P1 已定語意：視為缺，且**永不覆寫、永不刪除** |
| `state.json` 讀不到（UNREADABLE） | fail closed，視為 disabled |

**`state.json` 缺席的預設必須從現行的 `true` 翻成 `false`。** 已查證 `_effective_enabled`
（`tools.py:757`）：狀態不是我們的、manifest 又讀不到時回傳 `True`。新版面下套件層沒有
`tool.json`，legacy fallback 會拿到 `manifest=None` 而回答 `True`——於是一個只寫到一半的
meta 目錄會**把工具自己打開**。

修法不是加特例，而是**刪掉整條 legacy fallback**。這條的前提是「遷移之後不存在任何
legacy 套件」，而那個前提要靠第 14 節的**全有全無**遷移來保證——第三輪 finding 12 正確
指出：只要允許部分遷移，這個前提就不成立。

### 版本層 `versions/<vid>/.afterthread.meta/`

| 狀態 | 判定 |
|---|---|
| `origin.json` 在且合法 | 這一版**已提交**——它同時就是提交標記 |
| `origin.json` 缺或壞 | 這一版**未提交**：不可被 `current` 指向、找前一版時跳過、可被清理 |
| `summary.json` 缺 | **正常**（總結晚於發布） |
| `summary.json` 壞 | 視為沒有總結（沿用現行 `read_tool_meta` 的 total 語意） |

## 7. `current` 的讀寫契約

**vid 的語法**：`20260728T134501Z-a3f9c1`——UTC 時間戳 + 六位小寫 hex，正規式
`^[0-9]{8}T[0-9]{6}Z-[0-9a-f]{6}$`。這個語法**不含路徑分隔符也不含點**，所以
`../../.staging/<uuid>` 這種內容是**語法錯誤**而不是需要另外做包含性檢查的東西——把穿越
變成不可表示，比事後檢查便宜也可靠。

**讀（`current` 的目標驗證，以下簡稱「目標驗證」）**：

- 用現行的有界讀取器（`O_NOFOLLOW` + `S_ISREG`），上限 64 bytes
- 內容去掉尾端換行後必須**恰好**符合 vid 語法；空檔案是錯誤
- `versions/<vid>/` 必須存在、是**真的目錄**（非 symlink）、且**已提交**（第 6 節）
- 任何一項不成立 → **這個套件沒有生效版本**：invalid、不列為可用、不廣告、不執行。
  **不猜、不 fallback 到最新的一版**——猜就是同一個毛病

這套驗證**不只在讀取時用**：第 9 節的 discard 在把 `current` 指向前一版之前，必須讓那個
前一版通過**同一套**目標驗證。同一個問題只有一個拼法。

**寫**：走與側檔相同的原子發布器（mkstemp → fchmod → write → fsync → `os.replace` →
fsync 目錄）。`os.replace` 不會留下半個檔案，所以**寫失敗時舊值完好且仍可讀**。

**但發布器必須多回一個答案：這次發布持久化了沒有。** 已查證現行發布器在 `os.replace`
之後的目錄 fsync 是 `contextlib.suppress(OSError)` 包起來的，失敗也回 `True`
（`tools.py:1643）`。對開關來說那是對的（rename 已經發生，回 False 會謊報「沒生效」）；
但 discard 要**先確定指標落地、才可以毀掉舊版**，吞掉持久化失敗會讓斷電後檔案系統回到
舊的 `current=V`，而 V 已經被刪了——懸空指標。所以發布器回傳
`(published: bool, durable: bool)`：開關只看 `published`，discard 兩個都要看。

## 8. 生命週期

### 暫存區的三個名字

| 名字 | 是什麼 |
|---|---|
| `session_root` = `<tools_dir>/.staging/<uuid>/` | 這一場工作的全部，**`finally` 永遠清掉這個** |
| `build_root` = `session_root/build/` | builder 的工作區 |
| `shell_root` = `session_root/shell/` | 組好的成品 |

第三輪 finding 3 指出第二版寫的「既有 cleanup 自動涵蓋」**不由現行呼叫形狀保證**：現行
`_cleanup_staging` 只遞迴刪掉**它收到的那個路徑**，再試著 `rmdir` 父目錄
（`tool_builder.py:2543`）。如果 builder 改成拿 `build_root`，清理就只刪 `build/`，含
`.env` 的 `shell/` 會**永久留下一份憑證**。所以三個名字要明確分開，而**清理一律以
`session_root` 為對象**。

暫存區放在 `<tools_dir>/.staging/` 底下是**結構性**要求，不是慣例：現行程式碼靠
「staging 與 target 同在 `<tools_dir>` 底下」證明 rename 不會 EXDEV
（`tool_builder.py:2188`）。放到系統 temp 就會踩到，改用 `shutil.move` 則原子性沒了。

### 落地：一次 rename，不做 mkdir 佔名

第二版寫的是 `os.mkdir` 佔名再 rename。第三輪 finding 4 正確指出那是**兩個 syscall 不是一次
狀態轉移**：mkdir 成功後當機就留下一個空的 `<name>/`。

改成**單純一次 `os.rename(shell_root, <name>)`**，三種結果都是對的：

- 名字空著 → 成功
- 名字被**非空**目錄佔著 → `ENOTEMPTY`，安全失敗（這正是「同名工具已存在」該有的結果）
- 名字被**空**目錄佔著 → rename 成功並取代它。而一個空的 `<name>/` 只可能來自我們自己
  中斷的安裝（第 6 節把它定義成可回收殘骸），取代它正是想要的行為

少一個 syscall，也少一個要復原的狀態。

### 全新安裝

1. builder 在 `build_root` 建置（現行行為，不變）
2. 驗證 build 內容；**檢查 build 根的 `.env` 大小**
3. 在 `shell_root` 組出**完整**的套件：
   - `versions/<vid>/` ← build 的內容
   - `versions/<vid>/.afterthread.meta/origin.json`（`previous` 為 null）
   - `.afterthread.meta/state.json` 與 `.afterthread.meta/current`
   - 把 build 根的 `.env` 拉到 shell 的**套件層**
4. 注入表單秘密；**再檢查一次套件層 `.env` 大小**
5. `os.rename(shell_root, <name>)` ← **這一刻才叫安裝完成**
6. 之後產生 `summary.json`

### 修訂

1. builder 在 `build_root` 建置（不變）
2. 驗證（不變）
3. 在 `shell_root` 組出**一個版本目錄**的內容：build 的內容 +
   `.afterthread.meta/origin.json`（含這次的意見，`previous` = 目前的 vid）
4. `os.rename(shell_root, <name>/versions/<vid>)`
5. **發布 `current`** ← **這一刻才叫修訂完成**
6. 之後產生 `summary.json`

第 5 步之前新版本已經在磁碟上而且是**完整已提交**的，但沒有任何東西指向它，所以它是惰性的。
`current` 是唯一的提交點。

**vid 碰撞是要檢查的正常失敗，不是前提。** 六位 hex 只有 24 bits；時鐘回撥、同一秒重試、
或先前未發布的殘骸都可能讓 `versions/<vid>` 已經存在。rename 到一個非空目錄會失敗，所以
不會覆寫，但「名字必然空著」這個宣稱是錯的。做法：偵測到就重新產生 vid 並重試（有限次），
而不是讓一場花了幾分鐘和金錢的建置在提交那一刻失敗。

### 修訂與 `.env`：收掉 builder 出貨 `.env` 的能力

現行程式在修訂路徑上允許「本來沒有 `.env`，builder 做一份出貨」（`tool_builder.py:1978`）。
**新版面下取消這條。** 修訂只發布一樣東西：`current`。

理由是第 3 節的所有權規則，不是省事：套件層的 `.env` 是**操作者的**。而第三輪 finding 5
證明了保留它的代價——一次修訂會有兩個要發布的東西而且**沒有安全的先後**：

- 先寫 `.env`、`current` 失敗 → 工作回報失敗，但舊程式已經吃到新設定
- 先寫 `current`、`.env` 寫入失敗或當機 → 新程式在缺設定的情況下生效

這不需要併發，一次普通修訂加一次寫入失敗就會發生，屬於第 2 節不打折的失效復原類。

新的行為：

- 套件層 `.env` 在修訂期間**原封不動**（不 carry、不覆寫、不刪除）
- builder 在 build 根寫的 `.env` 在組 shell 時**丟棄**，並在工作結果裡告訴操作者
  「這一版需要 X、Y 兩個環境變數，請自行加進 `<name>/.env`」
- 版本內**巢狀**的 `.env` 仍然是普通的工具內容（沿用 R2-2 的既有先例）
- 全新安裝不受影響：那時套件層 `.env` 由這次安裝建立，只有一個提交點

**仍然要寫下來的語意限制**：`.env` 是所有版本共用的，所以
**「丟掉這一版」還原的是程式碼，不是設定。** 你手動改過的環境變數不會跟著回去。

### 執行

- **廣告的當下記住 `<vid>`**，連同那一版的規格一起
- **呼叫的時候直接跑那一版**，不再去讀 `current`

中途發生的修訂不影響進行中的對話——下一次對話才會拿到新版。

**唯一的例外是你在對話進行中親手丟掉那一版**（第 9 節）。廣告不是執行，所以那段期間沒有
任何 identity 登記，discard 的延後判定看不到它。這是**明示接受**的：後果是模型呼叫那個
工具時得到一個明確的拒絕（「這個版本已被丟棄」），而那是你幾秒前自己做的動作。第 15 節
R7-1 那一列因此帶著這個限定，不是無條件的保證。

不引入 reservation／refcount，理由是第 2 節的比例原則：要涵蓋的是「操作者在自己啟動的 AI
工作進行中丟掉版本」，代價是一次工具呼叫失敗，而 refcount 要處理租約到期、工作異常結束、
跨行程存續等一整套問題。

### 列表

`list_tools` 對每個套件**只解析一次 `current`**，規格與總結都從**同一個**版本目錄讀。
現行 R9-2 的修法成立正是因為 spec 與 status 共用同一個 `scan.directory`
（`tools.py:2529`、`:2600`）；分層之後若各自解析一次，會出現「規格來自 A、總結來自 B」的
撕裂列，而且因為 A 永久保留，對 A 的 identity 重驗**仍然會成功**，撕裂偵測不到。

### 刪除工具

整個 `<name>/` 移除；延後判定依第 4 節，要看**所有**版本目錄——`.stale-` 清掃也一樣。

## 9. 版本保留與「丟掉這一版」

**所有版本永久保留，沒有自動回收。** 一個版本只有兩種方式消失：你按「丟掉這一版」，或你
刪掉整個工具。

**「前一版」來自 `origin.json` 記下的 `previous`，不是資料夾名稱排序。** 字典序撐不住三件
事：同一秒建立的兩版由亂數尾碼決定順序、系統時鐘回撥、以及沒有欄位能區分「完整的舊版」與
「失敗留下的半成品」。vid 只當**身分**，歷史關係明白寫下來。

### 狀態轉移，順序是承重的

1. 解析 `current` 得到 V，讀 V 的 `origin.json` 得到 `previous` = P
2. **P 必須通過第 7 節的目標驗證**，而且 `P != V`。任一項不成立就回 409 並**不刪 V**
3. P 為 null（只有這一版）→ 等同**刪掉整個工具**，走現有的確認對話框
4. 發布 `current` = P，且**必須拿到 `durable=True`**（第 7 節）
5. **然後才**刪除 `versions/V/`（有東西在跑就延後）

第 2 步是第三輪 finding 6：具體情境是你手動移除了舊版 P 的目錄或它的 `origin.json`，再在
UI 上丟掉 V——沒有這步驗證，後端會先把 `current` 指向一個不存在的版本，再刪掉唯一還能用的
V，套件立刻整個 invalid。手改資料造成 `P == V` 時更糟：寫回 V 再刪掉 V，直接做出懸空指標。

第 4、5 步的順序加上 `durable` 要求是第三輪 finding 7：先改指標再刪目錄，所以任何一步中斷
都**不會留下懸空的 `current`**；最壞的殘留是一個沒人指向的版本目錄，不影響任何讀取端。

### API 與身分

**`DELETE /api/tools/{name}/versions/{vid}`**。現行刪除只用名稱定址
（`routers/tools.py:238`、`ToolsPage.jsx:1508`），沿用會讓「畫面顯示 A、你按確認、伺服器
刪掉 B」變成可能。把 vid 放進路徑是零成本的，而且它擋掉的主要不是併發，是**畫面過期**。

**`current_vid` 一旦存在，就必須成為前端的列身分。** 這不是重提裁決紀錄 #7——是 #7 自己
寫下的觸發條件發生了：#7 明訂「若日後 `GET /api/tools` 加上安裝時間戳或 id，
`toolInstanceKey` 應改用它，屆時 row/cache/job/ledger 四個消費端會自動一起收斂」。現行前端
用 `name + description` 當代理，程式註解自己說那只是因為 API 沒有真實身分
（`toolSummary.js:82`、`:102`）。新的觸發情境比 #7 原本的還普通，**單一分頁就會發生**：
你在 V 的欄位打了修訂意見還沒送出 → 丟掉 V 退回 P → P 的 description 跟 V 相同（修訂常常
不改 description）→ row 不 remount，草稿存活 → 你按送出，寫給 V 的意見拿去修訂 P，並花掉
一場建置。所以：

- `GET /api/tools` 增加 `current_vid` 與 `has_previous`
- `toolInstanceKey` / summary cache key / job ledger 四個消費端**一起**改用 `current_vid`
- 版本相關的請求（revise、regenerate、discard）都帶 expected vid，不符回 409

`has_previous` 是前端寫出正確確認文案的必要資訊（「退回前一版」還是「刪掉整個工具」）。
這**不等於**加版本清單 UI。

### 兩種 409 要分得開

- **vid 不符**（畫面過期）→ 前端必須**重抓列表並 remount 該列**，否則畫面還是舊 vid，
  再按一次還是失敗。現行刪除失敗只關 modal 顯示訊息、不重抓（`ToolsPage.jsx:817`）
- **全域名額忙碌** → 保留操作，讓操作者稍後再試

兩者用**不同的結構化錯誤碼**，不要讓前端解析訊息文字。

### 沒有生效版本的列長什麼樣

`current` 壞掉時套件仍要以**可行動的 invalid 列**出現，但這時沒有可合法讀取的 manifest，
也就沒有 description。現行 `ToolSummary.description` 是必填字串（`schemas.py:516`）。所以：

- `description` 對這種列改為可為 null，前端顯示錯誤原因而不是描述
- `current_vid` / `has_previous` 為 null / false
- 這種列只允許「刪除工具」，不允許開關、修訂、重新產生

### 磁碟成本

每一版是工具程式碼的完整副本，通常幾 KB。憑證不在版本裡，而且安裝時的內嵌秘密掃描會擋掉
把憑證寫進程式碼的版本，所以保留全部版本**不會**讓秘密多曝露一份。

## 10. 移除「定版」

**`finalized` 整個拿掉**，連同 409 `tool_finalized`、`PATCH /api/tools/{name}/summary`、
兩道前置閘、換裝前的重讀、`StoreRefusal.FINALIZED`、以及前端「定版／解除定版」兩顆按鈕和
它們背後那套不對稱閘門規則。

**第一個用途**（保護可變的總結）消失：總結屬於版本，安裝和修訂都只寫進**新**版本。

**第二個沒寫在名字上的用途**是中止一場進行中的修訂（`tool_builder.py:2253`）。新版面下
建置全程在暫存區，取代它的是**「丟掉這一版」**。

**已知且明示接受的語意差額**（裁決紀錄 #10）：舊閘門的語意是「這一版永遠不會上線」，新做法
是「先上線但退得回去」。接受的理由是**對照組不是舊閘門而是今天的實際行為**：今天若你沒有
在建置中途按下定版，修訂完成後**舊實作就被刪掉了**，連退路都沒有。

**「重新產生總結」保留。**

## 11. 手改仍然被接住

你手動編輯版本目錄裡的工具檔案仍然是**支援的行為**（D21）。「不可變」是**後端自己的操作
之間**的約定，不是對你強制的性質。

現行的「對話中途 `tool.json` 被改過就拒絕執行」保留不變。**範圍要說清楚**：
`package_identity` 只 lstat `tool.json`（`tools.py:2637`）。你改 `run.py` 而不動 `tool.json`
時，實作變了但身分沒變，**這道檢查不會拒絕**，而且該版的 `summary.json` 仍在描述改之前的
實作。這是 D21 下刻意的取捨，但它是第 15 節兩列宣稱的**限制條件**。

手改也會製造第 9 節第 2 步要擋的狀態（刪掉舊版目錄或它的 `origin.json`），那不是攻擊，是
支援的工作流程的正常後果——所以擋在 discard 而不是禁止手改。

## 12. 併發

**全域一次一個工作維持不變**（`_admit_job`）。安裝、修訂、同步重新產生總結，**以及「丟掉
這一版」**共用一個名額。

理由有兩個：

1. 兩場修訂**同一個工具**時，`current` 是會被覆蓋的暫存器——兩次原子寫入都會成功，後寫的
   蓋掉先寫的。
2. **AI 日誌的歸屬**：後端問的是「這個工作流程最新的一筆」而不是「我這次產生的那一筆」。
   兩場同工作流程的 session 並行時答案會變成隨機。這是裁決紀錄 #3 已接受的殘留，而它可以
   被接受**正是因為**全域一次一個讓它幾乎不可能發生。

放寬成「每個工具一次一個」會解決 (1) 但讓 (2) 從「幾乎不可能」變成「同時修兩個工具就會
發生」。**要並行時的正確順序是先把日誌歸屬修對**，而不是先放寬。

一般的 AI 對話**不**受這個名額限制（它們不是建置類工作），這是刻意的，也是第 10 節那個
語意差額與第 8 節「廣告後被丟掉」的來源。

## 13. `origin.json` 與 `summary.json` 的寫入契約

現行的 `write_tool_meta` 是側檔的**唯一收口**：固定 schema（不序列化呼叫端給的 dict）、
秘密遮蔽、大小上限、原子寫入，而且**遮蔽失敗就整個不寫**。把 origin 拆成獨立檔案**不得**
把這些丟掉。

- 兩個檔案都走**同等**的 typed / bounded / sanitized / fail-closed / atomic publisher
- **來源網址在捕捉當下就降級成無憑證的 provenance**（現行行為，不變）
- `origin.json` 裝著來源、**你的修訂意見**（自由文字，要過遮蔽）與 **`previous` vid**
- `origin.json` 在 rename 之前就要在 shell 裡（第 8 節），所以失敗只是丟掉暫存；
  `summary.json` 失敗只是沒有總結

## 14. 遷移

一次性離線腳本，操作者手動執行，執行時沒有服務在跑。

### 全有全無

**腳本要嘛把整個 tools 目錄遷移完成，要嘛讓它維持原狀。** 這不是保守，是第 6 節刪掉 legacy
fallback 的**前提**：只要允許部分遷移，就會有「舊扁平套件沒有 `current`、新 reader 又不再
讀 manifest `enabled`」的套件，它失效且沒有離開那個狀態的路徑。

做法是**先跑一次唯讀的預檢**，走訪每一個套件，把所有問題一次列給操作者；**全部可遷移才
開始寫**。預檢要判定的：

- `.afterthread-state.json` 的三種語意（D41，`tools.py:662`）：**OURS**（`enabled` 搬進新的
  `state.json`）、**FOREIGN**（開關退回 manifest legacy 欄位，原檔當工具內容搬進版本，一個
  byte 都不動）、**UNREADABLE**（報告，不猜）
- `.ai_meta.json` 的三種狀態，見下
- 套件已經有 `versions/` 或 `.afterthread.meta/` 而且**沒有我們的標記** → 那是操作者自己的
  東西，報告，不自作主張

### `.ai_meta.json`：缺席才是常態

summary sidecar **從未出貨**，所以「沒有 `.ai_meta.json`」是**最常見**的狀態，不是例外。
第二版只寫了「有的話把 origin 拆出來」，於是照字面實作會讓遷移寫出一個指向**未提交版本**的
`current`，新讀取端立刻判 invalid——整個 tools 目錄一次全滅。三種狀態都要有規則：

| 狀態 | 做法 |
|---|---|
| **缺席**（常態） | 合成一份合法的最小 `origin.json`（來源標成「遷移前既有」，`previous: null`） |
| **合法** | origin → `origin.json`，總結 → `summary.json`，`previous: null` |
| **讀不到／解析不了** | 原 bytes 保留，**停下來報告**——它是 origin 的唯一副本 |

### 每個套件的交換，用確定性的兄弟名字

第二版寫「舊的 rename 到 `.stale-` 前綴」，第三輪 finding 11 指出那有一個**無法續跑的
空窗**：先 rename 舊的、再 rename 新的，中間當機就沒有任何東西叫 `<name>`，而隨機 token
讓第二次執行認不出這是哪一場交易。

改用**確定性名字**，名字本身就是日誌：

1. `os.rename(shell, <name>.at-migrated)`
2. `os.rename(<name>, <name>.at-premigrate)`
3. `os.rename(<name>.at-migrated, <name>)`
4. 刪除 `<name>.at-premigrate`

重跑時看兄弟名字就知道停在哪一步，而且每一步都可以直接續做或回退。這兩個名字**不是**
`.stale-` 前綴，所以萬一操作者誤啟動服務，既有的 stale 清掃不會把它們當可回收殘骸收走。

- **已經是新版面**（有我們標記的 `.afterthread.meta/state.json`）→ 跳過。第二次執行是
  no-op，不是錯誤
- **任何一個套件失敗** → 用兄弟名字把已經換好的全部回退，非零離開
- 開始寫之前**先完整備份整個 tools 目錄**，文件寫明位置、權限與成功後的處置

manifest 裡的 legacy `enabled` 在讀完之後**從 `tool.json` 移除**。遷移後
`_STATE_PUBLISH_LOCK` 可以刪除（P1 的過渡性守衛，新版面下狀態檔不在被換掉的目錄裡）。

## 15. 這個設計讓哪些既有問題不成立

**這張表的每一列都要對得起第 2 節的最後一條**：宣稱不成立而其實成立，比 bug 更糟。

| 問題 | 為什麼不成立 | 前提條件 |
|---|---|---|
| R3／R6-1 執行中套件被換走或刪除 | 子行程的 cwd 是不可變的版本目錄 | **`delete_tool` 與 `.stale-` 清掃都要以所有版本目錄的 identity 判定**（第 4 節）——照現行程式碼沿用，兩者都會對不到 inode |
| R7-1 掃描→建 handler 的身分配對 | 廣告當下綁定 `<vid>`，執行時跑那一版 | 「不可變 + 不自動刪除 + 廣告當下綁定」**三件事一起**；**且手動 discard 是明示的例外**，那次呼叫得到定義好的拒絕（第 8 節） |
| R9-2 `list_tools` 撕裂的列 | 規格與總結來自同一個版本目錄 | **列表對每個套件只解析一次 `current`**（第 8 節） |
| R8-1 origin 永久遺失 | `origin.json` 在 rename 之前就在版本裡 | 遷移對 `.ai_meta.json` 的三種狀態都要有規則（第 14 節） |
| P1 r1-1 修訂覆蓋剛完成的切換 | 狀態檔不在被換掉的目錄裡 | — |
| 裁決 #9 修訂吞掉手改的狀態檔 | 同上 | — |
| **後端造成的**「總結描述的是另一個實作」 | 總結屬於版本 | **只限後端造成的錯配**；手改 `run.py` 之後總結仍會過期（第 11 節） |
| 修訂只有一個提交點 | 修訂不再發布 `.env`，只發布 `current` | 取消 builder 出貨 `.env` 的能力（第 8 節） |

**不會**因此消失：

- v4 R9-1 日誌編號跨行程重用（llm_log 的問題，與版面無關）
- 操作者手改造成的中途變動與總結過期（刻意保留，第 11 節）
- 裁決 #5（能替換 tools root 的人已有服務的 uid）
- 裁決 #3 的日誌歸屬（第 12 節）
- 裁決 #10 的語意差額（第 10 節）
- 廣告後被手動 discard 的那次呼叫失敗（第 8 節，明示接受）

## 17. 交付單位

**P2 與 P3 是同一個不可分割的交付與 review 單位。** P2 先移除定版時，版面仍是扁平的、修訂
仍整包換掉並刪除舊實作，而「丟掉這一版」要到 P3 才存在——中間那個狀態**既不能中止也不能
回復**，比現況差。已查證換裝前那道閘門（`tool_builder.py:2253`）就是中止能力本體。

| 內部順序 | 範圍 |
|---|---|
| 先 | 移除「定版」（後端 + 前端）。純刪除，不動版面 |
| 後 | 版本版面 + 遷移腳本 + 「丟掉這一版」 + 前端身分改用 `current_vid` |

review 對整段範圍一次進行。

## 18. 剩下的不確定

1. **遷移腳本的初始 `<vid>` 從哪來**：既有套件沒有可靠的建立時間。傾向用一個固定的初始
   vid，反正遷移後每個工具只有一版，lineage 從 `previous: null` 開始就對了。
2. **前端「丟掉這一版」的確認流程**：`has_previous` 為 false 時等同刪除工具，需要讓你清楚
   知道按下去會發生什麼，但又不該每次都跳一樣的重量級警告。
3. **取消修訂出貨 `.env` 之後的操作者體驗**：新版需要新的環境變數時，工作結果要能清楚說出
   「請把 X、Y 加進 `<name>/.env`」，而那份清單要從哪裡來（builder 的 `.env` 已被丟棄，
   所以要在丟棄前把 key 名抽出來，且**只留 key 不留 value**）。
