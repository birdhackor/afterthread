# web-v5 設計：不可變版本 + 指標切換

本文件是 web-v5 的**設計本體**。`docs/web-v5-plan.md` 是最初的計畫，其設計章節已被本文件
取代（保留它是為了追溯「當初打算怎麼做、後來為什麼不是」）。已完成的 P1 的裁決在
`docs/web-v5-decisions.md`（D41 及其五個 review 附錄）。

## 1. 要解決什麼

v4 的 overall review 跑了九輪、33 個 finding，全部是同一個類別的實例：

> **可變的路徑就是身分。** 名稱 → 路徑 → *此刻*擺在那裡的東西。

於是每一個跨時間的操作都要自己問一次「它還是原來那個嗎」，每多一個這種操作就多一個競態。
P1 已經拆掉其中一個根因（開關就地改寫 manifest）。本設計拆掉另一個，也是比較大的那個：
**套件的內容會被原地換掉**。

## 2. 版面

```
<tools_dir>/<name>/
    .afterthread.meta/          # 套件層 meta：後端的，工具不得碰
        state.json              #   { "afterthread": "...", "enabled": bool }
        current                 #   目前生效的 <vid>
    versions/<vid>/             # 一個版本，發布後工具檔案不再變動
        .afterthread.meta/      #   版本層 meta：後端的
            summary.json        #     這一版的 AI 總結（人類看的）
            origin.json         #     這一版是從什麼做出來的
        tool.json               #   以下都是工具自己的東西
        run.py …
    .env                        # 你的憑證；跨版本存活
```

### 一條規則，套在每一個共用目錄

**`.afterthread.meta/` 裡面的是後端的，其餘都是工具的。**

這條規則在兩個層級都成立，因為兩個層級都是「我們跟工具共用同一個資料夾」：`<name>/` 底下有
工具的 `versions/`，`versions/<vid>/` 底下有 AI 寫的程式碼。P1 review r5 那個 P1 的教訓就是
**不要在別人的目錄裡宣告單一檔名**——一個工具完全可能自己就有一個 `.state.json`。

實作上這條規則取代掉現行的三套機制：逐檔名的保留清單、每層級的比對規則、以及檔案內容裡的
所有權標記。builder 的指示會明確寫「這個資料夾是後端的，不准建立、不准修改」。

### 什麼放哪一層

| 版本層（跟著這一版生死） | 套件層（跨版本存活） |
|---|---|
| `summary.json`——描述**這一版的程式碼** | `state.json` 的 `enabled`——你關的是這個工具 |
| `origin.json`——來源網址、當初指示、這次的意見 | `current`——哪一版生效 |
| 產生這一版的 AI session 編號 | `.env`（不在 meta 裡，見下） |

`.env` **不進 meta 資料夾**，維持在 `<name>/.env`：它不是後端寫給自己看的東西，是**你會手動
編輯的憑證**，而且 v0.3.0 已經出貨在那個路徑上。這剛好也界定了 meta 的意思——
**meta 是「後端自己寫、自己讀、你不用管」的東西**。

## 3. 「不可變」的精確說法

> **工具的檔案在發布後不再變動；`.afterthread.meta/` 在發布後短時間內才寫完，之後也不再變。**

總結要跑一趟 LLM 才生得出來，所以它必然晚於發布。這不是漏洞，是把規則講清楚——對應到的可見
行為是「安裝完成後，總結晚幾秒才出現」。

`origin.json` **是發布的一部分**（來源在發布當下就完全已知），所以 v4 R8 那個「origin 可能
永久遺失」的問題連窗口都不存在。

## 4. 生命週期

**安裝**：建置 → 驗證 staging → 產生新 `<vid>` → 把 staging 移進 `versions/<vid>/` →
寫 `origin.json` → 寫 `state.json`（`enabled: true`）→ 寫 `current` → 之後產生 `summary.json`。

**修訂**：讀目前版本 → 建置 → 驗證 → 產生新 `<vid>` → 移進去 → 寫 `origin.json`
（含這次的意見）→ **切換 `current`** → 之後產生 `summary.json`。**舊版本原地不動。**

**執行**：讀 `current` → 得到 `versions/<vid>/` → 從那裡執行。拿到版本路徑之後，那個目錄的
內容**保證不會變**，所以不需要再問「還是同一包嗎」。

**刪除**：整個 `<name>/` 移除（有東西在執行就照現行做法延後）。

**回收**：不是 `current`、且沒有任何執行中的呼叫指向它的版本，可以刪除。

## 5. 移除「定版」

**`finalized` 整個拿掉。**

它原本存在的理由是「總結是可變的、而且屬於工具，所以需要一個旗標說別動它」。總結一旦屬於
版本且不會被蓋，這個旗標就沒有工作可做了——**安裝寫進新版本的資料夾，修訂寫進新版本的資料夾，
從來不會碰到舊版本**。

新的模型是：**每一版生下來就固定，你隨時可以生一版新的取代它。**

會一起消失的東西（目前散在 8 個檔案約 240 處）：

- `finalized` / `summary_status` 狀態本身，以及 `PATCH /api/tools/{name}/summary`
- 409 `tool_finalized` 錯誤碼與它的兩處前置閘、`StoreRefusal.FINALIZED`
- 修訂進場前與換裝前的兩道「已定版就拒絕」檢查
- 「定版時剛好有一個總結在生成」那個 TOCTOU 守衛
- 前端的「定版／解除定版」按鈕，以及它們背後那套不對稱閘門規則
  （可以定版、但永遠可以解除定版）

**「重新產生總結」保留。** 總結是**寫給人看的**（`tool.json` 的 `description` 才是給模型看的），
所以它寫得不好不會讓工具行為出錯。而且新模型下唯一會覆蓋某一版總結的路徑，只剩下你自己按那顆
按鈕——沒有自動覆蓋的路徑，就沒有需要防的東西。

## 6. 這個設計讓哪些既有問題不成立

| v4／v5 找到的問題 | 新設計下 |
|---|---|
| R3／R6-1 執行中套件被換走或刪除（子行程改道） | 子行程的 cwd 是不可變的版本目錄 |
| R7-1 掃描→建 handler 的身分配對 | 版本目錄內容不會變，不需要配對 |
| R9-2 `list_tools` 撕裂的列 | 同上 |
| R8-1 origin 永久遺失 | origin 是發布的一部分 |
| P1 r1-1 修訂覆蓋剛完成的切換 | 狀態檔不在被換掉的目錄裡 |
| 裁決 #9 修訂吞掉手改的狀態檔 | 同上 |
| 「總結描述的是另一個實作」 | 總結屬於版本 |

**不會**因此消失、仍需各自處理：

- v4 R9-1 日誌編號跨行程重用（llm_log 的問題，與版面無關）
- 操作者手改**版本目錄裡**的工具檔案造成的中途變動（刻意保留現行「拒絕」行為）
- 裁決 #5（能替換 tools root 的人已有服務的 uid）

## 7. 遷移

需要處理**兩種**既有狀態：

1. **v0.3.0 出貨的扁平版面**：`<name>/tool.json`（`enabled` 在裡面）+ 實作檔 + `.env`。
2. **本分支 P1 之後的狀態**：同上，外加 `<name>/.afterthread-state.json`。

`.ai_meta.json`（總結側檔）**從未出貨**——它是本次 session 的 P3a 才建的（`dcd2aef`，
2026-07-26），而 v0.3.0 是 2026-07-23 打的標籤。所以只有分支上的開發資料會有它。

**遷移策略（本設計最不確定的一點，見第 9 節）**：目前傾向**讀取端同時看得懂兩種版面**，
遇到扁平版面就當作「只有一個版本、`current` 指向它」，第一次寫入（安裝／修訂／切換開關）
時才真的建立新版面。理由是讀取路徑永遠不寫入、啟動時不做任何 migration pass——與 P1 的
fallback 同一個體例。

## 8. 對外契約的變化

- `GET /api/tools` 的列不再有 `summary_status`
- `PATCH /api/tools/{name}/summary` 消失
- `GET /api/tools/{name}/summary` 回的是**目前版本**的總結
- 409 `tool_finalized` 消失
- 前端「工具」頁少掉兩顆按鈕，可能多一個版本清單（見第 9 節）

## 9. 我自己最不確定的地方（請優先攻擊）

1. **遷移策略**：「讀取端雙版面」表示扁平版面的支援要活多久？永遠？還是第一次寫入就轉換、
   之後刪掉相容路徑？永遠支援等於永遠有兩條路徑要維護；一次轉換則是啟動時或首次寫入時的
   mutation，而後者的失敗處理不明顯。
2. **`<vid>` 用什麼**：要能安全當路徑元件、要能排序（回溯需要知道「上一版」）、要能在同一
   毫秒內連續建立兩版而不撞號。時間戳？uuid？單調計數器？各有代價。
3. **回收的精確條件**：「沒有執行中的呼叫指向它」要怎麼問。現行的執行登記是用目錄 inode，
   版本化之後 `<vid>` 本身就是天然的鍵——但登記的生命週期要涵蓋到「輸出遮蔽完成」而不只是
   子行程結束（v4 R4-1 的教訓）。
4. **保留幾版**：只留 `current` 和「還有人在用的」？還是留最近 N 版以便回溯？留越多，
   `.env` 裡的秘密散布在越多份舊程式碼旁邊（內嵌秘密掃描是 staging-only）。
5. **版本層 meta 在發布後才寫完**——這是否讓任何「這個目錄不會變」的假設變成半真？特別是
   回收與遷移的判斷。
6. **UI 要不要顯示版本歷史**：技術上現在免費（資料就在那裡），但它是新的產品表面，
   而且會帶出「可以回溯嗎」這個問題。本設計傾向先不做，只顯示目前版本。
7. **`.env` 留在套件層**是否正確：如果兩個版本需要不同的環境變數（例如新版改用不同的 API），
   單一 `.env` 會是問題。目前判斷是「不會，因為修訂是改實作不是換 API」，但這是假設。
