# web-v5 設計：不可變版本 + 指標切換

本文件是 web-v5 的**設計本體**。`docs/web-v5-plan.md` 是最初的計畫，其設計章節已被取代
（保留以追溯「當初打算怎麼做、後來為什麼不是」）。已完成的 P1 的裁決在
`docs/web-v5-decisions.md`（D41 及其五個 review 附錄）。

**修訂紀錄**：第一版經過一輪 design review（9 條 finding，6 條 P1）與一輪與操作者的討論後
重寫；第二版經過第二輪 design review（15 條 finding，11 條 P1）後再次修訂。第 16 節逐條記錄
兩輪每一條 finding 的處置。

## 1. 要解決什麼

v4 的 overall review 跑了九輪、33 個 finding，全部是同一個類別的實例：

> **可變的路徑就是身分。** 名稱 → 路徑 → *此刻*擺在那裡的東西。

P1 已經拆掉其中一個根因（開關就地改寫 manifest）。本設計拆掉另一個，也是比較大的那個：
**套件的內容會被原地換掉**。

**第二輪 review 的第一課**：本設計自己引進了一個新的「名字 → 路徑 → 此刻在那裡的東西」
——`current`，一個內容是目錄名的檔案——而第一版只寫了「切換是原子的」六個字。第 7 節是
補上的讀寫契約。**引進一個新的間接層，就要同時寫出它的契約**，否則等於把剛拆掉的毛病
換個地方養一隻。

## 2. 操作環境與嚴格度校準

本專案是**單人本機工具**，這件事是設計前提，不是免責聲明。實際環境：

- **一個操作者，通常一個瀏覽器分頁。** 沒有多使用者、沒有多租戶。
- **建置類工作要花錢且以分鐘計。** 操作者不會、也沒有動機同時開好幾場。
- **沒有敵對行為者**（D21：能改套件檔案的人已經有服務的 uid）。手改是**支援的工作流程**。
- **工具集規模是個位數到數十個**，不是數千個。

由此得到的**嚴格度校準**，適用於本設計的 review 與實作：

- **併發類的 finding 要說出一個單一操作者做得出來的實際順序**，並以**對這個操作者的後果**
  判斷嚴重性，而不是以理論上的可達性。「兩場修訂交錯」若需要操作者同時開兩個分頁各按一次
  且時間差在毫秒級，那是低嚴重性。
- **修法要與嚴重性成比例。** 如果一個併發缺口用「把這個操作加進既有的單一名額」就能關掉，
  那就關掉（成本是一行）；如果要引入新的鎖、租約、引用計數或協定，先問值不值得。
- **但這個折扣不涵蓋三類問題**，它們與併發無關，一律照原本的嚴格度處理：
  1. **正確性**——同一個問題在兩處會得到兩個答案、或某個函式被餵了錯的東西卻不會報錯。
  2. **失效復原**——當機、中斷、寫入失敗之後留下的狀態，以及有沒有路徑離開那個狀態。
  3. **資料遺失**——尤其是憑證與 origin 這種**唯一副本**。
- **「不成立」的宣稱不打折。** 一條宣稱某類問題不再可達的敘述，錯的時候比一個 bug 更糟，
  因為它會讓後續的 review 不再看那一塊。第 15 節的每一列都要對得起這個標準。

## 3. 版面

```
<tools_dir>/<name>/                 # 整個目錄是後端管的
    .afterthread.meta/              #   後端的：這個工具「現在」的狀態
        state.json                  #     { "afterthread": ..., "enabled": bool }
        current                     #     目前生效的 <vid>（契約見第 7 節）
    versions/                       #   後端的：由後端建立、命名、刪除
        <vid>/                      #     一個版本
            .afterthread.meta/      #       後端的：這一版的資料
                origin.json         #         來源、修訂意見、前一版（＝已提交標記）
                summary.json        #         這一版的 AI 總結（人類看的）
            tool.json               #       以下是工具自己的東西
            run.py …
    .env                            #   你的憑證，跨版本存活
```

### 所有權規則

第一版的規則寫「`.afterthread.meta/` 是後端的，其餘都是工具的」——**那是錯的**，因為
`versions/` 也是後端建立、命名、刪除的。正確的講法要分兩層：

- **套件層 `<name>/`**：整個目錄由後端管。`.afterthread.meta/` 與 `versions/` 都是後端的；
  `.env` 是**操作者的**（你會手動編輯，而且 v0.3.0 已出貨在這個路徑）。工具的檔案在這一層
  **一個都沒有**——它們全都住在某一版裡面。
- **版本層 `versions/<vid>/`**：`.afterthread.meta/` 是後端的，**其餘全部是工具的**。

這條界線的意義是：**工具（和產生它的 builder session）只在版本層裡活動，而後端在版本層只
佔用一個名字。** P1 review r5 的教訓——不要在別人的目錄裡宣告單一檔名——在這裡的落實方式是
只宣告一個目錄名，而且只在工具真正會寫東西的那一層宣告。

### 「不准碰」不是強制力

builder 的指示會寫明保留名稱，但**指示不能取代檢查**——builder session 有 shell，寫得出
任何東西。現行的 `_strip_builder_sidecars` 之所以存在就是這個理由，它必須繼續存在，只是
比對對象從一組檔名改成「staging 根目錄下的 `.afterthread.meta/`」（staging 根目錄就是未來的
版本根目錄）。

## 4. 兩個目錄錨點：哪個函式拿到哪一個

今天全系統只有一個「套件目錄」，所有東西都在裡面。分層之後有**兩個**錨點，而第一版設計
從頭到尾把它們當成一個概念——這是第二輪最有殺傷力的 finding，因為餵錯目錄**不會報錯，
只會安靜地答錯**：拿版本目錄去讀 `.env` 會讀不到憑證並忽略開關，拿套件目錄去跑會找不到
`run.py`。

**規則：不留任何一個叫 `directory` 而語意含糊的參數。** 引入一個小的解析結果
`ResolvedPackage(package_root, version_root, vid)`，兩個成員是**不同型別**（同 D40 r5 讓兩種
identity 有不同 shape 的手法），餵錯是型別錯誤而不是執行期的錯答。

| 既有函式 | 拿哪一個 | 為什麼 |
|---|---|---|
| `package_enabled` / `_read_enabled_state` | package_root | 開關是工具的，不是某一版的 |
| `_read_manifest_object` / `_scan_package` 的 manifest 讀取 | version_root | 規格屬於版本 |
| `package_identity`（`tool.json` 的 inode） | version_root | 同上 |
| `_load_tool_dotenv` / `_env_values_for_package` | package_root | 憑證跨版本存活 |
| 安裝時的 `.env` 大小閘 | package_root | 同上 |
| `_run_tool_subprocess` 的 cwd | version_root | 工具跑自己那一版的檔案 |
| `directory_identity`（執行中保護的登記） | version_root | 子行程實際跑在這裡 |
| `delete_tool` 的延後判定 | **每一個** version_root | 見下方，這是一個已確認的缺陷 |
| `read_tool_meta`（總結） | version_root 的 `.afterthread.meta/` | 總結屬於版本 |
| `.stale-` 殘骸清掃 | tools_dir 層 | 不變 |
| `validate_package` | staging root（＝未來的 version_root）；`.env` 大小閘看 package_root | |
| `tool_meta` 的檔案 inventory | version_root | |
| `tool_meta` 的 `.env` key 讀取 | package_root | |

### 已確認的缺陷：刪除的延後判定會對不到 inode

已對程式碼查證：handler 登記的是**子行程實際執行的那個目錄**的 identity
（`tools.py:3993`），而 `delete_tool` 查的是**被 rename 的套件根目錄**的 identity
（`tools.py:4357`）。今天兩者是同一個目錄所以對得上；分層之後子行程跑在 `versions/<vid>/`
而刪除查 `<name>/`，**兩個 inode 不相等**，於是「沒人在跑」的判定為真，`rmtree` 直接執行，
正在跑的子行程之後開檔案得到 ENOENT。

而且同一個工具可能同時有數個舊 vid 正在執行（廣告當下綁版本，見第 8 節）。所以：

- **刪除整個工具**：要對該套件**所有**版本目錄的 identity 做延後判定，任一個在執行就延後。
- **丟掉某一版**：只看**那一版**的 identity。

這一條同時是第 15 節 R3／R6-1 那一列成立的**前提**，不是實作細節。

## 5. 三層可變性

第一版寫「發布後不再變」，同時又保留「隨時可以重新產生總結」——自相矛盾。正確的講法是三層：

| 東西 | 什麼時候固定 |
|---|---|
| 版本裡的**工具檔案** | 發布後後端不再修改（你手動改仍然可以，見第 11 節） |
| `origin.json` | **在提交那一刻就已經在裡面**，之後不再修改（見第 8 節的組裝順序） |
| `summary.json` | **可以隨時整份原子替換**（總結晚於發布才生得出來，而且你可以按「重新產生」） |

這個區分是承重的：任何「這個目錄還會不會變」的判斷都要看它問的是哪一層。

## 6. `.afterthread.meta/` 的合法狀態

半完成的 meta 目錄是**當機與寫入失敗的正常產物**，不是異常輸入。每個讀取端都要有明確答案。

### 套件層 `<name>/.afterthread.meta/`

| 狀態 | 判定 |
|---|---|
| 目錄不存在 | 套件 **invalid**，列出可行動的錯誤（遷移後不該出現） |
| `current` 缺、壞、或指不到一個完整版本 | 套件 **invalid，不啟用、不執行**（第 7 節，fail closed） |
| `state.json` 缺 | **視為 disabled** |
| `state.json` 是別人的（FOREIGN） | 同 P1 已定語意：視為缺，且**永不覆寫、永不刪除** |
| `state.json` 讀不到（UNREADABLE） | fail closed，視為 disabled |

**`state.json` 缺席的預設必須從現行的 `true` 翻成 `false`。** 已查證 `_effective_enabled`
（`tools.py:757`）：狀態不是我們的、manifest 又讀不到時回傳 `True`。今天沒事，因為套件層
一定有 `tool.json` 可讀；新版面下**套件層沒有 `tool.json`**，legacy fallback 會拿到
`manifest=None` 而回答 `True`——於是一個只寫到一半的 meta 目錄會**把工具自己打開**。

修法不是加特例，而是**刪掉整條 legacy fallback**：遷移之後不存在任何 legacy 套件（第 14
節），manifest 裡的 `enabled` 不再是任何答案的來源。缺席即 disabled，只有一條規則。

### 版本層 `versions/<vid>/.afterthread.meta/`

| 狀態 | 判定 |
|---|---|
| `origin.json` 在 | 這一版**已提交**——它同時就是提交標記 |
| `origin.json` 缺或壞 | 這一版**未提交**：不可被 `current` 指向、找前一版時跳過、可被清理 |
| `summary.json` 缺 | **正常**（總結晚於發布） |
| `summary.json` 壞 | 視為沒有總結（沿用現行 `read_tool_meta` 的 total 語意） |

讓 `origin.json` 兼任提交標記是刻意的：一個檔案同時回答「這一版完成了嗎」與「它的前一版是
誰」，不需要第二個標記檔，也不會出現兩個標記互相矛盾的狀態。

## 7. `current` 的讀寫契約

`current` 是整個設計的唯一提交點，所以它需要與第 13 節同等明確的契約。**沒有這一節，
`current` 就是本設計號稱要消滅的那個毛病的新實例。**

**vid 的語法**：`20260728T134501Z-a3f9c1`——UTC 時間戳 + 六位小寫 hex，正規式
`^[0-9]{8}T[0-9]{6}Z-[0-9a-f]{6}$`。這個語法**不含路徑分隔符也不含點**，所以
`../../.staging/<uuid>` 這種內容是**語法錯誤**而不是需要另外做包含性檢查的東西——把穿越
變成不可表示，比事後檢查便宜也可靠。

**讀**：

- 用現行的有界讀取器（`O_NOFOLLOW` + `S_ISREG`），上限 64 bytes；symlink、非一般檔案、
  超長一律拒絕
- 內容去掉尾端換行後必須**恰好**符合 vid 語法；空檔案是錯誤
- `versions/<vid>/` 必須存在、是**真的目錄**（非 symlink）、且**已提交**（第 6 節）
- 任何一項不成立 → **這個套件沒有生效版本**：invalid、不列為可用、不廣告、不執行。
  **不猜、不 fallback 到最新的一版**——猜就是同一個毛病

**寫**：走與側檔相同的原子發布器（在 `.afterthread.meta/` 內 mkstemp → fchmod → write →
fsync → `os.replace` → fsync 目錄）。`os.replace` 不會留下半個檔案，所以**寫失敗時舊值
完好且仍可讀**，工具維持在舊版而不是掉進「沒有生效版本」。

## 8. 生命週期

### 組裝與提交的共同形狀

安裝與修訂都遵循同一個形狀：**在暫存區組出完整的東西（含 `origin.json`），然後一次
rename**。這讓「未提交」的狀態幾乎不會落到磁碟上的正式位置。

**暫存位置**：`<tools_dir>/.staging/<uuid>/` 底下再分 `build/`（builder 的工作區）與
`shell/`（組好的成品）。三個理由：

1. **同一個檔案系統**。現行程式碼把「staging 在 `<tools_dir>` 底下、target 也在」寫成
   *結構性*保證而不是期望（`tool_builder.py:2188`），rename 才不會 EXDEV。組裝位置放到
   系統 temp 就會踩到，改用 `shutil.move` fallback 則原子性直接沒了。
2. **殘骸有人收**。現行 `_cleanup_staging` 認的是 `.staging/<uuid>/`，成品放在它底下就
   **自動被既有清掃涵蓋**，不需要第二套回收機制。
3. **成品含 `.env`**。無人管理的殘骸等於憑證多留一份在磁碟上——這是第 2 節列的「資料遺失」
   類，不打折。

**佔名**：最後一步不是直接 rename，而是先 `os.mkdir(<tools_dir>/<name>)` 作為**排他建立**
（名字被任何東西佔用就 EEXIST，原子），成功之後才 `os.rename(shell, <name>)`——POSIX 允許
rename 到一個空目錄上，而那個空目錄正是我們剛建的。這樣不會覆蓋掉任何既有內容。

### 全新安裝

1. builder 在 `.staging/<uuid>/build/` 建置（現行行為，不變）
2. 驗證（現行行為，不變）
3. 在 `.staging/<uuid>/shell/` 組出**完整**的套件：
   - `versions/<vid>/` ← build 的內容
   - `versions/<vid>/.afterthread.meta/origin.json`（`previous` 為 null）
   - `.afterthread.meta/state.json`（enabled 的初始值）與 `.afterthread.meta/current`
   - 把 build **根目錄**的 `.env` 拉到 shell 的**套件層**
4. `mkdir <name>` 佔名 → `os.rename(shell, <name>)` ← **這一刻才叫安裝完成**
5. 之後產生 `summary.json`

第 4 步之前 `<name>/` 完全不存在，所以任何一步失敗都只是丟掉暫存的東西，**不會留下一個
佔著名字又修不好的目錄**，也不會留下沒人收的憑證。

### 修訂

1. builder 在 `.staging/<uuid>/build/` 建置（不變）
2. 驗證（不變）
3. 在 `.staging/<uuid>/shell/` 組出**一個版本目錄**的內容：build 的內容 +
   `.afterthread.meta/origin.json`（含這次的意見，`previous` = 目前的 vid）
4. `os.rename(shell, <name>/versions/<vid>)` ← vid 是新的，名字必然空著
5. **發布 `current`** ← **這一刻才叫修訂完成**
6. 之後產生 `summary.json`

第 5 步之前新版本已經在磁碟上而且是**完整已提交**的，但沒有任何東西指向它，所以它是惰性的。
`current` 是唯一的提交點。

### 修訂與 `.env`

第一版設計完全沒寫這一段，而現行程式碼在修訂路徑上**已經**對 `.env` 有明確行為
（`tool_builder.py:1978`、`:2012`）：本來有就保留 live bytes，本來沒有則 builder 做的那份
可以出貨（要過同一道政策閘）。搬到新版面之後：

- 那套邏輯**原封不動**，只是作用對象變成**套件層**的 `<name>/.env`
- build 根目錄的 `.env` 一樣走 hoist，適用同一道政策閘
- 版本內**巢狀**的 `.env` 仍然是普通的工具內容（沿用 R2-2 的既有先例）

**由此得到一個必須寫下來的語意限制**：`.env` 是**所有版本共用**的，所以

> **「丟掉這一版」還原的是程式碼，不是設定。**

新版改了 key 名或 endpoint、你再丟掉它退回舊版，舊程式碼會配到新設定。這在單人小工具的
實際使用下可接受（見第 2 節），但它是**設計的性質**而不是疏漏，操作者必須知道。第一版把
它寫在「將來的假設」裡是錯的——現行修訂**現在**就允許動 `.env`。

### 執行

工具是在一次 AI 工作**開始時**被廣告給模型的，模型可能幾分鐘後才呼叫。所以：

- **廣告的當下記住 `<vid>`**，連同那一版的規格一起
- **呼叫的時候直接跑那一版**，不再去讀 `current`

這是正確的語意：模型看到的是那一版的參數規格，跑那一版本來就對。中途發生的修訂不影響
進行中的對話——下一次對話才會拿到新版。

### 列表

`list_tools` 對每個套件**只解析一次 `current`**，規格與總結都從**同一個**版本目錄讀。
現行 R9-2 的修法之所以成立，正是因為 spec 與 status 共用同一個 `scan.directory`
（`tools.py:2529`、`:2600`）；分層之後若兩者各自解析一次 `current`，就會出現「規格來自 A、
總結來自 B」的撕裂列，而且因為 A 永久保留，對 A 的 identity 重驗**仍然會成功**，撕裂偵測
不到。這是一句話的契約，不是機制。

### 刪除工具

整個 `<name>/` 移除；延後判定依第 4 節，要看**所有**版本目錄。

## 9. 版本保留與「丟掉這一版」

**所有版本永久保留，沒有自動回收。** 一個版本只有兩種方式消失：你按「丟掉這一版」，或你
刪掉整個工具。

**「前一版」來自 `origin.json` 記下的 `previous`，不是資料夾名稱排序。** 第一版靠字典序
推論先後，那撐不住三件事：同一秒建立的兩版由亂數尾碼決定順序、系統時鐘回撥會讓後做的排
前面、以及沒有任何欄位能區分「完整的舊版」與「失敗留下的半成品」。vid 只當**身分**，
歷史關係明白寫下來。時間戳保留是為了讓你看資料夾名字就知道那一版什麼時候做的。

**「丟掉這一版」的狀態轉移**，順序是承重的：

1. 解析 `current` 得到 V，讀 V 的 `origin.json` 得到 `previous` = P
2. P 為 null（只有這一版）→ 等同**刪掉整個工具**，走現有的確認對話框
3. 否則：**先發布 `current` = P**，**再**刪除 `versions/V/`（有東西在跑就延後）

先改指標再刪目錄，所以任何一步中斷都**不會留下懸空的 `current`**；最壞的殘留是一個沒人
指向的版本目錄，那不影響任何讀取端，而且版本本來就永久保留。

**API 帶 vid**：`DELETE /api/tools/{name}/versions/{vid}`。現行刪除是**只用名稱定址**的
（`routers/tools.py:238`、`ToolsPage.jsx:1508`），沿用會讓「畫面上顯示 A、你按確認、伺服器
刪掉 B」變成可能。把 vid 放進路徑是零成本的，而且它擋掉的主要不是併發，是**畫面過期**。
不符就回 409。

**列表要多兩個欄位**：`current_vid` 與 `has_previous`。前端需要知道「丟掉這一版」是「退回
前一版」還是「刪掉整個工具」才能給出正確的確認文案。這**不等於**加版本清單 UI。

**磁碟成本**：每一版是工具程式碼的完整副本，通常幾 KB。憑證不在版本裡（`.env` 在套件層），
而且安裝時的內嵌秘密掃描會擋掉把憑證寫進程式碼的版本，所以保留全部版本**不會**讓秘密多
曝露一份。

## 10. 移除「定版」

**`finalized` 整個拿掉**，連同 409 `tool_finalized`、`PATCH /api/tools/{name}/summary`、
兩道前置閘、換裝前的重讀、`StoreRefusal.FINALIZED`、以及前端「定版／解除定版」兩顆按鈕和
它們背後那套不對稱閘門規則。

**它原本的第一個用途**是保護可變的總結。總結一旦屬於版本，安裝和修訂都只寫進**新**版本的
資料夾，永遠不會碰到舊版本——這個用途消失。

**它原本還有第二個沒寫在名字上的用途**：中止一場進行中的修訂（`tool_builder.py:2253`
在換裝前最後一刻重讀定版狀態，前端也刻意讓它在工作進行中還能按）。新版面下建置全程在暫存
資料夾，套件只有在提交那一刻才變成系統看得到的東西，所以取代它的是**「丟掉這一版」**。

**已知且明示接受的語意差額**（裁決 #10）：舊閘門的語意是「這一版永遠不會上線」，新做法是
「先上線但退得回去」。在修訂完成到你按下丟掉之間，另一場一般的 AI 工作理論上可以呼叫到
新版。接受的理由是**對照組不是舊閘門而是今天的實際行為**：今天若你沒有在建置中途按下定版，
修訂完成後**舊實作就被刪掉了**，連退路都沒有；新設計在可回復性上嚴格勝出。加上第 2 節的
環境校準（單人、要撞上必須同時在別處跑一場 AI 工作），差額可接受。完整理由與「將來什麼
情況下要重新評估」寫在裁決紀錄 #10。

**「重新產生總結」保留。** 總結是寫給人看的（`tool.json` 的 `description` 才是給模型看的），
寫得不好不會讓工具行為出錯。新模型下唯一會覆蓋某一版總結的路徑，只剩下你自己按那顆按鈕。

## 11. 手改仍然被接住

你手動編輯版本目錄裡的工具檔案仍然是**支援的行為**（D21）。「不可變」是**後端自己的操作
之間**的約定，不是對你強制的性質。

現行的「對話中途 `tool.json` 被改過就拒絕執行」保留不變：後端在廣告當下記下該版
`tool.json` 的檔案身分，執行前再取一次。差別是這道檢查現在**只回答手改這一個問題**——因為
修訂不會再原地改寫任何東西。

**這道檢查的範圍要說清楚**：`package_identity` 只 lstat `tool.json`（`tools.py:2637`）。
你改 `run.py` 而不動 `tool.json` 時，實作變了但身分沒變，**這道檢查不會拒絕**，而且該版的
`summary.json` 仍在描述改之前的實作。這是 D21 下刻意的取捨（不阻止手改），但它是第 15 節
兩列宣稱的**限制條件**，不能省略：手改之後的總結要靠你自己按「重新產生」。

## 12. 併發

**全域一次一個工作維持不變**（`_admit_job`）。安裝、修訂、同步重新產生總結，**以及「丟掉
這一版」**共用一個名額——把 discard 加進去是一行的成本，也是第 2 節「修法要與嚴重性成比例」
的示範：它關掉的是「修訂與 discard 交錯寫 `current`，後寫者讓先寫者的成功變成孤兒」。

維持全域限制的理由有兩個，第二個是第一輪 design review 挖出來的：

1. 兩場修訂**同一個工具**時，`current` 是會被覆蓋的暫存器——兩次原子寫入都會成功，後寫的
   蓋掉先寫的，其中一場「成功」的修訂等於沒生效。（不同工具各有各的 `current`，不會互相
   覆蓋，所以這個理由本身只需要「每個工具一次一個」。）
2. **AI 日誌的歸屬**：後端記錄「這一版是哪次 session 建的」時，問的是「這個工作流程最新的
   一筆」而不是「我這次產生的那一筆」。兩場同工作流程的 session 並行時，這個答案會變成隨機
   ——工具 A 的日誌連結可能開出工具 B 的建置過程。這是裁決紀錄 #3 已接受的殘留，而它可以被
   接受**正是因為**全域一次一個讓它幾乎不可能發生。

放寬成「每個工具一次一個」會解決 (1) 但讓 (2) 從「幾乎不可能」變成「同時修兩個工具就會
發生」。**等到真的需要並行時，正確的順序是先把日誌歸屬修對**（讓每次呼叫記住自己產生的
那一筆），而不是先放寬。

一般的 AI 對話**不**受這個名額限制（它們不是建置類工作），這是刻意的，也是第 10 節那個
語意差額的來源。

## 13. `origin.json` 與 `summary.json` 的寫入契約

現行的 `write_tool_meta` 是側檔的**唯一收口**：固定 schema（不序列化呼叫端給的 dict）、
秘密遮蔽、大小上限、原子寫入，而且**遮蔽失敗就整個不寫**。把 origin 拆成獨立檔案**不得**
把這些丟掉。

- 兩個檔案都走**同等**的 typed / bounded / sanitized / fail-closed / atomic publisher
- **來源網址在捕捉當下就降級成無憑證的 provenance**（現行行為，不變）：presigned query 或
  路徑裡的 token 是遮蔽比對不到的，所以直接丟掉那些部分而不是遮蔽
- `origin.json` 現在還裝著**你的修訂意見**（自由文字，同樣要過遮蔽）與 **`previous` vid**
- **`origin.json` 寫入失敗必須阻止提交**——它在 rename 之前就要在 shell 裡（第 8 節），
  所以失敗只是丟掉暫存；`summary.json` 失敗只是沒有總結，不影響已完成的安裝或修訂

## 14. 遷移

一次性離線腳本，操作者手動執行，執行時沒有服務在跑。所以**不需要**讀取端同時看得懂兩種
版面，也不需要 lazy migration。

腳本要處理的既有狀態：

1. **v0.3.0 出貨的扁平版面**：`<name>/tool.json`（`enabled` 在裡面）+ 實作檔 + `.env`
2. **本分支 P1 之後**：同上，外加 `<name>/.afterthread-state.json`
3. **本分支的 `.ai_meta.json`**：從未出貨（`dcd2aef`，2026-07-26；v0.3.0 是 2026-07-23），
   但**在 HEAD 上真實存在**，而且它裝著**唯一一份** origin 與現有的總結

### 每個套件的處理

- **`.ai_meta.json` 必須被拆進新位置**：origin → `versions/<vid>/.afterthread.meta/origin.json`
  （`previous` 為 null），總結 → 同目錄的 `summary.json`。把它當普通工具檔搬進版本，新的
  讀取端在 `.afterthread.meta/` 找不到東西，**唯一副本就沒了**——這是第 2 節列的資料遺失類。
- **`.afterthread-state.json` 有三種語意，不能只寫「有就讀」**（D41，`tools.py:662`）：
  - **OURS** → `enabled` 搬進新的 `state.json`
  - **FOREIGN**（工具自己的檔案）→ 開關**退回 manifest 的 legacy 欄位**，而原檔**當成工具
    內容搬進版本**，一個 byte 都不能動
  - **UNREADABLE** → fail closed：停下來報告這個套件，不要猜
- 工具檔案搬進 `versions/<vid>/`，`.env` 留在套件層，寫 `state.json` 與 `current`
- manifest 裡的 legacy `enabled` 欄位在讀完之後**從 `tool.json` 移除**（它從此不是任何答案的
  來源，第 6 節要刪掉整條 fallback）

### 二次執行與中斷

第一版的規則是「若套件本來就有 `versions/` 或 `.afterthread.meta/` 就停下來報告」——但
**腳本自己一開始就會建立這兩個名字**，於是它同時是停止條件也是自己的產物。一次中斷的執行
會讓第二次必然拒絕那個套件，而整個 root 此時是新舊混合的，runtime 又明定不支援雙讀。這是
邏輯上的自相矛盾，不是嚴格度問題。

修法用**與安裝同一個手法**：

- **每個套件各自原子遷移**：在 `<tools_dir>/.staging/migrate-<uuid>/` 組出完整的新版面套件，
  然後 `os.rename` 換掉舊的（舊的先 rename 到 `.stale-` 前綴，成功後再刪）。每個套件因此
  **要嘛完全是舊版面、要嘛完全是新版面**，沒有中間態。
- **可續跑**：已經是新版面的套件（有我們的 `.afterthread.meta/state.json` 且帶標記）直接
  跳過。第二次執行是 no-op，不是錯誤。
- **「停下來報告」只留給真正的撞名**：套件有 `versions/` 或 `.afterthread.meta/` 但**沒有
  我們的標記**——那是操作者自己的東西，腳本不自作主張。標記用 P1 已經建立的同一個手法
  （文件內的 ownership marker），所以「這是我們建的」與「這是別人的」可以區分。
- **先完整備份整個 tools 目錄**，並在文件裡寫明備份位置、權限，以及成功後要不要保留。

遷移後 `_STATE_PUBLISH_LOCK` 可以刪除（它是 P1 的過渡性守衛，前提是狀態檔會被換裝波及；
新版面下狀態檔不在被換掉的目錄裡，而且沒有 legacy 套件了）。

## 15. 這個設計讓哪些既有問題不成立

**這張表的每一列都要對得起第 2 節的最後一條**：宣稱不成立而其實成立，比 bug 更糟。

| 問題 | 為什麼不成立 | 前提條件 |
|---|---|---|
| R3／R6-1 執行中套件被換走或刪除 | 子行程的 cwd 是不可變的版本目錄，而且版本不會自動刪除 | **延後判定必須以版本目錄的 identity 為準，刪除整個工具要等所有版本**（第 4 節）——照現行程式碼直接沿用會對不到 inode |
| R7-1 掃描→建 handler 的身分配對 | 廣告當下綁定 `<vid>`，執行時跑那一版 | 「不可變 + 不自動刪除 + 廣告當下綁定」**三件事一起**，少任何一件都不成立 |
| R9-2 `list_tools` 撕裂的列 | 規格與總結來自同一個版本目錄 | **列表對每個套件只解析一次 `current`**（第 8 節）；各自解析會撕裂且偵測不到 |
| R8-1 origin 永久遺失 | `origin.json` 在 rename 之前就在版本裡，不依賴事後的 LLM 往返 | 遷移必須把 `.ai_meta.json` 的 origin 拆出來（第 14 節） |
| P1 r1-1 修訂覆蓋剛完成的切換 | 狀態檔不在被換掉的目錄裡 | — |
| 裁決 #9 修訂吞掉手改的狀態檔 | 同上 | — |
| **後端造成的**「總結描述的是另一個實作」 | 總結屬於版本，發布與修訂只寫新版本 | **只限後端造成的錯配**；你手改 `run.py` 之後總結仍會過期（第 11 節） |

**不會**因此消失：

- v4 R9-1 日誌編號跨行程重用（llm_log 的問題，與版面無關）
- 操作者手改版本裡的工具檔案造成的中途變動與總結過期（刻意保留，第 11 節）
- 裁決 #5（能替換 tools root 的人已有服務的 uid）
- 裁決 #3 的日誌歸屬（第 12 節）
- 裁決 #10 的語意差額（第 10 節）

## 17. 交付單位

**P2 與 P3 是同一個不可分割的交付與 review 單位。** 第一版把它們寫成兩個階段，那是錯的：
P2 先移除定版時，版面仍是扁平的、修訂仍整包換掉並刪除舊實作，而「丟掉這一版」要到 P3
才存在——中間那個狀態**既不能中止也不能回復**，比現況差。已查證換裝前那道閘門
（`tool_builder.py:2253`）就是中止能力本體。

| 內部順序 | 範圍 |
|---|---|
| 先 | 移除「定版」（後端 + 前端）。純刪除，不動版面 |
| 後 | 版本版面 + 遷移腳本 + 「丟掉這一版」 |

先刪定版的理由仍然成立（版面改動動的是簡化過的程式碼，反過來要把同一批總結相關程式碼改
兩次），但那是**內部順序**，不是兩次出貨。review 對整段範圍一次進行。

## 18. 剩下的不確定

1. **遷移腳本的初始 `<vid>` 從哪來**：既有套件沒有「建立時間」的可靠來源（mtime 會被各種
   操作推動）。傾向用一個固定的初始 vid，反正遷移後每個工具只有一版，而 lineage 從
   `previous: null` 開始就對了。
2. **前端「丟掉這一版」的確認流程**：`has_previous` 為 false 時等同刪除工具，需要讓你清楚
   知道按下去會發生什麼，但又不該每次都跳一樣的重量級警告。
3. **刪掉 legacy fallback 的時機**：第 6 節要刪掉 manifest `enabled` 這條路，前提是遷移
   已經跑過。若腳本在某個套件上停下來報告（FOREIGN／UNREADABLE／真撞名），那個套件會停在
   舊版面，而新的讀取端不認得它——需要確定它被列成 invalid 並給出可行動的訊息，而不是
   靜默消失。
