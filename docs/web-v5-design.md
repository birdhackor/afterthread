# web-v5 設計：不可變版本 + 指標切換

本文件是 web-v5 的**設計本體**。`docs/web-v5-plan.md` 是最初的計畫，其設計章節已被取代。
已完成的 P1 的裁決在 `docs/web-v5-decisions.md`（D41 及其五個 review 附錄）。

**修訂紀錄**：五輪 design review（9 + 15 + 15 + 11 + 12 條 finding）與三輪與操作者的討論。
第 17 節逐條記錄每一條 finding 的處置。

**第五輪之後改了做法。** 前四輪的 finding 數量沒有下降（9／15／15／11／12），而第四輪
**全部 11 條**、第五輪 8 條 P1 中的大多數，都打在**前一輪的修法**上。逐條追下去發現兩件事：

1. **設定檔那一題三輪換了三個答案，每個答案都生出一批新的 P1。** 一個問題連續換答案而且
   每次都製造新問題，通常不是答案不夠好，是**放在錯的層次解**。第 3 節現在把整個機制拿掉。
2. **文件已經在規定 fsync 呼叫順序、快取鍵、線上格式**——而 reviewer 自己標註這些「一般
   review 抓不到，要 fault injection／crash 測試才驗得出來」。**那就不該寫在散文裡。**
   第 16 節把它們改成「不變量 + 必須有的測試」，在程式碼裡定案。

這一版因此比上一版**短**，而且拿掉的機制比加上的多。

## 1. 要解決什麼

v4 的 overall review 跑了九輪、33 個 finding，全部是同一個類別的實例：

> **可變的路徑就是身分。** 名稱 → 路徑 → *此刻*擺在那裡的東西。

P1 已經拆掉其中一個根因（開關就地改寫 manifest）。本設計拆掉另一個：**套件的內容會被原地
換掉**。

每一輪 review 的第一課，留著當實作時的提醒：

- **二**：引進間接層（`current`）就要同時寫出它的契約。
- **三**：把一件事拆成兩個目錄，**每一個原本只需要一個答案的地方都變成需要兩個**，漏掉的
  不會報錯，只會安靜答錯。
- **四**：**修法本身要當成新程式碼審**。不要相信「這是為了修 X 而寫的，所以它是對的」。
- **五**：**一個機制連續生出 finding，先問它該不該存在，再問怎麼修。**

## 2. 操作環境與嚴格度校準

本專案是**單人本機工具**，這是設計前提，不是免責聲明。一個操作者、通常一個分頁、建置要花
錢且以分鐘計、沒有敵對行為者（D21，手改是**支援的工作流程**）、工具數量個位數到數十個。

**校準**：

- **併發類的 finding 要說出一個單一操作者做得出來的實際順序**，嚴重性看**對他的後果**。
- **修法要與嚴重性成比例。**
- **折扣不涵蓋三類**：**正確性**（同一問題兩處兩個答案、或函式被餵錯卻不報錯）、
  **失效復原**（當機／中斷／寫入失敗留下的狀態，以及有沒有路徑離開）、**資料遺失**
  （唯一副本）。
- **「不成立」的宣稱不打折。** 第 15 節每一列都要對得起這一條。

## 3. 設定與秘密：什麼都不改

前四輪在這裡繞了三圈（把 `.env` 從 staging 拉上來 → 取消 builder 出貨 `.env` → 兩層 `.env`
合併），第五輪 8 個 P1 裡有 4 個**只因為「兩層合併」這個機制存在才存在**：內嵌秘密掃描會
掃到自己而拒絕、遮蔽用的快取鍵只認得一個檔案、遷移分不清舊檔裡哪些是 builder 的預設值
（導致修訂成功但完全不生效）、以及「把我的設定刪掉」沒有定義。

**正解是把機制拿掉：`.env` 維持今天的樣子，一個檔案、在套件層、是操作者的。**

| 東西 | 放哪裡 | 誰的 | 存活範圍 |
|---|---|---|---|
| **秘密**（API key 等） | `<name>/.env` | **操作者的**（安裝表單注入 + 你手改） | 跨版本 |
| **設定預設值**（endpoint、mode…） | **工具自己的程式碼裡** | 那一版的 | 跟著版本 |

工具讀設定的方式就是一般的 `os.environ.get("API_BASE", "https://預設值")`——**預設值寫在
程式碼裡**，而程式碼是版本內容，不可變、跟著版本走、`current` 切回舊版時自然一起回去。
你在 `.env` 設的值蓋過它，這是環境變數本來就有的行為，不需要任何新機制。

**builder 不寫 `.env`。** 第四輪反對取消這個能力的理由是「只有 builder 知道的設定值會遺失」
——那個理由在這裡不成立，因為**那個值現在在程式碼裡，什麼都沒遺失**。而 R3-1 那個「修訂要
能執行『把 key 存進 .env』的意見」講的是**秘密**，秘密的正路是安裝表單的注入或你自己編輯。

於是所有跟 `.env` 有關的既有機制——大小閘、政策閘、內嵌秘密掃描、遮蔽值快取、
`_preserve_env_file`——**一行都不用改**。builder 若還是寫了一份，照既有的剝除邏輯丟掉，
並在工作結果裡告訴你它宣告了哪些變數名（**只列名字不列值**）。

**要寫進 builder 指示的一句話**：設定的預設值放進程式碼，不要寫 `.env`；需要憑證就在說明
裡寫清楚變數名，由操作者提供。

**誠實的限制**：「丟掉這一版」還原的是**那一版的程式碼與它內建的預設值**，不是你在 `.env`
裡設的東西——那是你的，不屬於任何一版，本來就該留著。

## 4. 版面

```
<tools_dir>/<name>/                 # 整個目錄是後端管的
    .afterthread.meta/              #   後端的：這個工具「現在」的狀態
        state.json                  #     { "afterthread": ..., "enabled": bool }
        current                     #     目前生效的 <vid>（契約見第 6 節）
    versions/                       #   後端的：由後端建立、命名、刪除
        <vid>/                      #     一個版本
            .afterthread.meta/      #       後端的：這一版的資料
                origin.json         #         來源、修訂意見、前一版（＝已提交標記）
                summary.json        #         這一版的 AI 總結（人類看的）
            tool.json               #       以下是工具自己的東西
            run.py …
        <vid>.discarded/            #     被丟掉但當時還在執行的版本（第 8 節）
    .env                            #   你的秘密（第 3 節）
```

**所有權**：套件層 `<name>/` 由後端管，`.env` 是**操作者的**，工具的檔案在這一層一個都沒有；
版本層 `versions/<vid>/` 只有 `.afterthread.meta/` 是後端的，其餘全部是工具的。

**「不准碰」不是強制力**：builder 的指示會寫明保留名稱，但 builder session 有 shell。現行的
`_strip_builder_sidecars` 必須繼續存在，比對對象是「build 根目錄下的 `.afterthread.meta/`」。

## 5. 三種目錄，三個型別

餵錯目錄**不會報錯，只會安靜地答錯**。第四輪我用了一個 `ResolvedPackage(package_root,
version_root, vid)`，第五輪指出它**表達不了必須處理的狀態**：`_scan_package` 要處理
`current` 壞掉、vid 不存在、版本未提交——這些情況下**根本沒有合法的 version_root**；而
`delete_tool` 與清掃要走訪**所有**版本，一個 version_root 也裝不下。

正確的形狀是**三個型別，其中一個是和型別（sum type）**：

| 型別 | 是什麼 | 誰拿它 |
|---|---|---|
| `PackageRoot` | 套件目錄 | `package_enabled`、`_read_enabled_state`、`.env` 載入與遮蔽、`delete_tool`、discard、清掃 |
| `VersionRoot` | 一個版本目錄 | manifest 讀取、`package_identity`、子行程 cwd、`directory_identity`、`read_tool_meta` |
| `Resolution` | **`Resolved(PackageRoot, VersionRoot, vid)` 或 `Unresolved(PackageRoot, 原因)`** | 解析 `current` 的唯一出口 |

- **只有 `Resolved` 那一支帶得出 `VersionRoot`**，所以「沒有生效版本」是型別上的另一支，
  不是一個必須記得檢查的 None。
- `_scan_package` 收 `PackageRoot`，內部解析，兩支都要處理——這正是第五輪 finding 5 說我
  漏掉的：它**同時**讀 state（套件層）和 manifest（版本層）。照第四輪的表把它的參數改成
  版本目錄，state 會從錯的位置讀，配合「state 缺席即 disabled」，**所有合法工具會一次全部
  被列成停用，而且沒有任何錯誤訊息**。
- 走訪所有版本的操作收 `PackageRoot`，自己列舉 `VersionRoot`。

## 6. `current` 的讀寫契約

**vid 語法**：`20260728T134501Z-a3f9c1`，正規式 `^[0-9]{8}T[0-9]{6}Z-[0-9a-f]{6}$`。不含
路徑分隔符也不含點，所以 `../../.staging/<uuid>` 是**語法錯誤**——把穿越變成不可表示。
這也讓 `<vid>.discarded` 這種名字天生指不到。

**目標驗證**（讀取、discard 選前一版、算 lineage 狀態三處共用同一個實作）：

- 有界讀取器（`O_NOFOLLOW` + `S_ISREG`），上限 64 bytes
- 內容去掉尾端換行後必須**恰好**符合 vid 語法；空檔案是錯誤
- `versions/<vid>/` 必須存在、是**真的目錄**（非 symlink）、且**已提交**（第 7 節）
- 任何一項不成立 → `Unresolved`：套件 invalid、不啟用、不廣告、不執行。
  **不猜、不 fallback 到最新的一版**

**寫**：走與側檔相同的原子發布器（mkstemp → fchmod → write → fsync → `os.replace` →
fsync 目錄）。**回傳型別不變，維持 `bool`。**

第四輪為了讓 discard 知道「指標落地了沒」，把發布器改成回傳
`(published, durable)`；第五輪指出那個部分成功狀態（replace 成功、目錄 fsync 失敗）**沒有
任何恢復路徑**。兩者都不必要——**真正的修法是把破壞性動作和指標寫入解耦**（第 8 節）：
discard 不再「先確認落地才刪」，而是**根本不把刪除當成交易的一部分**。既然所有版本永久
保留，「沒刪掉」本來就是每個非當前版本的正常狀態。

於是第四輪那整套 `PublishResult` 與 bool 投影規則**一起刪除**，連同它自己引來的
「`if not write_tool_meta(...)` 遇到 tuple 恆為真」的陷阱。

## 7. 版本的提交與可變性

| 東西 | 什麼時候固定 |
|---|---|
| 版本裡的**工具檔案** | 發布後後端不再修改（你手動改仍然可以，第 12 節） |
| `origin.json` | **在提交那一刻就已經在裡面**，之後不再修改 |
| `summary.json` | **可以隨時整份原子替換** |

`.env` 不在這張表裡——它是操作者的，隨時可改，不屬於任何一版。

**`origin.json` 兼任提交標記**：在＝已提交；缺或壞＝未提交（不可被 `current` 指向、找前一版
時跳過、可被清理）。`summary.json` 缺是**正常**（總結晚於發布）；壞就當作沒有總結。

**套件層 meta 的合法狀態**：

| 狀態 | 判定 |
|---|---|
| `<name>/` 已存在（**任何內容**） | 全新安裝一律拒絕——維持現行行為（`tool_builder.py:1729`） |
| `.afterthread.meta/` 不存在而 `<name>/` 非空 | 未遷移的舊版面：invalid，訊息指向遷移腳本 |
| `current` 缺／壞／指不到完整版本 | `Unresolved`：invalid，不啟用、不執行 |
| `state.json` 缺 | **視為 disabled** |
| `state.json` 是別人的（FOREIGN） | 視為缺，且**永不覆寫、永不刪除**（P1 已定語意） |
| `state.json` 讀不到（UNREADABLE） | fail closed，視為 disabled |

**`state.json` 缺席的預設必須從現行的 `true` 翻成 `false`。** 已查證 `_effective_enabled`
（`tools.py:757`）：狀態不是我們的、manifest 又讀不到時回傳 `True`。新版面下套件層沒有
`tool.json`，於是一個只寫到一半的 meta 目錄會**把工具自己打開**。修法是**刪掉整條 legacy
fallback**，前提是第 14 節的**全有全無**遷移。

## 8. 生命週期

### 暫存區的三個名字

| 名字 | 是什麼 |
|---|---|
| `session_root` = `<tools_dir>/.staging/<uuid>/` | 這一場工作的全部，**`finally` 永遠清掉這個** |
| `build_root` = `session_root/build/` | builder 的工作區 |
| `shell_root` = `session_root/shell/` | 組好的成品 |

現行 `_cleanup_staging` 只遞迴刪掉**它收到的那個路徑**（`tool_builder.py:2543`）。若 builder
改成拿 `build_root`，清理就只刪 `build/`，`shell/` 會留下。三個名字要分清楚，**清理一律以
`session_root` 為對象**。暫存區在 `<tools_dir>/.staging/` 底下是**結構性**要求：現行程式碼
靠「staging 與 target 同在 `<tools_dir>` 底下」證明 rename 不會 EXDEV（`tool_builder.py:2188`）。

### 全新安裝

1. builder 在 `build_root` 建置（不變）
2. 驗證 build 內容
3. 在 `shell_root` 組出**完整**的套件：`versions/<vid>/`（build 的內容）、該版的
   `origin.json`（`previous` 為 null）、`.afterthread.meta/{state.json, current}`
4. 表單秘密注入 shell 的 `.env`；檢查 `.env` 大小（**在 rename 之前**，這樣失敗時整場安裝
   還沒被回報成功，丟掉暫存即可）
5. **確認 `<name>` 不存在**，然後 `os.rename(shell_root, <name>)` ← 安裝完成
6. 之後產生 `summary.json`

### 修訂

1. builder 在 `build_root` 建置（不變）
2. 驗證（不變）
3. 在 `shell_root` 組出**一個版本目錄**的內容：build 的內容 + `origin.json`（含這次的意見，
   `previous` = 目前的 vid）
4. `os.rename(shell_root, <name>/versions/<vid>)`
5. **發布 `current`** ← 修訂完成
6. 之後產生 `summary.json`

`.env` 在整場修訂中**完全不動**。第 5 步之前新版本已經在磁碟上而且**完整已提交**，但沒有
任何東西指向它。**`current` 是唯一的提交點。**

**vid 碰撞是要檢查的正常失敗**：六位 hex 只有 24 bits，時鐘回撥或同秒重試都可能撞。檢查
**`versions/` 底下任何以該 vid 開頭的項目**（涵蓋 `<vid>/` 與 `<vid>.discarded/`），撞到就
重新產生並重試，不要讓一場花了幾分鐘和金錢的建置在提交那一刻失敗。

### 執行

- **廣告的當下記住 `<vid>`**，連同那一版的規格
- **呼叫的時候直接跑那一版**，不再去讀 `current`

**唯一的例外是你在對話進行中親手丟掉那一版**。廣告不是執行，那段期間沒有 identity 登記。
這是**明示接受**的：後果是模型呼叫時得到明確的拒絕，而那是你幾秒前自己做的動作。不引入
reservation／refcount，理由是第 2 節的比例原則。

### 列表與總結讀取

`list_tools` 對每個套件**只解析一次 `current`**，規格與總結都從**同一個** `Resolved` 讀。

**總結的 GET 也要綁版本。** 現行 GET 只帶名稱、後端自己重新解析當下的 current
（`routers/tools.py:401`），而前端用實例身分當 cache key（`toolSummary.js:82`）。於是：展開 V
的總結送出 GET → 丟掉 V 切回 P → 那個 GET 讀到 P 的總結卻寫進 V 的 cache。

**定案（第五輪指出這裡不能留選擇）**：**回應帶上它實際讀到的 vid，前端不符就丟棄、不寫
cache。** 選這個而不是「請求帶 expected vid」，因為它對一個不知道 vid 的舊分頁或書籤也成立，
而且不用改請求 schema。

### 刪除工具

整個 `<name>/` 移除。延後判定要看**所有**版本目錄——`delete_tool` 與 `.stale-` 清掃**共用
同一個判斷函式**，不要有第二種拼法（兩者今天都只看套件根的 identity，`tools.py:4357`、
`tool_builder.py:2494`，而登記的是子行程實際執行的目錄 `tools.py:3993`）。

## 9. 版本保留與「丟掉這一版」

**所有版本永久保留，沒有自動回收。** 一個版本只有兩種方式消失：你按「丟掉這一版」，或你
刪掉整個工具。**「前一版」來自 `origin.json` 記下的 `previous`**，不是資料夾名稱排序。

### 狀態轉移

1. 解析 `current` 得到 V，讀 V 的 `origin.json` 得到 `previous` = P
2. **`P` 為 null** → 這是唯一的一版，等同**刪掉整個工具**，走現有的確認對話框。**結束**
3. `P` 必須通過第 6 節的目標驗證，而且 `P != V`。任一項不成立 → 回 `lineage_unavailable`
   409，**不動任何東西**
4. 發布 `current` = P ← **這一刻 discard 就完成了**
5. 之後**盡力**移除 `versions/V`：沒有東西在跑就刪掉；有的話改名成 `versions/V.discarded`，
   交給既有清掃在之後的工作裡重試

**第 2 步排在第 3 步前面**是第四輪 finding 1：`null` 不可能通過版本驗證，反過來寫會讓單一
版本的工具按「丟掉這一版」**永遠回 409**。

**第 5 步是「盡力」而不是交易的一部分**，這是第五輪 finding 8 的解法，也讓第四輪引進的整套
durability 回傳消失（第 6 節）。理由很簡單：**版本本來就永久保留，所以「V 還在磁碟上」是
每個非當前版本的正常狀態**，不是需要恢復的錯誤。就算刪除完全沒發生，你看到的結果一樣正確
（current 是 P），而多留的目錄不影響任何讀取端。

### API 與身分

**`DELETE /api/tools/{name}/versions/{vid}`**——現行刪除只用名稱定址
（`routers/tools.py:238`、`ToolsPage.jsx:1508`），沿用會讓「畫面顯示 A、你按確認、伺服器
刪掉 B」變成可能。

**`current_vid` 一旦存在，就必須成為前端的列身分。** 這不是重提裁決紀錄 #7——是 #7 自己
寫下的觸發條件發生了。現行前端用 `name + description` 當代理，程式註解自己說那只是因為
API 沒有真實身分（`toolSummary.js:82`、`:102`）。新的出錯情境**單一分頁就會發生**：在 V 的
欄位打了修訂意見還沒送出 → 丟掉 V 退回 P → P 的 description 相同 → 那一列不會重建、草稿
還在 → 按送出，寫給 V 的意見拿去修訂 P，還花掉一場建置。所以 `toolInstanceKey` /
summary cache key / job / ledger **一起**改用 `current_vid`。

### lineage 要三態，不是布林

第四輪寫的 `has_previous: bool` 表達不了三種必須分開的情況（第五輪 finding 9）：

| `lineage` | 意思 | UI 該怎麼做 |
|---|---|---|
| `sole` | `previous` 為 null，只有這一版 | 「丟掉這一版」＝刪除整個工具，走重量級確認 |
| `usable` | `previous` 存在、通過驗證、且不等於 V | 正常的「退回前一版」 |
| `broken` | `previous` 非 null 但驗證不過或等於 V（手改的後果） | **不提供 discard**，顯示原因與「刪除整個工具」 |

`P != V` 必須算進同一個判定：手改把 `previous` 改成 V 之後，布林版會回 true、UI 給出
discard、而 endpoint 每次都穩定回 409。

### 三種 409，各有各的前端動作

| 錯誤碼 | 什麼情況 | 前端該做什麼 |
|---|---|---|
| `version_mismatch` | 畫面過期，伺服器上的 current 不是你看到的那個 | **重抓列表並 remount 該列** |
| `job_busy` | 全域名額被佔用 | 保留操作，稍後再試 |
| `lineage_unavailable` | `previous` 壞掉（手改的後果，且發生在你看到畫面之後） | **不要重試、不要 refetch**——顯示可行動的說明與「刪除整個工具」 |

用**不同的結構化錯誤碼**，不要讓前端解析訊息文字。

### 沒有生效版本的列

`description` 對這種列改為**可為 null**（現行 `ToolSummary.description` 是必填字串，
`schemas.py:516`），前端顯示錯誤原因；`current_vid` 為 null、`lineage` 為 `broken`；
只允許「刪除工具」。

## 10. 移除「定版」

**`finalized` 整個拿掉**，連同 409 `tool_finalized`、`PATCH /api/tools/{name}/summary`、
兩道前置閘、換裝前的重讀、`StoreRefusal.FINALIZED`、以及前端兩顆按鈕和它們背後那套不對稱
閘門規則。

第一個用途（保護可變的總結）消失：總結屬於版本。第二個沒寫在名字上的用途是中止一場進行中
的修訂（`tool_builder.py:2253`），取代它的是「丟掉這一版」。

**已知且明示接受的語意差額**（裁決紀錄 #10）：舊閘門是「這一版永遠不會上線」，新做法是
「先上線但退得回去」。理由是**對照組不是舊閘門而是今天的實際行為**——今天若沒在建置中途按
定版，修訂完成後**舊實作就被刪掉了**。

**「重新產生總結」保留。**

## 11. 併發

**全域一次一個工作維持不變**（`_admit_job`）。安裝、修訂、同步重新產生總結、**以及「丟掉
這一版」**共用一個名額。

1. 兩場修訂**同一個工具**時，`current` 是會被覆蓋的暫存器。
2. **AI 日誌的歸屬**：後端問的是「這個工作流程最新的一筆」而不是「我這次產生的那一筆」。
   這是裁決紀錄 #3 已接受的殘留，而它可以被接受**正是因為**全域一次一個。

**要並行時的正確順序是先把日誌歸屬修對**，而不是先放寬。一般的 AI 對話**不**受這個名額
限制，這是刻意的，也是第 10 節那個語意差額與第 8 節「廣告後被丟掉」的來源。

## 12. 手改仍然被接住

手動編輯版本目錄裡的工具檔案仍然是**支援的行為**（D21）。「不可變」是**後端自己的操作之間**
的約定，不是對你強制的性質。

現行的「對話中途 `tool.json` 被改過就拒絕執行」保留不變。**範圍要說清楚**：
`package_identity` 只 lstat `tool.json`（`tools.py:2637`）。改 `run.py` 而不動 `tool.json`
時，實作變了但身分沒變，**這道檢查不會拒絕**，該版的 `summary.json` 也仍在描述改之前的實作。

手改會製造第 9 節的 `broken` lineage，那不是攻擊，是支援的工作流程的正常後果——所以給它
自己的狀態與錯誤碼，而不是禁止手改。

## 13. `origin.json` 與 `summary.json` 的寫入契約

現行的 `write_tool_meta` 是側檔的**唯一收口**：固定 schema、秘密遮蔽、大小上限、原子寫入，
**遮蔽失敗就整個不寫**。把 origin 拆成獨立檔案**不得**把這些丟掉。

- 兩個檔案都走**同等**的 typed / bounded / sanitized / fail-closed / atomic publisher
- **來源網址在捕捉當下就降級成無憑證的 provenance**（現行行為，不變）
- `origin.json` 裝著來源、**你的修訂意見**（自由文字，要過遮蔽）與 **`previous` vid**
- `origin.json` 在 rename 之前就要在 shell 裡，失敗只是丟掉暫存；`summary.json` 失敗只是
  沒有總結

## 14. 遷移

一次性離線腳本，操作者手動執行，執行時沒有服務在跑。

### 全有全無，而且 commit point 要寫明

**腳本要嘛把整個 tools 目錄遷移完成，要嘛讓它維持原狀。** 這是第 7 節刪掉 legacy fallback
的**前提**：只要允許部分遷移，就會有「舊扁平套件沒有 `current`、新 reader 又不再讀 manifest
`enabled`」的套件，它失效且沒有離開那個狀態的路徑。

**日誌檔，不是靠目錄名字。** 第四輪用確定性兄弟名字兼當日誌，第五輪指出它自相矛盾：預檢
規定「兄弟名字已存在就拒絕」，續跑又規定「靠兄弟名字判斷停在哪」——**第一次中斷之後就
永遠自己救不回來**。改成：

- 開始寫之前建立 `<tools_dir>/.afterthread-migration.json`：這次要處理哪些套件、每個停在
  哪一步。**它才是日誌**，兄弟名字只是它記錄的狀態的實體。
- **沒有日誌檔** = 全新執行：預檢時任何既有的兄弟名字都是操作者的東西，**報告並停下**。
- **有日誌檔** = 續跑：兄弟名字對照日誌驗證後就是我們自己的，直接續做或回退。

**commit point：所有套件都換完的那一刻。** 之後刪除各套件的 `.at-premigrate` 備份是**可重試
的維護，失敗不觸發回退**。第四輪說「回退在任何時點都不需要刪除所以不會半途失敗」——那是
錯的（第五輪 finding 12）：清理階段刪掉 A 的備份之後 B 的刪除失敗，若還要求全部回退，A 已經
回不去了。定義 commit point 之後這個矛盾消失。

### 預檢（唯讀，把所有問題一次列出，全部可遷移才開始寫）

- `.afterthread-state.json` 的三種語意（D41，`tools.py:662`）：**OURS**（`enabled` 搬進新的
  `state.json`）、**FOREIGN**（開關退回 manifest legacy 欄位，原檔當工具內容搬進版本，一個
  byte 都不動）、**UNREADABLE**（報告，不猜）
- 套件已有 `versions/` 或 `.afterthread.meta/` 而**沒有我們的標記** → 報告，不自作主張
- 兄弟名字已存在且**沒有日誌檔** → 報告

### `.ai_meta.json`：缺席才是常態

summary sidecar **從未出貨**，所以「沒有 `.ai_meta.json`」是**最常見**的狀態。三種狀態都要
有規則，否則遷移會為每一個工具寫出指向**未提交版本**的 `current`，新讀取端一次全判 invalid：

| 狀態 | 做法 |
|---|---|
| **缺席**（常態） | 合成一份合法的最小 `origin.json`（來源標「遷移前既有」，`previous: null`） |
| **合法** | origin → `origin.json`，總結 → `summary.json`，`previous: null` |
| **讀不到／解析不了** | 原 bytes 保留，**停下來報告**——它是 origin 的唯一副本 |

### 每個套件的交換

`.env` **留在套件層原地不動**（第 3 節之後沒有歸屬問題了）。工具檔案搬進 `versions/<vid>/`，
manifest 的 legacy `enabled` 讀完後**從 `tool.json` 移除**。交換用三次 rename（新的就位 →
舊的挪開 → 新的上線），每一步都記進日誌檔。遷移後 `_STATE_PUBLISH_LOCK` 可以刪除。

## 15. 這個設計讓哪些既有問題不成立

**這張表的每一列都要對得起第 2 節的最後一條。**

| 問題 | 為什麼不成立 | 前提條件 |
|---|---|---|
| R3／R6-1 執行中套件被換走或刪除 | 子行程的 cwd 是不可變的版本目錄 | **`delete_tool`、discard、`.stale-` 清掃三者共用同一個「所有版本」判斷**（第 8、9 節） |
| R7-1 掃描→建 handler 的身分配對 | 廣告當下綁定 `<vid>` | 「不可變 + 不自動刪除 + 廣告當下綁定」三件事一起；**手動 discard 是明示的例外** |
| R9-2 `list_tools` 撕裂的列 | 規格與總結來自同一個 `Resolved` | 列表只解析一次 `current`（第 8 節） |
| R8-1 origin 永久遺失 | `origin.json` 在 rename 之前就在版本裡 | **持久化順序**（第 16 節不變量 D）；遷移對 `.ai_meta.json` 三種狀態都要有規則（第 14 節） |
| P1 r1-1 修訂覆蓋剛完成的切換 | 狀態檔不在被換掉的目錄裡 | — |
| 裁決 #9 修訂吞掉手改的狀態檔 | 同上 | — |
| **後端造成的**「總結描述的是另一個實作」 | 總結屬於版本 | **只限後端造成的錯配**；手改 `run.py` 之後總結仍會過期（第 12 節）；**總結 GET 帶回實際 vid**（第 8 節） |
| 修訂只有一個提交點 | 修訂只發布 `current`，`.env` 不動、設定在程式碼裡 | 第 3 節 |

**不會**因此消失：v4 R9-1 日誌編號跨行程重用；操作者手改造成的中途變動與總結過期；
裁決 #5、#3、#10；廣告後被手動 discard 的那次呼叫失敗。

## 16. 不變量與必須有的測試

**這一節取代前幾版寫在散文裡的實作細節**（fsync 呼叫順序、快取鍵組成、線上格式）。理由是
第五輪 reviewer 自己的判斷：那些東西「一般 review 抓不到，要 fault injection／crash 測試才
驗得出來」——**那就該寫成不變量加測試，在程式碼裡定案，而不是在文件裡規定呼叫序列**。

實作時每一條都要有**指名的測試**；沒有測試的不變量等於沒有。

| # | 不變量 | 必須有的測試 |
|---|---|---|
| A | 同一個問題只有一個拼法：「這底下還有沒有東西在跑」由**一個**函式回答，`delete_tool`、discard、`.stale-` 清掃三個呼叫端都用它 | 三個呼叫端各一個「版本目錄內有子行程在跑」的案例，都必須延後 |
| B | 沒有生效版本的套件**永遠不執行、永遠不廣告、永遠不被當成 enabled** | `current` 的每一種壞法（缺、空、語法錯、指向不存在、指向未提交、指向 symlink）各一個案例 |
| C | 套件層 `state.json` 缺席 ⇒ **disabled** | 一個只寫到一半的 meta 目錄不得使工具啟用 |
| D | **先讓東西可靠地存在，才讓別人指到它**：版本（含其子目錄的目錄項）持久化後才發布 `current`；套件 rename 後其承載目錄持久化後才回報安裝成功 | crash／fault injection：在每個持久化點之間注入失敗，事後不得出現「指標指向不存在的版本」或「回報成功但套件消失」 |
| E | **破壞性動作不與指標寫入耦合**：discard 完成的判準只有「`current` 已是 P」 | 讓 `versions/V` 的移除失敗，discard 仍須回報成功且 `current` 為 P |
| F | 遮蔽集合涵蓋**當前**生效的所有秘密值 | 換版之後立刻檢查日誌遮蔽（`.env` 未變的情況也要測，防快取失效漏掉） |
| G | 一次列表對每個套件只解析一次 `current`；一列的每個欄位都描述同一個版本 | 列表進行中發生修訂，該列必須整列來自同一版 |
| H | 前端的列身分、summary cache、job、ledger 用**同一個** `current_vid` | 丟掉 V 退回 description 相同的 P，未送出的草稿不得存活 |
| I | 遷移在 commit point 之前的任何中斷都可回退或續跑；之後的清理失敗不回退 | 每個 rename 之後中斷再重跑；清理階段注入失敗 |

## 18. 交付單位

**P2 與 P3 是同一個不可分割的交付與 review 單位。** P2 先移除定版時，版面仍是扁平的、修訂
仍整包換掉並刪除舊實作，而「丟掉這一版」要到 P3 才存在——中間那個狀態**既不能中止也不能
回復**，比現況差。已查證換裝前那道閘門（`tool_builder.py:2253`）就是中止能力本體。

| 內部順序 | 範圍 |
|---|---|
| 先 | 移除「定版」（後端 + 前端）。純刪除，不動版面 |
| 後 | 版本版面 + 遷移腳本 + 「丟掉這一版」 + 前端身分改用 `current_vid` |

review 對整段範圍一次進行，並以第 16 節的九條不變量與其測試為驗收基準。

## 19. 剩下的不確定

1. **遷移腳本的初始 `<vid>` 從哪來**：既有套件沒有可靠的建立時間。傾向用一個固定的初始
   vid，反正遷移後每個工具只有一版。**自由選擇，選錯不會逼迫重做。**
2. **前端「丟掉這一版」的確認流程**：`sole` 時等同刪除工具，需要讓你清楚知道按下去會發生
   什麼，又不該每次都跳一樣的重量級警告。**產品選擇，UI review 看得出來。**
3. **`versions/<vid>.discarded/` 的最終清理時機**：既有清掃在之後的工具工作裡重試，但若你
   再也不安裝或修訂任何工具，它會一直留著。傾向接受（磁碟成本是幾 KB，而且所有版本本來
   就永久保留），但沒有實測過長期行為。
