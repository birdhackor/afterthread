# web-v7 裁決紀錄

沿用 web-v4～v6 的體例：`docs/web-v7-plan.md` 寫**打算**做什麼，`docs/web-v7-design.md` 是設計本體，
本文件寫實作過程中計畫沒寫到的判斷，以及 review 的處置。逐階段接續，從 D48 起編號。

## D48（設計）：已審定的決策

以下是兩輪設計審查後定案、各階段派工都以它為前提的決策；推翻任何一條都要先改設計文件並重新審查。

| 決策 | 內容 | 推翻的代價 |
|---|---|---|
| 存放位置 | 草稿在套件層 `.afterthread.meta/draft/`，不在 `.staging`、不進 SQLite | 刪除工具、同名重裝、sweep、README 的 `.staging` 指示都要重新設計 |
| 接續模型 | 每一輪都從草稿複製到新的暫存工作區；草稿只在保存時換新 | 子行程與保存的競爭、唯一成果的保護要重新設計 |
| 識別 | 接續與放棄以 `(draft_id, generation)` 樂觀比對，`draft_id` 放棄後不重用 | 跨分頁的舊畫面會刪掉或重跑沒看過的成果 |
| 過期 | 只由 `current != base_vid` 判定；基底內容的變更是資訊、不是閘門 | 執行期寫檔的工具會讓草稿無故過期；也等於推翻 v5 §12 |
| 秘密 | 保存與複製進暫存時都用完整掃描器；命中的路徑保留上一份或不存；掃描失敗就不存 | 草稿會長期保存明文秘密 |
| 模型自述欄位 | `handoff`、`operator_action` 只用來顯示與交接，任何邏輯都不讀 | 會重開 v6 R11 不採用模型自報分類的理由 |
| 人接手的出口 | 發布草稿（不經 AI）是 P5 的範圍 | 只差設定的修正必須再付一輪 |

## D49（P1）：單一請求逾時的歸類

openai SDK（2.45.0）對單一請求的逾時擲 `openai.APITimeoutError`。它是 `APIConnectionError` 的子類別、屬於
`OpenAIError`，不是 builtin `TimeoutError`，所以只認 builtin `TimeoutError` 的歸類會把它算成上游錯誤。設計 §5
把「單一請求逾時」與「上游錯誤」分開，因此 `StructuredRunStats.failure` 把 `APITimeoutError` 記為
`request_timeout`，它的父類別與其他 SDK 錯誤仍記 `upstream`；請求本身擲出、整場期限沒有觸發的 builtin
`TimeoutError` 也記 `request_timeout`。擲出的例外與訊息不變（DJ）。卡片的 `request_timeout` 文案點名
`OPENAI_TIMEOUT_SECONDS`：`_get_client` 以它建出 client，作為每個請求的逾時。

## D50（P1）：`operator_action` 不限於沒做完

模型可以在 `run_shell` 裡帶新值驗證過程式、回 `ready=true` 發布，而套件的 `config.env` 仍要操作者貼上那一行。
提示因此要求：只要操作者必須在工作區外動手就寫 `operator_action`，不論做完與否；`handoff` 只在沒做完時寫。
前端在已發布的修訂卡片上也顯示「需要你動手」與交接筆記；停止原因在已發布的卡片上只在 `stopped_by` 有值
（預算結束了工具階段）時才顯示。設計 §4.1、§8 已照此更新。

## D51（P1）：前端不寫設定的上限值

設定的上限只定義在 `config.py` 的 `Field(le=…)`，超過上限的值在載入設定時就被拒絕。前端手抄一份，後端改邊界時
會無聲過時；卡片因此只點名設定名稱，不寫上限數字。

## D52（P2）：以中止訊號停止 builder 指令，不從外部殺

設計 §3.3 第 1 步原本寫「登記 `Popen`，逾時用 `tools._kill_process_group` 殺」。從外部
`killpg(getpgid(pid))` 可能落在 worker 的 `proc.wait()` 回收之後，打到已被重用的 PID，正是
`_communicate_bounded` 的 `teardown_lock`／`reaped` 要擋的情形。

實作改為每場 session 一個 `_BuilderShells`：一個 `threading.Event` 加上強參照的 task 集合。
`stop_and_wait` 先設訊號，再等每個指令的 worker 回報停止證據。`_communicate_bounded` 在輪詢時看到訊號，
就用它既有、在鎖下的拆除流程殺掉並回收；訊號設下之後才要啟動的指令不啟動。

「已停止」只有一個定義：指令的 leader 已回收，而且回收之後觀察到它的 process group 已不存在
（signal 0 得到 `ProcessLookupError`）；或它根本沒有啟動子行程。證據由 `_communicate_bounded` 的拆除在觀察到的當下
記下（`on_reaped`），不論函式之後正常返回還是擲出例外。送訊的結果都不是證據：`killpg(SIGKILL)` 成功只代表送到了
送訊當下的成員，送到不等於已退出；macOS 還會先收集成員再逐一送，送訊途中 fork 出來的成員根本收不到，審查時實測過
這種成員在證據記下之後仍在寫檔。EPERM 也不是：在 macOS 它代表沒有活的成員可送（只剩殭屍，leader 或非 leader 都算），
在兩個平台它也可能代表活的成員都是這個程序殺不了的。被 SIGKILL 的成員要等它的回收者（init、launchd）收走，
group 才會消失，所以確認要輪詢：第一次緊接在回收之後、不先等待，之後持續到拆除的時限為止。回收本身
若已用掉時限，仍會確認那一次；那時看到的消失仍是真的，只是可能晚於等待的一方放棄。

拆除只有一個時限：開始時以 `_REAP_TIMEOUT_SECONDS` 起算，回收前補送、回收後輪詢與 reader 的 join 共用它；
回收 leader 本身沒有上限，SIGKILL 回收不了的 leader 會佔住它的 worker，停止等待仍在自己的上限結束、算無法確認。
group 一消失，就沒有成員還拿著管線的寫端，join 立刻完成，所以等待上限不必逐段加總。回收前補送只在 macOS 做：
leader 未回收時 PGID 被它釘住，補送 SIGKILL 直到確認沒有活的成員可送（EPERM）或 group 已不存在（ESRCH），
或時限到；補送的退出不是證據，回收後的 ESRCH 才是。Linux 不需要也不能這樣做：它的群組訊號連進行中的 fork
都送得到，而殭屍 leader 未回收時 signal 0 一直回成功，迴圈會燒滿時限。回收之後不再送任何 kill，因為 PGID
已不再被 leader 釘住。
交給 `_communicate_bounded` 的 leader 只由拆除回收：輸出超量時的 kill 也直接對 `proc.pid` 送 `killpg`，不經 `getpgid`（macOS 對已退出的
leader 回 ESRCH），也不回落到 `proc.kill()`（它先 `poll()`，會回收已退出的 leader）。

啟動失敗的指令另有一條路：`_ShellPopen` 保留建構失敗的 `Popen`，依 CPython 留下的記錄判定。沒有 pid 是 fork 之前就失敗，
算沒有啟動；有 returncode 是 CPython 已回收 exec 失敗的子行程，之後 group 也已不存在才算已停止；fork 了卻沒被回收，
算無法確認，不殺它（它可能還沒 `setsid`）。例外的型別不是證據。

除了上面的送訊結果與例外型別，以下三種替代訊號也都試過、也都被推翻：
- asyncio task 的狀態：uvicorn 關閉時 `asyncio.run` 會取消所有 task，被取消的 command task 看起來已完成，
  它等待的 threadpool worker 卻還在跑；
- worker 返回：它可能在啟動子行程之後、拆除完成之前就被例外打斷；
- 時間到：只能說「等不到」，不能說「已停止」。

等待上限是 `tool_install_shell_timeout_seconds` 加上 `_REAP_TIMEOUT_SECONDS`。超過時不剝除、不發布，
也不清理這一場的暫存目錄：它原地保留，job 失敗並在訊息裡附上路徑；名額照放，理由見下一段。
等不到證據的情況例如：kernel 回收不了的 leader、回收失敗、group 在時限內沒有消失（送訊途中 fork 出來
而沒收到的成員、殺不了的成員、卡在不可中斷 kernel 等待的成員、沒有回收者收走的殭屍，例如服務在
Linux 上是 PID 1 而沒有 init）、
拆除完成之前被例外打斷、被卡住的執行緒（例如已啟動子行程、卻在第一次輪詢前停住）。
這個出口不得再等待可能被卡住的資源，例如卡住的 worker 佔著的共用 threadpool。至於沒有被排程、根本
沒進入 worker 的指令，它之後看到訊號就不會啟動，算作沒有啟動子行程（`entered` 握手；這個推導依賴
GIL 下的單一全序）。

「名額照放」不是 DC 的例外，而是從 DC 推導出來的：名額守的是後端寫入者之間的互斥（`_admit_job`），
一場已永久放棄保存、發布、清理的 session 不再是寫入者；殘留的 `run_shell` 指令也不是後端寫入者，它只在
自己的暫存目錄裡跑，碰不到下一個 job 的暫存目錄。「扣到確認停止」實際上就是扣到重啟，因為不返回的
worker 生不出證據。

這個推導的前提是：後端永不再碰保留的工作區。目前成立：`.staging` 只對空目錄 `rmdir`，`_sweep_stale_backups` 只收 `_STALE_BACKUP_RE`、`versions/*.discarded`，以及各套件 `.afterthread.meta/` 底下屬於草稿的命名（D54），下一場用新的 uuid。
守衛是一則測試：保留一個工作區之後再跑一場 job，那個目錄原封不動。日後若有步驟會去碰舊的 `.staging` 目錄
（例如啟動時清掃），名額或每個工作區一個標記就得回來。

不變量 DA 依賴 DC：`scan_embedded_secrets` 以路徑走訪子目錄（`os.scandir`），目錄在分類之後被換成連結時
會走出工具包；它只在工作區已靜止時才可靠。若日後要掃描別人可能同時在改的樹，改用以 fd 走訪
（`O_DIRECTORY | O_NOFOLLOW` 加 `os.scandir(fd)`）。

設計 §3.3 第 1 步與 §9 的 DC 已照此更新。

## D53（P2）：後端產生的路徑不遮蔽

回報給操作者的暫存目錄、草稿目錄等路徑，只由設定的工具目錄、固定名稱與隨機 id 組成，不含操作者或檔案提供的文字。
它們不經秘密遮蔽：操作者要原樣複製它們；而遮蔽要掃描工具目錄，必須在 worker 上做。在「無法確認停止」的出口，
worker 可能正是卡住的資源。

不遮蔽不等於不做可編碼處理：Linux 上工具目錄的路徑可以含非 UTF-8 位元組，原樣送進 JSON 會讓整個回應失敗。
API 回應裡的後端路徑都換成可編碼的形式（欄位用同一個型別，錯誤訊息裡的就地處理），代價是含替代字元的路徑
不能原樣拿去用。

## D54（P3）：草稿落地時的幾個判斷

實作者動手前先推導，主 agent 據此定案。設計 §3.3、§3.8、§7 已照此更新。

- **「有草稿」就是 `<pkg>/.afterthread.meta/draft/` 這個目錄項存在**，不論它的狀態。若把「沒有說明檔」當成沒有草稿，
  下一次保存寫出說明檔之後，sweep 會把當機時留下、內容完整的 `files-*` 當成孤兒刪掉。
- **放棄殘留留在同一層**：改名成 `.afterthread.meta/draft.discarded-<hex>`。同目錄改名，殘留跟著套件走，刪除工具時一起
  消失；不借用工具目錄層的刪除殘留命名。
- **鎖**：
  - 保存的第 8 到第 11 步持共享 tools lock。設計原本只寫到第 10 步，延伸到第 11 步，刪除上一份檔案目錄時也排除 `delete_tool`。
  - 放棄用「名額加共享鎖」，不用排他鎖：AI 請求整段都持共享鎖，用排他鎖會在對話進行中讓放棄回 409。名額已排除 job 與
    sweep，共享鎖讓 `delete_tool` 回 409。
  - 草稿的 sweep 在 `_sweep_stale_backups` 的排他鎖內執行，自己不取鎖；持共享鎖時不呼叫會取排他鎖的函式。
- **連結**：目標路徑裡 `..` 緊接在本身是連結的元件之後，就不存（§3.3 第 6 步）。
- **文字清理在 P3 自己的邊界，不改 `llm.py`**：
  - 說明檔寫入時，每個字串依序遮蔽、截斷、套 `_utf8_safe`，再以寫進檔案的形式檢查（D55）；讀出時套 `_utf8_safe`，
    交給 API 前再遮蔽一次。
  - 模型文字進不來：結構化輸出的文字欄位經 `memory_ai._coerce_str`，遇到 lone surrogate 就驗證失敗、觸發修正重試。
  - P3 真正的 surrogate 來源是檔名（掃描命中的路徑、沒存的路徑），以及從磁碟讀回的說明檔。
- **輪數**：說明檔另記累計輪數 `attempt_count`；`attempts` 只留最近 5 輪，每筆帶自己的 `number`。job 與列表的
  `draft.attempts` 都取累計輪數。
- **第一輪的 `origin.feedback` 也帶「草稿 `<draft_id>`，經過 N 輪」**：第一輪在 `ready=true` 時也會先保存再發布，
  帶了這一行，發布成功而刪草稿失敗時，§3.7 的「已發布」才判定得出來，而不是落到「結果未知」。
- **發布失敗時，回報成果實際所在的路徑**：發布分兩段搬移（`build` 先到同一場的 `shell`，再進 `versions/<vid>`），
  成果可能已經不在暫存目錄裡。


## D55（P3）：檢查要落在真正存下、真正動到的那個對象上

保存與放棄的幾道檢查，原本落在相鄰但不同的對象上：大小與連結量的是換回舊版**之前**的工作區，草稿拿到的卻是
換回之後的樹；讀取與放棄經過 `.afterthread.meta/` 的別名，保存與 sweep 卻不經過；`finally` 只在正常返回的
路徑上決定要不要保留暫存目錄。這裡的決定一律改成檢查那個真正被存下或被動到的對象。設計 §3.1、§3.3、§3.8、
§9 已照此更新。

- **連結在複本上再判一次**：換回舊版會改變路徑上的元件是不是連結、指向哪裡。一般檔案換成連結，或連結換成
  目標不同的連結，都會讓工作區上判過的連結在草稿裡走出去。複製完成後，以複本為根把每個連結判一次，先全部
  判完再刪；工作區上的那一次判斷保留，負責決定要不要規劃。只排除「一般檔案換成連結」是不夠的：連結換連結
  一樣會改變解析路線。
- **大小上限算複製出來的東西**：在複製時邊寫邊累計，換回的舊版也算；舊版的來源可能在保存途中被手改，只在
  規劃時加總會被超過。掃描前對工作區的那一次保留，它限的是掃描的成本。
- **草稿只經由套件自己的、真目錄的 `.afterthread.meta/` 到達**：它是連結或不是目錄，這個套件就沒有自己的
  草稿。否則一個工具的列會顯示另一個工具的草稿，用它的 token 放棄會刪掉那一份。`lstat` 本身失敗（不是不存在）
  時，讀取照舊「看不到就當作有」，寫入照舊不寫；放棄也是寫入，看不到就不動手，回報沒刪。寫入者經由專用的
  入口拿路徑，那個入口只交出看得到的路徑，所以「看不到」不必靠每個呼叫者記得去看。
- **發布這條路上，暫存目錄要有人接住成果才清**：從發布前的保存開始（取消送達時保存的 worker 可能還在跑，所以
  旗標在保存開始之前就立起），到發布的結果處理完為止，例外或取消都保留暫存目錄。發布的 worker 可能還在寫時
  也保留：只有它正常返回或自己丟出例外，才算結束。組版本來源說明失敗算發布失敗。
- **「已刪除」只靠親眼看到不存在**：放棄只在 `lstat` 回「不存在」時回報已刪；其他錯誤都回報 `draft/` 本身是
  殘留，不把「看不到」當成「不在了」。
- **存下的複本整棵重掃**：工作區上的掃描決定規劃，存下的卻是複本，兩者在換回舊版與改寫連結目標的地方不同。
  複本做好、連結判過之後，用保存開始時那一份已知秘密把複本整棵再掃一次，命中的路徑刪掉並記成沒存；
  這次掃描失敗就整輪不保存檔案。它涵蓋原本對換回檔案的逐檔重掃，那一道因此拿掉。接續把草稿複製進新的
  暫存工作區時，用同一個步驟。
- **沒有說明檔時，token 由 `draft/` 裡實際有的東西算**：說明檔在時，它的 inode、ctime、size 分得出不同次
  建立；不在或讀不到時，另把 `draft/` 直接成員的名字與身分算進去（保存建立的成員都帶隨機名字）。說明檔在時
  不加：sweep 收孤兒會改變成員，換來無謂的 409。
- **自由文字以寫進檔案的形式檢查**：在 str 上遮蔽之後，JSON 編碼（跳脫序列）與 `_utf8_safe`（替代字元）還會
  產生新的位元組，能在檔案裡拼出已知秘密，例如單引號的 PEM 在 `.env` 裡保留字面的 `\n`。所以每段自由文字遮蔽、
  截斷、scrub 之後，再以它在檔案裡的 JSON 字串字面、用同一個比對器檢查一次，命中就整段換成遮蔽標記。寫入前
  另有一道底線：把形狀由樣式檢查固定的欄位（識別字、時間戳、詞彙值）清空後的整份編碼再比對一次，命中就把
  全部自由文字降成標記重試，仍命中才放棄寫入。這道底線看得到以後新增、卻沒走遮蔽的欄位。識別字照舊不遮。
  - 照這樣檢查的寫入者：草稿說明檔、版本的 `origin.json` 與 `summary.json`（同一個 `tools._redacted`）、AI 日誌
    的 JSONL（`llm_log` 保留自己的一份 helper）。草稿複本已整棵重掃。執行紀錄（`tool_runs._storable`）是同一類
    但決定不守：它在遮蔽之後才把孤立 surrogate 寫成三個 U+FFFD，能拼出含連續三個 U+FFFD 的已知值；只有工具參數
    與訊息會帶 surrogate（輸出解碼時已換掉），讀出時又會再遮一次。理由寫在 `_storable` 旁。
  - 不涵蓋表示法層級的不同：秘密以真換行登記而文字是字面的 `\n`、base64 等其他編碼、`.env` 讀入時已被
    替換掉的位元組。精確比對本來就保護不了表示法改變。
  - 這一類的收斂不再看「某個檔案裡找不到」，而是看這份寫入者名單：每一個都標明以什麼形式檢查。
- **連結目標保留原本的元件**：絕對目標若先做字面正規化，`x/..` 會在判斷之前被摺掉，存下的連結指向另一個檔案，
  而且沒有記錄。字面正規化只對每個元件都是真目錄的那一段成立。所以只把根前綴（照給定或解析後的寫法）當文字剝掉，
  作業系統經由它一定走到根；其餘元件原樣交給同一條規則。在複本上再判一次，只能驗「存下的連結在複本之內」；驗不了
  「它還是原本那一個」，那個資訊在改寫時就沒了。所以連結這個領域的名單，是一則對作業系統的差分測試：列舉各種連結
  形狀，保存之後逐一比對複本裡與工作區裡解析到的位置。規則可以保守地拒絕作業系統其實解析在內的形狀，但要記下原因；
  測試不放秘密，驗的是沒有換回舊版的情形。
- **觀測不足不授權動作**：查詢失敗得到的結果，不能拿來證明身分相同、可以保存、可以刪除或已經刪除。它可以轉成
  保守的結果，但要追到每個使用它的地方，確認沒有一處因此拿到動作許可。這一類已出現過幾種形狀：推測已刪除、
  看不到 metadata 仍放棄、連結判斷把查不到當成「不是連結」、token 把兩次查不到算成同一個值、拿不到鎖就說成
  沒有草稿、整棵樹 fsync 略過列不出的目錄仍回報已落盤。修法是把 P3 程式裡
  每個把查詢失敗轉成答案的地方列出來，一一追到使用者，不是逐處補。
  - 列舉的方法：從 P3 的每個動作（保存、放棄、發布前後的標記與刪除、清掃、擋修正）出發，放行是好幾個查詢的
    合取，每一項都要沿呼叫一路追到最底層的原語，不論定義在哪個檔案；只追到呼叫處、或只看放行前最後一個查詢，
    都會漏。暫存目錄的檢查 `_verify_staging_root` 就是這樣漏掉的：它定義在 P3 之前，P3 的保存靠它放行。
    根路徑的取得（`tools_dir()`）、快取與注入的 provider 都在這條鏈上。
  - 判定成員要走完整條路：從最後的動作往回，列出路上每一道拒絕，注入查詢失敗後看每一道實際怎麼回答；走得過全部
    拒絕的情境才是成員。改共用的 helper 之前，先列出它所有使用者，以及各自拿失敗的答案做什麼。
  - 原語分兩類。會傳出錯誤的：`os.lstat`、`os.stat`、`os.scandir`、`open`、`os.readlink`、
    `os.path.realpath(..., strict=True)`。會吞掉錯誤的：`os.path` 的判斷式、`Path.exists`／`is_*`、不帶
    `strict=True` 的 `resolve()` 與 `realpath`、`shutil.rmtree(..., ignore_errors=True)`、`contextlib.suppress`、
    `except OSError` 之後回一個定值。碰到吞錯的，要問那個定值是放行還是拒絕。
  - 依名稱找套件的 `tools._resolve_package_dir_no_alias` 是成員，經由放棄：別名的 `lstat` 失敗時，`is_symlink()`
    答「不是連結」，接著的 `resolve()` 跟隨別名交出實際套件，`_own_meta` 重查的正是那個實際路徑，所以拿著實際草稿
    的 token、以別名的名稱放棄，會刪掉實際草稿；沒有故障時同一個請求是 404。下游的重查只有在看的是同一個對象時才
    擋得住；看的是從失敗查詢推出來的值，就補不回已經丟掉的身分。修法是檢查解析的結果：解析後的目錄必須正好等於
    `tools_dir()` 交出的路徑接上名稱（只取一次根路徑，右邊不再解析），不依賴會失敗的查詢；經同一個 helper 的
    「丟掉某一版」也因此不會經別名動到實際套件。不改成嚴格的 `lstat`，因為實際套件在查詢暫時失敗時也會變成
    None，而 P3 以外有使用者把 None 當成「已不在」並據此刪執行紀錄（那不屬於這件工作，已回報）。
- **已知秘密要交代是否完整**：遮蔽與掃描用的已知秘密，來自每個已安裝工具的 `.env`。讀一個 `.env` 的結果分兩種。
  確定的答案：不存在、確認是連結或特殊檔、超過讀取上限、parser 交出的值（含部分或沒有）——照 app 自己的讀法，
  這個來源就是這些值。不知道：其他查詢或讀取失敗。只要有一個來源不知道，`_redaction_secrets()` 就不交出清單，
  改拋錯，錯誤說是哪個工具的 `.env` 與下一步；它所有的使用者原本就宣稱失敗時不放行，所以保存、發布驗證、清單、
  builder 與工具輸出都照各自的方式失敗，不再拿缺了值的清單當完整的。代價是任何一個 `.env` 讀不到時，這些動作
  全部停下，直到操作者處理；已確認的特殊檔、超限或解析結果不會造成這種停擺。工具執行期讀 `.env` 的降級（讀不到
  就沒有額外 env）不變。失敗不進快取。`tools_dir()` 改用 `strict=ALLOW_MISSING` 的解析：缺少的元件照字面；某一段
  是一般檔（ENOTDIR）也是確定沒有目錄，回傳設定的路徑本身，核心的 AI 功能照舊在沒有工具下運作；其他失敗往外拋，
  不再把查不到的連結後面的 `..` 依字面消掉。這兩種錯誤的訊息只含路徑、工具名、錯誤型別與下一步；API 的 500、
  安裝與修訂 job 的錯誤都直接帶出它，操作者看得到該修哪裡。
- **AI 日誌在清單不完整時不存本文**：D36 讓記錄器在出錯時退回存未遮蔽的本文，理由是觀測器不能讓被記錄的呼叫
  失敗。不拋錯仍然成立，但最後那道「照寫入形式檢查」（`_checked_as_written`）拿到不完整的清單、或自己失敗時，改存
  「本文未記錄」的標記，不存本文：缺的那個值可能正好由 JSON 編碼拼出來，前面的即時遮蔽看的是文字，擋不到。這個
  標記和「命中秘密、已遮蔽」的標記不同，看日誌的人不會以為本文含秘密。狀態、耗時與 usage 照記。D36 其他的降級
  這次不動。
- **連結的升級方式重新裁決**：原本講好，差分測試存在之下若仍有連結缺陷成立，就改成「解析、不剖析」。這個條件
  在終止複審觸發了，但那條缺陷的成因是錯誤資訊遺失：全面改用解析也一樣會吞錯（`os.path.realpath` 不帶
  `strict=True` 就會），解決不了。所以改成：保留元件規則並修正查詢錯誤的語意，另在最終複本上以會傳出錯誤的
  解析，直接檢查每個留下的連結落在複本內，或在複本內確認懸空，無法確認就不存。這道檢查不改存下的字串，所以不必攤平
  連結指連結；保真仍由差分測試守。
- **看不到的草稿，放棄不刪**：先前寫過兩句承諾，現在都推翻。一句是「無法使用的草稿都能用 `discard_token` 放棄，
  每份草稿都有 token」；另一句是「`draft/` 看不到時算作有草稿，操作者可以放棄它」。DG 優先：放棄要能證明刪的是
  操作者看到的那一份，查詢失敗時證明不了，刪下去可能刪掉沒看過的成果；留著只會擋住新的修正，而 500
  `draft_not_removed` 的訊息給了下一步：檢查權限與檔案系統狀態後再放棄，或照訊息確認後手動刪除。兩句都從
  「放棄也是寫入，看不到就不動手」那條起就已經不成立（`draft/` 看不到的那種形狀），當時沒有改寫；token 只供顯示
  那條，再把「看不到」擴大到說明檔與成員的查詢。原本錯在推論：讀取時把看不到的草稿當作有，理由是 sweep 的安全
  （D54），從來不是「放棄一定成功」，不能拿來推出「操作者可以放棄它」。
  看得到的無法使用草稿（說明檔內容壞掉、檔案目錄不見）照舊能放棄。

## D56（P4）：接續的保存、刪除與送出

實作者先盤點了 P4 的每個動作，以及 P4 會改到的共用函式和它們的所有使用者。設計諮詢看過兩則之後，主 agent 據此定案。
設計 §3.1、§3.2、§3.3、§3.4、§3.5、§3.7、§4.2、§7、§8、§9 照此更新。

- **成果沒有人接住，就不清暫存**：指令確認停止之後，這一輪的暫存目錄只在下列情況清除：
  - 成果已經存進草稿，而且說明檔確認落盤；發布的 worker 還沒返回時仍然保留，同 P3。
  - 已經發布，成果在版本目錄裡。
  - 沒有值得保存的東西：第一輪沒有變更，模型也沒有交回筆記。

  其他出口一律保留，包括：
  - 保存沒存成，不論原因；秘密清單不完整也算。
  - 保存寫了說明檔，卻無法確認落盤。`saved` 仍是 True：清單確實已經是新的一輪。
  - 發布失敗，而發布前的保存沒有確認落盤：寫過 `publishing`，不等於草稿接住了成果。
  - 遮蔽模型筆記時拿不到完整的秘密清單：當成正常出口，不寫說明檔。
  - 建置器的 `.env` 剝除失敗：不保存檔案。工作區可能還留著那個 `.env`，所以後端記錄要說明這一點，README 也要提醒
    取回之後刪除整個目錄。

  保留時要注意：
  - **保留之前，一律先剝除建置器的 `.env`**。指令確認停止之後先剝除，再遮蔽筆記、保存；例外或取消時，在保留之前補剝。
    剝除失敗也保留（見下面〈剝除失敗改為保留〉）。指令無法確認停止的出口照 P2：不剝除，整個保留。
  - **保留的旗標在取得停止證據的當下立起**（內層的 `finally`），所以向外傳播的例外與取消也接得到。
  - **job 的 `draft.retained_path` 寫成果實際所在的路徑**：發布可能已經把它搬到同一場的 `shell` 或 `versions/` 底下，
    要用發布交回的位置。
    - 這個承諾只對正常返回、而且位置已知的出口成立。例外與取消照 P3，只在後端記錄寫 session 的路徑。
    - 工作區本身驗證不過時，只能說原本的工作區路徑沒有確認，不能宣稱成果在那裡。

  理由：保存失敗、落盤沒確認、清單暫時讀不到，都只是「無法確認已安全保存」，推不出「可以刪掉唯一的成果」。P3 在一般
  未發布的保存失敗出口清掉暫存，現在統一成這一條。第一輪也照這條：多留一份無害，少一套例外。

  **這一條推翻了 P3 的兩項取捨**：
  - 發布路徑以外的保存失敗，清掉暫存。
  - P3 接受過的一條殘餘：發布前的保存開始之前，取消照樣刪掉暫存，「與其他路徑上的保存失敗相同」。

  現在兩者都保留暫存。取消時，旗標在取得停止證據的當下就已立起，保留之前先補剝建置器的 `.env`。

  這兩項取捨不是到 P4 才變錯，而是一開始就把「唯一成果不會消失」（DD）的範圍框在發布路徑上。第一輪的保存一樣
  可能因為暫時的狀況失敗，例如某個工具的 `.env` 一時讀不到；這時清掉暫存，就丟了付過錢的那一輪唯一的成果。P4 的
  設計諮詢以這個反例指出了它。依那兩項取捨寫成的文字都已照新規則改寫，包括設計 §3.3、§9 的 DD，以及 README
  的草稿段與 `.staging` 段。

  更精確地說：範圍窄的前提來自 D48 審定的設計，它只回應了「發布前保存失敗、發布又失敗」那一個情境。P3 第一輪審查
  的 finding 已經寫出同一個機制：秘密查詢失敗 → 沒有保存 → `finally` 清掉暫存 → 付過錢的成果消失。這個機制在發布
  路徑以外一字不差地成立，裁決卻照設計那句發布路徑的承諾，只修了發布路徑；從第二輪起，剩下的那一半被寫成已接受的
  殘餘。

  D56 另外改了 P3 定下的三項做法，理由各見它們的那一條：
  - sweep 不再收沒被說明檔點名的 `files-*`。D54 第一條用「sweep 會把當機時留下、內容完整的 `files-*` 當成孤兒刪掉」，說明為什麼
    沒有說明檔也算有草稿；那個後果現在不會發生了，那條規則本身不變。
  - 發布前的保存一律複製。P3 的設計寫的是：接續的一輪沒有變更就只記這一輪，沒有發布前的例外。
  - D55 的「旗標在保存開始之前就立起」：改成在取得停止證據的當下立起。

  **剝除失敗改為保留**（訊號 B 的複審指出，定案之後重新裁決）：原本照 P3，剝除失敗就嘗試清掉暫存，免得留下建置器寫的
  `.env`。這個理由在主要的失敗成因下不成立。讓剝除的 `unlink` 失敗的原因（例如建置器把工作區改成唯讀），也會讓清除時
  對同一個檔案的 `unlink` 以同樣方式失敗；`rmtree(ignore_errors=True)` 於是留下 `.env`，卻刪掉其他還刪得掉的成果。
  實測：工作區改成唯讀、底下的子目錄仍可寫時，`.env` 與工作區根層的檔案都還在，子目錄裡的檔案被刪了。只有暫時性的
  錯誤會讓第二次成功，而那正是成果不該消失的時候。
  - 這是 D55 那份列舉漏掉的動作：清暫存。從 `run_revise` 放下保留旗標的出口追到原語：
    - 說明檔確認落盤：來自原子寫入的 `durability_out`，是確定的答案；
    - 沒有值得保存的東西：`same_tree` 有一邊是 None 就不相等，查詢失敗只會變成「有變更」；
    - 已經發布：發布正常返回；
    - 剝除失敗：`_strip_builder_env` 把 `lstat`（不存在以外）與 `unlink` 的失敗轉成剝除失敗，再由它放行刪除——這個
      出口就是這一類的成員。
  - 保留之後，`.env` 留在資料目錄底下，與套件自己的 `.env` 在同一個資料目錄裡；P2 對指令無法確認停止的出口，
    已經接受過同樣的狀態。工作區確認過時，job 回報它的路徑。
  - `finally` 的補剝失敗也一樣保留。安裝不在這一條的範圍內。
  - **更正：上面的列舉漏了 `saved`**（第一輪審查指出，複審同意）。它以出口為單位列，`_holding` 只追了 `durable`。
    改以放行條件的原子列：清暫存，要指令確認停止、發布的 worker 不在寫、保留旗標放下；旗標放下，要沒有值得保存的
    東西，或 `saved` 與 `durable` 都成立，或已經發布，或成果已搬離這一場的暫存目錄。`saved` 為 True 有兩個來源：
    做出新的檔案目錄，看的是做出來的那份複本；未改檔的接續只記一輪，原本沒有看檔案目錄——這是這一類的第二個成員。
    D55 那段寫的是「查詢失敗得到的結果」；根本沒有查詢、只有假定，同樣是觀測不足。
- **未改檔的接續沿用原本的檔案目錄之前，先看過它**：只記一輪之前，在鎖內確認檔案目錄現在的雜湊仍等於開工時複製出來
  的那份（`copied_out`）。不相等或無法確認，例如一輪進行中被改過、被移走，或讀不完整，就把這一輪記成沒存：檔案目錄
  不動，操作者改過的那份仍是草稿目前的檔案；暫存保留並回報路徑。
  - 不改成複製一份新的檔案目錄：那會讓操作者手改的內容退到 `kept`，下一輪帶進工作區的反而是手改之前的內容。
  - 這個比對與刪除上一份檔案目錄的第三個條件是同一個觀察，共用一個函式。
- **草稿記下的執行紀錄摘要，讀回時驗形狀**：說明檔 `runs[]` 的 workflow、vid、outcome 寫入時遮過，是自由文字；讀回時
  不能當成後端的值。紀錄已清除、只剩摘要時，讀回處驗它們是後端產生的形狀，不合就略過那一筆；驗過之後與資料庫裡的
  紀錄一樣，照原樣進 prompt。
  - 代價：一個秘密剛好等於後端產生的值的一段時，例如 vid 的尾碼，那個值在 prompt 裡不遮。資料庫那一路本來就如此：
    後端自己的值照原樣放，遮了會把它弄亂。
  - 不選「建 prompt 時再遮一次」：只遮已清除的那一路，兩條路就不一致；而且固定的欄位裡會出現遮蔽標記。

  不重試 fsync：寫入函式在替換之前已經 fsync 過暫存檔，`durable` 為 False 指的是之後的目錄 fsync 沒有確認。fsync 失敗
  之後再呼叫一次就成功，證明不了先前的寫入已經落盤：回寫失敗時，核心可能丟掉髒頁並清掉錯誤狀態。
- **保存交回三件事**：
  - 這一輪的檔案是否在草稿裡（`saved`）：存成了新的檔案目錄，或接續一輪下來沒有變更、草稿原本的檔案就是它；
  - 這一輪是否已經記進說明檔；
  - 說明檔是否確認落盤。

  `saved` 為 False 不代表說明檔沒動：許多保存失敗的出口已經記下失敗的一輪、加了 generation、清掉了 `running`。「只記
  這一輪」的補寫，只給還沒記的出口。
- **上一份檔案目錄先點名，再決定刪不刪**：只有成功提交一個不同的新檔案目錄時，才處理上一份。只記一輪、保存失敗、
  沿用原本的檔案目錄時，都不動它。

  處理方式：把上一份記進 `kept`，和新的說明檔同一次寫入。寫完之後，下面三件事都親眼確認了，才當場刪：
  - 說明檔確認落盤。
  - 開工時上一份的雜湊（`copied_out`，複製之前取）與複製完成、模型開始之前的工作區雜湊（`copied_in`）相同，也就是
    帶進工作區的正是開工時的內容。漏掉的項目、改寫的連結、複製期間被換掉又換回來的檔案，都會讓兩者不同。
  - 上一份現在的雜湊仍等於 `copied_out`：這一輪進行中沒人改它。

  其餘情況，它留在 `kept`，job 卡片說它在哪、為什麼留。

  理由：
  - 落盤要等說明檔寫完才知道，所以「沒落盤就記進 `kept`」來不及寫進同一份說明檔。
  - 只比開工與保存兩個時點，證明不了中間帶進工作區的是同一份內容。
  - 複製進來時漏掉的項目，不放進新的複本：草稿根目錄的 `.env`、命中秘密的檔、指到外面的連結、特殊檔。新複本只放後端
    掃過的內容（DA），所以這些項目只能留在上一份裡。

  `kept` 的修剪與上限：
  - 名字只在改寫說明檔時、親眼看到不在（`lstat` 回不存在）才拿掉。查詢失敗的照留，也不會因為上限而丟掉。
  - 開工時，修剪後仍達上限，就不開始、不花錢。
- **sweep 不再收沒被點名的 `files-*`**：「沒被說明檔點名」不是可以刪的證據。
  - 情境：說明檔寫完、還沒確認落盤就當機，舊說明檔回來了；新的檔案目錄就變成沒被點名，而操作者可能已經照畫面給的路徑
    改過它。
  - sweep 只收兩種：`.incoming-*`（半成品，從來沒有給出路徑），以及已授權刪除留下的 `draft.discarded-*`（放棄、
    發布後刪除）。
  - 沒被點名的 `files-*` 留到放棄為止。發布後刪除看到多出來的名字，會留下整份草稿。
  - 不選「延後刪除，把基線寫進說明檔，由 sweep 重算後再刪」：它多一個欄位、讓 sweep 每次都要雜湊，卻仍然保護不了那個
    沒被點名的新目錄。
- **草稿目錄要看得到**：清單的草稿多帶兩項：整個草稿目錄的路徑，以及 `kept` 的路徑。
  - 草稿提示要說：草稿目錄裡可能還有沒列出的目錄。
  - 放棄的確認框要說：整個草稿目錄都會刪掉。

  否則操作者照 `path` 取回之後就放棄，會漏掉兄弟目錄裡的手改。
- **發布後刪除**：
  - **草稿裡有多出來的名字，或內容不同時**：照舊留下整份草稿。原因文字改成「草稿仍有額外的項目，可能含沒發布的內容」，
    不再說發布期間被改過。不新增判定值。
  - **要發布的保存一律複製**，接續一輪下來什麼都沒改也一樣。這樣發布後刪除永遠有發布前那次保存做出的複本可比。
  - **接續的發布前保存沒存成、發布卻成功時**：照舊不寫 `publishing`。
    - job 的 `draft` 帶出保存或補記交回的身分；兩者都沒有時，才用開工時的身分當歷史參照。
    - 原因說：已發布；這一輪沒存進草稿，請取回草稿裡需要的內容再放棄。
    - 成果已經在發布的版本裡，暫存照清。
- **一輪由誰收尾**：
  - **開工寫入 `running`**：在 job 內的前置檢查之後、複製之前寫入。寫不進去，就不開始、不花錢。這次寫入要交回寫完的說明檔
    （新的 generation），之後的保存與比對都用它。
  - **收尾依已知事實分成三種**：
    - **未開始**：開始對話之前的出口，包括複製、掃描、大小上限、`kept` 上限。清掉自己的 `running`，不算一輪，`runs` 不變。
      清不掉就留著，不宣稱已清。
    - **已執行**：對話結束、指令確認停止之後的每個正常出口，這一輪都要記進說明檔，並清掉 `running`。
      - 保存已經記下時，不再記。
      - 還沒記的，另外寫一次，只記這一輪。包括工作區驗證不過、sidecar 剝除失敗、env 剝除失敗、保存前就失敗、保存
        意外失敗。
      - 這一次寫入本身寫不進去時（拿不到鎖、套件已不是原來那個、說明檔被換、秘密清單不完整、寫入失敗），`running`
        就留著。
    - **指令無法確認停止，或未預期的例外**：不碰說明檔，`running` 留著。
      - 前者是因為 D52 不許在那裡等 threadpool。
      - 後者是選擇：留給下一輪記成 `interrupted`，比在例外路徑上補寫單純。
  - **「只記這一輪」與清 `running` 的寫入**：要在鎖內確認四件事：套件身分、`draft_id`、預期的 generation（開工寫入交回的
    那一個），以及 `running.job_id` 是這個 job。
    - 任何一項不符就不寫，不重讀最新的說明檔、改對它補記。
    - 這項比對只管 `running` 的收尾。`clear_publishing` 照舊用發布時的預期 generation。
  - **上一個 `running` 沒清**：下一輪寫入 `running` 時發現已有標記，先把它記成一輪。
    - 結局用新的 `interrupted`，`finished_at` 留空，`job_id` 與 `started_at` 取自舊標記。
    - 不拿發現的時間當結束時間，也不寫成 `failed`：那是一輪沒有留下結束紀錄，不是一次已知的失敗。
    - 沒有其他占用名額的 job，但這證明不了它的指令已經停止。
- **送出接續**：
  - **請求**：`draft_id` 與 `draft_generation` 要嘛都有、要嘛都沒有，否則 422。`draft_id` 要符合 `DRAFT_ID_PATTERN`，
    `draft_generation` 至少為 1。帶了這一對，就不需要意見或紀錄。
  - **沒帶這一對**：
    - 有草稿 → `draft_pending`。可接續時說「請接續或放棄」，其他狀態說「請先放棄」；狀態由清單用的同一個判定算出。
    - 沒有草稿 → 第一輪，照現行流程。
  - **帶了這一對**：名額之後再讀一次說明檔，依序看第一個成立的那一條：
    1. 看到 `draft/` 不存在 → `draft_gone`。
    2. `draft/` 看不到，或說明檔讀不出 → `draft_unusable`。
    3. `draft_id` 不同 → `draft_gone`。
    4. `generation` 不同 → `draft_changed`。
    5. 檔案目錄不在，或不是目錄 → `draft_unusable`。
    6. 有 `publishing` → `draft_publishing`。不讀 origin，所以已發布與結果未知都擋得住。
    7. 說明檔的 `base_vid` 不是 `current` → `version_mismatch`。後端自己比，不只靠前端送來的 `expected_vid`。
    8. 路由第一次讀到的不是同一份 `(draft_id, generation)`，包括第一次讀不到 → `draft_changed`。這一輪用的紀錄，必須
       是判定的那份說明檔記著的。
  - 每個拒絕碼在路由都有對應，沒有對應的不能變成 500。
- **複製進暫存工作區**：
  - **用保存的同一條複製管線**，來源是草稿的檔案目錄，目的地是新的暫存工作區：
    - 連結以來源為根判斷，並改寫成相對連結；
    - 邊複製邊累計檔案數與大小；
    - 在複本上再判一次連結並解析；
    - 複本整棵重掃秘密，命中的路徑不帶入。

    複本要保住 `tree_digest` 看得到的東西（權限位元），否則 `copied_out` 與 `copied_in` 永遠不同，上一份永遠刪不掉。
  - **不帶入的根目錄條目**：根目錄的 `.env`，含大小寫不同、但其實是同一個條目的名字；以及 `.afterthread.meta/`。
    - 判斷「是不是同一個條目」的查詢失敗（而不是看到不存在）時，也不帶入，記成沒帶入（讀不到）；上一份會因此留在 `kept`。
    - 這項寬容只限這一個判斷：整棵的掃描失敗，仍然是不開始。
    - 第一輪的來源是版本目錄，照舊。
  - **持共享鎖**，在 `_still_the_package` 與說明檔比對之後才複製。複製之前先量一次大小，超過就不開始；這一步只負責提早
    拒絕，實際的上限由複製時的累計守住。
  - **沒帶入的清單**：完整的留在記憶體；寫進這一輪的紀錄與提示時才截短。
- **附上的紀錄**：
  - 這一輪新附的紀錄，在一輪結束、記進說明檔的那次寫入時（保存，或只記這一輪）併進 `runs`：新附的排在前面，去重，保留
    最近附上的 3 筆。看的是附上的先後，不是執行時間。
  - 這一輪用的就是這份合併後的清單。
  - 沒開始的一輪不改 `runs`。被中斷的一輪，它新附的紀錄不留；下一輪要用就再附一次。
- **接續提示**：
  - **各段上限**：
    - 原本的意見 20,000；這一輪的說明 20,000。
    - 上一輪：停止原因與錯誤 2,000、summary 2,000、handoff 4,000、operator_action 1,000；上一輪操作者的說明 20,000。
    - 更早的輪次每輪一行，最多 4 行，每行 300 字。
    - 沒帶入的檔案、變更的檔名，各最多 50 筆，每筆 300 字，附「另有 N 筆」。
    - 附上的紀錄沿用各自的存檔上限，重新遮蔽後再截。
  - 說明檔的 `NOTE_CAP` 提高到 20,000，與請求的上限一致。
  - **總上限**：使用者提示不超過 `char_allowance(llm_prompt_budget_tokens)`；系統提示加使用者提示，不超過
    `char_allowance(llm_tool_conversation_budget_tokens)` 的一半。標題、固定指示與省略標記都算在內。
    - 超過時的縮減順序：先縮更早的輪次與兩份清單，再縮附上紀錄的內文、`config.env`、`tool.json`、原本的意見、上一輪的
      筆記；這一輪的說明與固定指示最後才縮。
    - 第一輪用同一個函式。單欄上限與總上限都可能讓第一輪的提示和現在不同，不追求逐字相同。
  - **`tool.json` 從整理好的暫存工作區讀**；`config.env` 與 `.env` 照舊每輪從套件層重讀。
  - **附上的紀錄的說法**：
    - `run.vid == base_vid`：說「執行的是這份草稿的基底版本，工作區可能已經改過，請先確認現況」。
    - 不同：保留原本的 vid 與警告。
    - 已清除、只剩摘要的紀錄：不給重跑的指示。
  - **變更清單**：排除根目錄的 `.afterthread.meta/`。任一邊雜湊不出來時寫「無法列出」，不寫「沒有變更」。
- **文字不宣稱草稿的檔案是哪個時點的**：
  - `attempt_count` 只是嘗試的次數。保存沒存成之後，草稿的檔案可能來自更早的某一輪，操作者也可能手改過。
  - 所以不說「草稿是第 N 輪結束時的狀態」，改說這一輪的進度沒有存進草稿，請取回需要的內容。
  - 剛保存成功的那一輪，卡片的「進度已保存（第 N 輪）」照舊成立。
- **卡片**：
  - **對目前草稿的宣稱與按鈕**，只在下列條件都成立時出現：
    - 清單的草稿與 job 的 `draft_id`、generation 都相同；
    - 清單資料來自觀察到 job 結束之後才發起、並且成功完成的那次讀取。重讀失敗不算。

    generation 不同時，說「目前的草稿已不是這張卡片對應的那一份」，不給按鈕。沒有對應工具列的卡片一律不給按鈕。按鈕另外
    還要求草稿是可接續的狀態，而且沒有其他工作在跑。
  - **這一輪自己的結果**一律顯示，不受上面的條件限制：保存與否、原因、`retained_path`。它可能是成果唯一的取回位置。
  - **按鈕**：P4 只放「接續修正」「加上說明後接續…」。「發布草稿」等 P5；「放棄」留在工具列的草稿提示，確認框在那裡。
  - **`saved` 為 True 時**：先說「進度已保存（第 N 輪）」，再帶 `reason` 與 `retained_path`。`retained_path` 不再
    一律說成「未能存成草稿」。
