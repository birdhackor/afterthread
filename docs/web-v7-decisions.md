# web-v7 裁決紀錄

沿用 web-v4～v6 的體例：`docs/web-v7-plan.md` 寫**打算**做什麼，`docs/web-v7-design.md` 是設計本體，
本文件寫實作過程中計畫沒寫到的判斷，以及 review 的處置。逐階段接續，從 D48 起編號。

## D48（設計）：已審定的決策

以下是兩輪設計審查後定案、各階段派工都以它為前提的決策；推翻任何一條都要先改設計文件並重新審查。

| 決策 | 內容 | 推翻的代價 |
|---|---|---|
| 存放位置 | 草稿在套件層 `.afterthread.meta/draft/`，不在 `.staging`、不進 SQLite | 刪除工具、同名重裝、sweep、README 的 `.staging` 指示都要重新設計 |
| 接續模型 | 每一輪都從草稿複製到新的暫存工作區；草稿只在保存時換新 | 子行程與保存的競爭、唯一成果的保護要重新設計 |
| 識別 | 接續與放棄以 `(draft_id, generation)` 樂觀比對，`draft_id` 放棄後不重用 | 跨分頁的舊畫面會刪掉或重跑沒看過的成果 |
| 過期 | 只由 `current != base_vid` 判定；基底內容的變更是資訊、不是閘門 | 執行期寫檔的工具會讓草稿無故過期；也等於推翻 v5 §12 |
| 秘密 | 保存與複製進暫存時都用完整掃描器；命中的路徑保留上一份或不存；掃描失敗就不存 | 草稿會長期保存明文秘密 |
| 模型自述欄位 | `handoff`、`operator_action` 只用來顯示與交接，任何邏輯都不讀 | 會重開 v6 R11 不採用模型自報分類的理由 |
| 人接手的出口 | 發布草稿（不經 AI）是 P5 的範圍 | 只差設定的修正必須再付一輪 |

## D49（P1）：單一請求逾時的歸類

openai SDK（2.45.0）對單一請求的逾時擲 `openai.APITimeoutError`。它是 `APIConnectionError` 的子類別、屬於
`OpenAIError`，不是 builtin `TimeoutError`，所以只認 builtin `TimeoutError` 的歸類會把它算成上游錯誤。設計 §5
把「單一請求逾時」與「上游錯誤」分開，因此 `StructuredRunStats.failure` 把 `APITimeoutError` 記為
`request_timeout`，它的父類別與其他 SDK 錯誤仍記 `upstream`；請求本身擲出、整場期限沒有觸發的 builtin
`TimeoutError` 也記 `request_timeout`。擲出的例外與訊息不變（DJ）。卡片的 `request_timeout` 文案點名
`OPENAI_TIMEOUT_SECONDS`：`_get_client` 以它建出 client，作為每個請求的逾時。

## D50（P1）：`operator_action` 不限於沒做完

模型可以在 `run_shell` 裡帶新值驗證過程式、回 `ready=true` 發布，而套件的 `config.env` 仍要操作者貼上那一行。
提示因此要求：只要操作者必須在工作區外動手就寫 `operator_action`，不論做完與否；`handoff` 只在沒做完時寫。
前端在已發布的修訂卡片上也顯示「需要你動手」與交接筆記；停止原因在已發布的卡片上只在 `stopped_by` 有值
（預算結束了工具階段）時才顯示。設計 §4.1、§8 已照此更新。

## D51（P1）：前端不寫設定的上限值

設定的上限只定義在 `config.py` 的 `Field(le=…)`，超過上限的值在載入設定時就被拒絕。前端手抄一份，後端改邊界時
會無聲過時；卡片因此只點名設定名稱，不寫上限數字。

## D52（P2）：以中止訊號停止 builder 指令，不從外部殺

設計 §3.3 第 1 步原本寫「登記 `Popen`，逾時用 `tools._kill_process_group` 殺」。從外部
`killpg(getpgid(pid))` 可能落在 worker 的 `proc.wait()` 回收之後，打到已被重用的 PID，正是
`_communicate_bounded` 的 `teardown_lock`／`reaped` 要擋的情形。

實作改為每場 session 一個 `_BuilderShells`：一個 `threading.Event` 加上強參照的 task 集合。
`stop_and_wait` 先設訊號，再等每個指令的 worker 回報停止證據。`_communicate_bounded` 在輪詢時看到訊號，
就用它既有、在鎖下的拆除流程殺掉並回收；訊號設下之後才要啟動的指令不啟動。

「已停止」只有一個定義：指令的 leader 已回收，而且回收之後觀察到它的 process group 已不存在
（signal 0 得到 `ProcessLookupError`）；或它根本沒有啟動子行程。證據由 `_communicate_bounded` 的拆除在觀察到的當下
記下（`on_reaped`），不論函式之後正常返回還是擲出例外。送訊的結果都不是證據：`killpg(SIGKILL)` 成功只代表送到了
送訊當下的成員，送到不等於已退出；macOS 還會先收集成員再逐一送，送訊途中 fork 出來的成員根本收不到，審查時實測過
這種成員在證據記下之後仍在寫檔。EPERM 也不是：在 macOS 它代表沒有活的成員可送（只剩殭屍，leader 或非 leader 都算），
在兩個平台它也可能代表活的成員都是這個程序殺不了的。被 SIGKILL 的成員要等它的回收者（init、launchd）收走，
group 才會消失，所以確認要輪詢：第一次緊接在回收之後、不先等待，之後持續到拆除的時限為止。回收本身
若已用掉時限，仍會確認那一次；那時看到的消失仍是真的，只是可能晚於等待的一方放棄。

拆除只有一個時限：開始時以 `_REAP_TIMEOUT_SECONDS` 起算，回收前補送、回收後輪詢與 reader 的 join 共用它；
回收 leader 本身沒有上限，SIGKILL 回收不了的 leader 會佔住它的 worker，停止等待仍在自己的上限結束、算無法確認。
group 一消失，就沒有成員還拿著管線的寫端，join 立刻完成，所以等待上限不必逐段加總。回收前補送只在 macOS 做：
leader 未回收時 PGID 被它釘住，補送 SIGKILL 直到確認沒有活的成員可送（EPERM）或 group 已不存在（ESRCH），
或時限到；補送的退出不是證據，回收後的 ESRCH 才是。Linux 不需要也不能這樣做：它的群組訊號連進行中的 fork
都送得到，而殭屍 leader 未回收時 signal 0 一直回成功，迴圈會燒滿時限。回收之後不再送任何 kill，因為 PGID
已不再被 leader 釘住。
交給 `_communicate_bounded` 的 leader 只由拆除回收：輸出超量時的 kill 也直接對 `proc.pid` 送 `killpg`，不經 `getpgid`（macOS 對已退出的
leader 回 ESRCH），也不回落到 `proc.kill()`（它先 `poll()`，會回收已退出的 leader）。

啟動失敗的指令另有一條路：`_ShellPopen` 保留建構失敗的 `Popen`，依 CPython 留下的記錄判定。沒有 pid 是 fork 之前就失敗，
算沒有啟動；有 returncode 是 CPython 已回收 exec 失敗的子行程，之後 group 也已不存在才算已停止；fork 了卻沒被回收，
算無法確認，不殺它（它可能還沒 `setsid`）。例外的型別不是證據。

除了上面的送訊結果與例外型別，以下三種替代訊號也都試過、也都被推翻：
- asyncio task 的狀態：uvicorn 關閉時 `asyncio.run` 會取消所有 task，被取消的 command task 看起來已完成，
  它等待的 threadpool worker 卻還在跑；
- worker 返回：它可能在啟動子行程之後、拆除完成之前就被例外打斷；
- 時間到：只能說「等不到」，不能說「已停止」。

等待上限是 `tool_install_shell_timeout_seconds` 加上 `_REAP_TIMEOUT_SECONDS`。超過時不剝除、不發布，
也不清理這一場的暫存目錄：它原地保留，job 失敗並在訊息裡附上路徑；名額照放，理由見下一段。
等不到證據的情況例如：kernel 回收不了的 leader、回收失敗、group 在時限內沒有消失（送訊途中 fork 出來
而沒收到的成員、殺不了的成員、卡在不可中斷 kernel 等待的成員、沒有回收者收走的殭屍，例如服務在
Linux 上是 PID 1 而沒有 init）、
拆除完成之前被例外打斷、被卡住的執行緒（例如已啟動子行程、卻在第一次輪詢前停住）。
這個出口不得再等待可能被卡住的資源，例如卡住的 worker 佔著的共用 threadpool。至於沒有被排程、根本
沒進入 worker 的指令，它之後看到訊號就不會啟動，算作沒有啟動子行程（`entered` 握手；這個推導依賴
GIL 下的單一全序）。

「名額照放」不是 DC 的例外，而是從 DC 推導出來的：名額守的是後端寫入者之間的互斥（`_admit_job`），
一場已永久放棄保存、發布、清理的 session 不再是寫入者；殘留的 `run_shell` 指令也不是後端寫入者，它只在
自己的暫存目錄裡跑，碰不到下一個 job 的暫存目錄。「扣到確認停止」實際上就是扣到重啟，因為不返回的
worker 生不出證據。

這個推導的前提是：後端永不再碰保留的工作區。目前成立：`.staging` 只對空目錄 `rmdir`，`_sweep_stale_backups` 只收 `_STALE_BACKUP_RE`、`versions/*.discarded`，以及各套件 `.afterthread.meta/` 底下屬於草稿的命名（D54），下一場用新的 uuid。
守衛是一則測試：保留一個工作區之後再跑一場 job，那個目錄原封不動。日後若有步驟會去碰舊的 `.staging` 目錄
（例如啟動時清掃），名額或每個工作區一個標記就得回來。

不變量 DA 依賴 DC：`scan_embedded_secrets` 以路徑走訪子目錄（`os.scandir`），目錄在分類之後被換成連結時
會走出工具包；它只在工作區已靜止時才可靠。若日後要掃描別人可能同時在改的樹，改用以 fd 走訪
（`O_DIRECTORY | O_NOFOLLOW` 加 `os.scandir(fd)`）。

設計 §3.3 第 1 步與 §9 的 DC 已照此更新。

## D53（P2）：後端產生的路徑不遮蔽

回報給操作者的暫存目錄、草稿目錄等路徑，只由設定的工具目錄、固定名稱與隨機 id 組成，不含操作者或檔案提供的文字。
它們不經秘密遮蔽：操作者要原樣複製它們；而遮蔽要掃描工具目錄，必須在 worker 上做。在「無法確認停止」的出口，
worker 可能正是卡住的資源。

不遮蔽不等於不做可編碼處理：Linux 上工具目錄的路徑可以含非 UTF-8 位元組，原樣送進 JSON 會讓整個回應失敗。
API 回應裡的後端路徑都換成可編碼的形式（欄位用同一個型別，錯誤訊息裡的就地處理），代價是含替代字元的路徑
不能原樣拿去用。

## D54（P3）：草稿落地時的幾個判斷

實作者動手前先推導，主 agent 據此定案。設計 §3.3、§3.8、§7 已照此更新。

- **「有草稿」就是 `<pkg>/.afterthread.meta/draft/` 這個目錄項存在**，不論它的狀態。若把「沒有說明檔」當成沒有草稿，
  下一次保存寫出說明檔之後，sweep 會把當機時留下、內容完整的 `files-*` 當成孤兒刪掉。
- **放棄殘留留在同一層**：改名成 `.afterthread.meta/draft.discarded-<hex>`。同目錄改名，殘留跟著套件走，刪除工具時一起
  消失；不借用工具目錄層的刪除殘留命名。
- **鎖**：
  - 保存的第 8 到第 11 步持共享 tools lock。設計原本只寫到第 10 步，延伸到第 11 步，刪除上一份檔案目錄時也排除 `delete_tool`。
  - 放棄用「名額加共享鎖」，不用排他鎖：AI 請求整段都持共享鎖，用排他鎖會在對話進行中讓放棄回 409。名額已排除 job 與
    sweep，共享鎖讓 `delete_tool` 回 409。
  - 草稿的 sweep 在 `_sweep_stale_backups` 的排他鎖內執行，自己不取鎖；持共享鎖時不呼叫會取排他鎖的函式。
- **連結**：目標路徑裡 `..` 緊接在本身是連結的元件之後，就不存（§3.3 第 6 步）。
- **文字清理在 P3 自己的邊界，不改 `llm.py`**：
  - 說明檔寫入時，每個字串依序遮蔽、截斷、套 `_utf8_safe`，再以寫進檔案的形式檢查（D55）；讀出時套 `_utf8_safe`，
    交給 API 前再遮蔽一次。
  - 模型文字進不來：結構化輸出的文字欄位經 `memory_ai._coerce_str`，遇到 lone surrogate 就驗證失敗、觸發修正重試。
  - P3 真正的 surrogate 來源是檔名（掃描命中的路徑、沒存的路徑），以及從磁碟讀回的說明檔。
- **輪數**：說明檔另記累計輪數 `attempt_count`；`attempts` 只留最近 5 輪，每筆帶自己的 `number`。job 與列表的
  `draft.attempts` 都取累計輪數。
- **第一輪的 `origin.feedback` 也帶「草稿 `<draft_id>`，經過 N 輪」**：第一輪在 `ready=true` 時也會先保存再發布，
  帶了這一行，發布成功而刪草稿失敗時，§3.7 的「已發布」才判定得出來，而不是落到「結果未知」。
- **發布失敗時，回報成果實際所在的路徑**：發布分兩段搬移（`build` 先到同一場的 `shell`，再進 `versions/<vid>`），
  成果可能已經不在暫存目錄裡。


## D55（P3）：檢查要落在真正存下、真正動到的那個對象上

保存與放棄的幾道檢查，原本落在相鄰但不同的對象上：大小與連結量的是換回舊版**之前**的工作區，草稿拿到的卻是
換回之後的樹；讀取與放棄經過 `.afterthread.meta/` 的別名，保存與 sweep 卻不經過；`finally` 只在正常返回的
路徑上決定要不要保留暫存目錄。這裡的決定一律改成檢查那個真正被存下或被動到的對象。設計 §3.1、§3.3、§3.8、
§9 已照此更新。

- **連結在複本上再判一次**：換回舊版會改變路徑上的元件是不是連結、指向哪裡。一般檔案換成連結，或連結換成
  目標不同的連結，都會讓工作區上判過的連結在草稿裡走出去。複製完成後，以複本為根把每個連結判一次，先全部
  判完再刪；工作區上的那一次判斷保留，負責決定要不要規劃。只排除「一般檔案換成連結」是不夠的：連結換連結
  一樣會改變解析路線。
- **大小上限算複製出來的東西**：在複製時邊寫邊累計，換回的舊版也算；舊版的來源可能在保存途中被手改，只在
  規劃時加總會被超過。掃描前對工作區的那一次保留，它限的是掃描的成本。
- **草稿只經由套件自己的、真目錄的 `.afterthread.meta/` 到達**：它是連結或不是目錄，這個套件就沒有自己的
  草稿。否則一個工具的列會顯示另一個工具的草稿，用它的 token 放棄會刪掉那一份。`lstat` 本身失敗（不是不存在）
  時，讀取照舊「看不到就當作有」，寫入照舊不寫；放棄也是寫入，看不到就不動手，回報沒刪。寫入者經由專用的
  入口拿路徑，那個入口只交出看得到的路徑，所以「看不到」不必靠每個呼叫者記得去看。
- **發布這條路上，暫存目錄要有人接住成果才清**：從發布前的保存開始（取消送達時保存的 worker 可能還在跑，所以
  旗標在保存開始之前就立起），到發布的結果處理完為止，例外或取消都保留暫存目錄。發布的 worker 可能還在寫時
  也保留：只有它正常返回或自己丟出例外，才算結束。組版本來源說明失敗算發布失敗。
- **「已刪除」只靠親眼看到不存在**：放棄只在 `lstat` 回「不存在」時回報已刪；其他錯誤都回報 `draft/` 本身是
  殘留，不把「看不到」當成「不在了」。
- **存下的複本整棵重掃**：工作區上的掃描決定規劃，存下的卻是複本，兩者在換回舊版與改寫連結目標的地方不同。
  複本做好、連結判過之後，用保存開始時那一份已知秘密把複本整棵再掃一次，命中的路徑刪掉並記成沒存；
  這次掃描失敗就整輪不保存檔案。它涵蓋原本對換回檔案的逐檔重掃，那一道因此拿掉。接續把草稿複製進新的
  暫存工作區時，用同一個步驟。
- **沒有說明檔時，token 由 `draft/` 裡實際有的東西算**：說明檔在時，它的 inode、ctime、size 分得出不同次
  建立；不在或讀不到時，另把 `draft/` 直接成員的名字與身分算進去（保存建立的成員都帶隨機名字）。說明檔在時
  不加：sweep 收孤兒會改變成員，換來無謂的 409。
- **自由文字以寫進檔案的形式檢查**：在 str 上遮蔽之後，JSON 編碼（跳脫序列）與 `_utf8_safe`（替代字元）還會
  產生新的位元組，能在檔案裡拼出已知秘密，例如單引號的 PEM 在 `.env` 裡保留字面的 `\n`。所以每段自由文字遮蔽、
  截斷、scrub 之後，再以它在檔案裡的 JSON 字串字面、用同一個比對器檢查一次，命中就整段換成遮蔽標記。寫入前
  另有一道底線：把形狀由樣式檢查固定的欄位（識別字、時間戳、詞彙值）清空後的整份編碼再比對一次，命中就把
  全部自由文字降成標記重試，仍命中才放棄寫入。這道底線看得到以後新增、卻沒走遮蔽的欄位。識別字照舊不遮。
  - 照這樣檢查的寫入者：草稿說明檔、版本的 `origin.json` 與 `summary.json`（同一個 `tools._redacted`）、AI 日誌
    的 JSONL（`llm_log` 保留自己的一份 helper）。草稿複本已整棵重掃。執行紀錄（`tool_runs._storable`）是同一類
    但決定不守：它在遮蔽之後才把孤立 surrogate 寫成三個 U+FFFD，能拼出含連續三個 U+FFFD 的已知值；只有工具參數
    與訊息會帶 surrogate（輸出解碼時已換掉），讀出時又會再遮一次。理由寫在 `_storable` 旁。
  - 不涵蓋表示法層級的不同：秘密以真換行登記而文字是字面的 `\n`、base64 等其他編碼、`.env` 讀入時已被
    替換掉的位元組。精確比對本來就保護不了表示法改變。
  - 這一類的收斂不再看「某個檔案裡找不到」，而是看這份寫入者名單：每一個都標明以什麼形式檢查。
- **連結目標保留原本的元件**：絕對目標若先做字面正規化，`x/..` 會在判斷之前被摺掉，存下的連結指向另一個檔案，
  而且沒有記錄。字面正規化只對每個元件都是真目錄的那一段成立。所以只把根前綴（照給定或解析後的寫法）當文字剝掉，
  作業系統經由它一定走到根；其餘元件原樣交給同一條規則。在複本上再判一次，只能驗「存下的連結在複本之內」；驗不了
  「它還是原本那一個」，那個資訊在改寫時就沒了。所以連結這個領域的名單，是一則對作業系統的差分測試：列舉各種連結
  形狀，保存之後逐一比對複本裡與工作區裡解析到的位置。規則可以保守地拒絕作業系統其實解析在內的形狀，但要記下原因；
  測試不放秘密，驗的是沒有換回舊版的情形。
